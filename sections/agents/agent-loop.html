LLM может объяснить ошибку доступа, но для разбора конкретного случая ей могут понадобиться действующая инструкция и состояние сервиса. Заранее неизвестно, какие сведения окажутся достаточными и какое действие потребуется после первого результата. LLM-агент (LLM agent) решает эту задачу циклом: модель выбирает следующий шаг по доступному контексту, исполняющий код выполняет его и возвращает результат для нового решения. Разберём, где проходит граница между выбором и исполнением, какое состояние сохраняется между шагами и кто останавливает работу. Один пример доведём от первого запроса до минимальной реализации без агентного фреймворка.

Где заканчивается одиночный вызов LLM

Пользователь спрашивает: «При входе в корпоративный портал получаю ACCESS_CHECK_FAILED. Что делать?» Код ошибки, портал, инструкция и ответы инструментов далее условные: это один учебный пример, а не описание реальной системы.

Если передать модели только вопрос, она может перечислить правдоподобные причины: недостаточные права, истёкшую сессию, недоступный сервис авторизации. Но из строки ошибки не следует, какая причина действовала в этом случае. Дополнительные рассуждения над тем же входом не заменят отсутствующее наблюдение о сервисе.

Дадим помощнику две операции: search_instruction(query) ищет инструкцию во внутренней базе, get_service_status(service) читает страницу статуса. Найденная инструкция сообщает: ACCESS_CHECK_FAILED означает, что проверка доступа не завершилась; сначала нужно проверить сервис auth. Если зарегистрирован связанный сбой, он может объяснить симптом. Если сбоя нет, для продолжения нужны подробный текст ошибки и время её возникновения.

После поиска возникает новое решение: проверять статус, искать дальше или сообщить о нехватке данных? Его нельзя принять на основе результата, который ещё не получен. Можно собрать все нужные сведения заранее и сделать один вызов LLM для ответа — это достаточное решение, если состав сведений известен. Цикл нужен, когда результат одного действия определяет следующее.

Здесь одиночный вызов — один проход модели по уже подготовленному контексту без исполнения инструментов внутри него. Один HTTP-запрос к готовому сервису может скрывать несколько таких проходов и целый цикл на стороне сервера. Число запросов к API само по себе не определяет устройство системы.

Кому поручить выбор следующего шага

Первый вариант — заранее заданный процесс (workflow): код ищет инструкцию, проверяет статус по предусмотренному условию и выбирает ветку ответа. В нём могут быть циклы, ветвления и вызовы LLM, например для извлечения имени сервиса из текста. Важно, что разработчик заранее определил переходы между операциями.

Во втором варианте модель после каждого результата выбирает инструмент и аргументы либо завершает работу. Это агентное управление в принятом здесь смысле. Такое различие workflow и агента используется в инженерном разборе Anthropic; универсального определения слова «агент» у всех авторов нет.

Момент в нашем примереWorkflowАгентное управление
Инструкция найденаКод проверяет предусмотренное условие и переходит к чтению статуса auth.Модель читает результат и предлагает get_service_status(service="auth").
Статус не даёт объясненияЗаранее заданная ветка запрашивает подробности ошибки.Модель решает, есть ли полезное действие среди доступных, или завершает запуск с запросом подробностей.

Для нашей короткой инструкции workflow вполне достаточен: веток мало, их смысл известен. Агентный вариант интересен как устройство системы, которая сможет выбирать действия по содержанию разных найденных инструкций. За эту гибкость приходится платить вызовами модели для решений и возможностью выбрать ненужный шаг, неверные аргументы или преждевременное завершение. Сам факт наличия цикла не улучшает ответ.

На практике граница может быть локальной: поиск всегда запускается кодом, а дальнейшая диагностика поручается модели. Поэтому полезнее назвать конкретное решение, которое принимает LLM, чем классифицировать всё приложение одним словом.

Модель, исполняющий код, инструменты и состояние

Чтобы реализовать второй вариант, разделим четыре участника и состояние самого запуска. Это разделение ответственности, а не требование разнести их по разным процессам.

Часть системыОтветственностьВ нашем примере
МодельПо предоставленному контексту выбирает действие с аргументами либо завершение с ответом.Предлагает прочитать статус auth, поскольку так предписывает найденная инструкция.
Исполняющий код (runtime)Собирает контекст, проверяет формат решения, вызывает нужную функцию, сохраняет результат и контролирует предел шагов.Находит get_service_status в реестре и передаёт ему аргумент service="auth".
Инструмент (tool)Выполняет определённую операцию и возвращает результат или ошибку исполнения.Читает страницу статуса и возвращает сведения о зарегистрированном инциденте.
Внешняя среда (environment)Содержит данные и объекты, с которыми работают инструменты; может меняться независимо от запуска.База инструкций, сервис авторизации, страница его статуса и реальное состояние учётной записи.
Состояние выполнения (execution state)Хранит задачу, журнал решений и наблюдений, счётчик шагов и причину остановки.Вопрос пользователя, найденная инструкция и результат проверки статуса.

Наблюдение (observation) — результат взаимодействия, который код передаёт модели. Оно не равно полному состоянию среды: страница статуса может обновляться с задержкой и ничего не говорить о конкретной учётной записи. В нашем случае инструменты только читают данные. Состояние запуска меняется после каждого чтения, хотя сам помощник не меняет ни права пользователя, ни работу сервиса.

Доступный модели контекст (context) тоже не равен всему состоянию запуска. Это переданные в очередной вызов инструкции, описания инструментов, вопрос и выбранная часть журнала. В минимальном примере передадим весь журнал. Сохранённый результат, который не попал в контекст, не становится известен модели автоматически.

Вывод get_service_status(service="auth") — запрос на действие, а не свидетельство выполненной проверки. Исполнение начинается только тогда, когда код действительно вызывает инструмент. Если функция вернула ошибку, нельзя записать в журнал успешный статус сервиса.

Конкретный протокол передачи зависит от API. Например, для клиентских инструментов Claude модель возвращает блок tool_use, приложение исполняет операцию и отправляет связанный блок tool_result. Для серверных инструментов исполнитель находится у провайдера. Это разные размещения кода, но граница между предложением и исполнением сохраняется; см. официальное описание протокола.

Как выполняется агентный цикл

От вопроса к новому наблюдению

Начальный контекст содержит вопрос, правило «не утверждать причину без данных» и описания двух инструментов. Модель выбирает поиск инструкции с запросом ACCESS_CHECK_FAILED. Код проверяет имя функции и аргументы, записывает предложенное действие и вызывает поиск. Только после возврата инструмента в журнал добавляется найденная инструкция.

Следующий вызов модели получает этот журнал. Теперь в контексте есть правило диагностики и имя auth, поэтому модель может предложить чтение статуса. Код выполняет его тем же способом. Пусть инструмент вернул зарегистрированный инцидент: «Проверки доступа завершаются по тайм-ауту». В третьем решении модель завершает запуск: инцидент может объяснять ошибку; сначала следует дождаться восстановления и повторить вход, а при сохранении ошибки — предоставить подробности.

Модель не выбирает все будущие операции заранее. Второе решение принимается после поиска, третье — после чтения статуса. Если проверка вернула нормальный статус, контекст другой: из него нельзя заключить, что у пользователя неправильные права. В нашем примере доступных инструментов для дальнейшей диагностики нет, поэтому помощник должен попросить подробный текст ошибки и время, завершив текущий запуск.

Что именно обновляется между решениями

Обозначим состояние запуска перед решением через \(S_t\), сформированный из него контекст — через \(C_t\), решение модели — через \(D_t\). Для нашей реализации достаточно следующей записи:

\[C_t=\operatorname{buildContext}(S_t),\qquad D_t\sim p_{\theta}(\,cdot\mid C_t).\]

Здесь \(p_{\theta}\) — распределение решений, задаваемое моделью и выбранным декодированием. Решение имеет один из двух видов: вызов инструмента \(D_t=\operatorname{Call}(n_t,u_t)\), где \(n_t\) — имя и \(u_t\) — аргументы, или завершение \(D_t=\operatorname{Finish}(r_t,m_t)\), где \(r_t\) — причина и \(m_t\) — сообщение пользователю. Это контракт нашего цикла, а не обязательный формат всех API.

Для допустимого вызова исполнитель получает наблюдение \(O_t\) и обновляет состояние:

\[O_t=\operatorname{execute}(n_t,u_t;E_t),\qquad H_{t+1}=H_t\mathbin{\Vert}[D_t,O_t],\qquad S_{t+1}=(H_{t+1},t+1).\]

\(E_t\) обозначает внешнюю среду в момент исполнения, \(H_t\) — журнал с исходным вопросом, а \(\Vert\) — добавление записей в конец. Инструкции и реестр инструментов здесь фиксированы и не включены в изменяемую пару \(S_t\). Функция исполнения включает чтение среды и упаковку результата; \(O_t\) может содержать ошибку. Завершение обрабатывается отдельной веткой: сообщение возвращается пользователю, нового вызова инструмента нет.

Запись объясняет две ошибки реализации. Если добавить в журнал только решение \(D_t\), модель увидит собственное намерение, но не результат. Если получить \(O_t\), но не включить его в следующий \(C_{t+1}\), исполнение состоялось, однако новое решение не сможет учитывать полученные сведения.

В статье ReAct взаимодействие также строится вокруг действий и новых наблюдений, а конкретный рецепт добавляет текстовые рассуждения между ними. Для показанного здесь контракта отдельное поле с рассуждениями не требуется: исполнитель работает с действием, аргументами и результатом.

Когда остановиться

У цикла должен быть явный результат, чтобы вызывающая программа могла отличить ответ от незавершённой диагностики. В нашем контракте предусмотрены три штатных исхода.

ИсходКто инициируетЧто возвращается в примере
completed: задача ответа завершенаМодель предлагает Finish; код завершает запуск.Объяснение возможной связи с зарегистрированным инцидентом и следующий шаг пользователя. Это не означает, что доступ восстановлен.
blocked: продолжение требует недоступных данныхМодель предлагает Finish с указанием препятствия.Статус нормальный либо прочитать его не удалось; для продолжения нужны подробности ошибки. Они перечислены в сообщении.
step_limit: исчерпан предел решенийИсполняющий код, независимо от желания модели продолжать.Честное сообщение о незавершённой диагностике и сохранённый журнал.

Метка completed фиксирует решение завершить задачу ответа, а не устанавливает истинность причины. Даже инструмент, который успешно прочитал страницу статуса, подтверждает только содержание этой страницы. Успех исполнения операции, завершение запуска и правильность вывода — разные свойства.

Ошибка инструмента сама по себе не обязана останавливать цикл: модель может выбрать другой источник или завершить работу с указанием препятствия. Например, тайм-аут чтения страницы статуса означает «наблюдение не получено», а не «сервис авторизации недоступен». В нашем небольшом наборе инструментов другого способа проверить статус нет.

Предел считаем по вызовам модели для выбора решения. Поиск, проверка статуса и финальный ответ требуют трёх решений и двух исполнений инструментов. При пределе в два решения после чтения статуса цикл остановится: финальный ответ потребовал бы ещё одного вызова модели. Дополнительный вызов для «итогового резюме» тоже нужно было бы включить в бюджет.

Конечный предел решений ограничивает число итераций, но не время одного вызова. В реальном адаптере модели и инструментах нужны тайм-ауты; иначе операция может зависнуть внутри первой итерации. Ошибка протокола, например неизвестное имя инструмента, также отличается от нехватки данных для диагностики.

Минимальный цикл на Python

Ниже — исполняемый код на Python 3.10 или новее. Сам цикл и диспетчер реализованы полностью; два инструмента возвращают условные локальные данные. Функция call_model — не реализованная заглушка адаптера LLM: прямой вызов с ней завершится NotImplementedError. Ниже подставим заранее заданные решения, чтобы проверить механику без модели и сетевых запросов.

Адаптер получает словарь контекста и должен вернуть ровно один объект Call или Finish. Он переводит наши описания инструментов в схему выбранного API и преобразует ответ API в этот контракт. Если генерация оборвалась или ответ не разобран, адаптер должен сообщить об ошибке, а не выдавать её за финальный ответ. Поддержка нескольких вызовов в одном ответе здесь намеренно не реализована.

from copy import deepcopy
from dataclasses import dataclass


@dataclass(frozen=True)
class Call:
    name: str
    args: dict


@dataclass(frozen=True)
class Finish:
    status: str  # "completed" или "blocked"
    message: str


def search_instruction(query):
    if "ACCESS_CHECK_FAILED" not in query:
        return {"found": False}
    return {
        "found": True,
        "id": "access-17",
        "text": (
            "ACCESS_CHECK_FAILED: проверка доступа не завершилась. "
            "Проверьте статус auth. Связанный инцидент может объяснять "
            "ошибку; если инцидента нет, нужны подробный текст и время ошибки."
        ),
    }


def get_service_status(service):
    if service != "auth":
        return {"known": False}
    return {
        "known": True,
        "service": "auth",
        "status": "incident",
        "details": "Проверки доступа завершаются по тайм-ауту.",
    }


TOOLS = {
    "search_instruction": {
        "description": "Поиск инструкции по тексту или коду ошибки.",
        "parameter": "query",
        "run": search_instruction,
    },
    "get_service_status": {
        "description": "Чтение страницы статуса указанного сервиса.",
        "parameter": "service",
        "run": get_service_status,
    },
}

RULES = (
    "Выбери один Call или Finish. Опирайся на результаты инструментов. "
    "Не считай предложенный вызов выполненным. Не утверждай причину "
    "без данных. Если продолжить нельзя, верни blocked и назови, чего не хватает."
)


def call_model(context) -> Call | Finish:
    # Заглушка: здесь нужен адаптер к выбранному API модели.
    raise NotImplementedError("Подключите LLM или учебную подстановку")


def run_agent(question, model=call_model, max_steps=3):
    if type(max_steps) is not int or max_steps < 1:
        raise ValueError("max_steps должен быть положительным целым")
    history = [{"kind": "user", "text": question}]
    tool_descriptions = {
        name: {
            "description": spec["description"],
            "required_string_argument": spec["parameter"],
        }
        for name, spec in TOOLS.items()
    }

    for step in range(max_steps):
        context = {
            "instructions": RULES,
            "tools": tool_descriptions,
            "history": history,
            "remaining_decisions": max_steps - step,
        }
        decision = model(deepcopy(context))

        if isinstance(decision, Finish):
            if decision.status not in {"completed", "blocked"}:
                raise ValueError("Недопустимый статус Finish")
            if not isinstance(decision.message, str) or not decision.message.strip():
                raise ValueError("Finish должен содержать сообщение")
            return {
                "status": decision.status,
                "message": decision.message,
                "steps": step + 1,
                "history": history,
            }

        if not isinstance(decision, Call) or not isinstance(decision.name, str):
            raise ValueError("Ожидался Call или Finish")
        spec = TOOLS.get(decision.name)
        if spec is None:
            raise ValueError("Неизвестный инструмент")
        parameter = spec["parameter"]
        if (not isinstance(decision.args, dict)
                or set(decision.args) != {parameter}
                or not isinstance(decision.args[parameter], str)
                or not decision.args[parameter].strip()):
            raise ValueError("Нужен ровно один указанный строковый аргумент")

        call_id = f"call-{step + 1}"
        history.append({"kind": "call", "id": call_id,
                        "name": decision.name, "args": deepcopy(decision.args)})
        try:
            data = spec["run"](**decision.args)
            observation = {"ok": True, "data": data}
        except OSError as error:
            # Например, TimeoutError: наблюдение о сервисе не получено.
            observation = {"ok": False, "error": type(error).__name__}
        history.append({"kind": "observation", "call_id": call_id,
                        **observation})

    return {
        "status": "step_limit",
        "message": "Диагностика не завершена: исчерпан предел решений.",
        "steps": max_steps,
        "history": history,
    }

В context передаются описания инструментов, но не их Python-функции. Исполнение находится в строке spec["run"](**decision.args); добавление записи call перед ней лишь фиксирует запрос. Пара id / call_id связывает результат с конкретным вызовом. Копия контекста отделяет вход адаптера от изменяемого журнала исполнителя.

Обработчик OSError выбран для этого примера: реальный инструмент должен переводить ожидаемые ошибки своего HTTP-клиента в договорённый формат. Ошибки программирования и нарушения контракта здесь прерывают выполнение исключением. Проверка аргументов подтверждает допустимость вызова, но не проверяет, разумно ли модель выбрала инструмент.

Учебный прогон без LLM

Подстановка ниже возвращает три заранее записанных решения. Это не агентное управление моделью и не проверка её качества: так воспроизводится конкретная траектория, чтобы проверить передачу результатов и остановку.

decisions = iter([
    Call("search_instruction", {"query": "ACCESS_CHECK_FAILED"}),
    Call("get_service_status", {"service": "auth"}),
    Finish("completed", "Инцидент auth может объяснять ошибку. "
           "Дождитесь восстановления и повторите вход; "
           "если ошибка сохранится, пришлите подробный текст и время."),
])

result = run_agent(
    "При входе в портал получаю ACCESS_CHECK_FAILED. Что делать?",
    model=lambda context: next(decisions),
    max_steps=3,
)
print(result["status"], result["steps"])  # completed 3
print([item["kind"] for item in result["history"]])
# ['user', 'call', 'observation', 'call', 'observation']

Для реального запуска заменяется адаптер, а учебные инструменты подключаются к источникам данных. Следующее решение должно зависеть от полученного контекста: нормальный статус и ошибка чтения требуют другого исхода, чем инцидент. Чтобы воспроизвести предел в два решения, заново создайте итератор и передайте max_steps=2: получите step_limit с обоими наблюдениями, но без финального решения модели.
