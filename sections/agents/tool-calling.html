В первом разделе модель возвращала исполнителю готовый объект Call или Finish, а адаптер к LLM оставался заглушкой. Языковая модель так не умеет: она продолжает последовательность токенов. Вызов инструмента (tool call) — это фрагмент текста в формате, которому модель научили, а действием его делают сервер и исполняющий код. Шаблон чата вставляет описания функций в промпт, парсер извлекает вызов из ответа, код проверяет аргументы и только потом исполняет. Разберём, что на каждом этапе обеспечивают обучение, JSON Schema, ограниченное декодирование и проверки в коде. Пример диагностики ACCESS_CHECK_FAILED доведём до адаптера к OpenAI-совместимому серверу.

Вызов инструмента — продолжение текста

Возьмём для примера открытую модель Qwen3-4B-Instruct-2507; её формат вызовов здесь сверен с шаблоном чата чекпойнта 8 октября 2026 года. Код обращается к серверу через API: передаёт список сообщений и отдельное поле tools с описаниями функций. Модель же получает одну последовательность токенов. Её собирает шаблон чата (chat template) — программа на языке шаблонов Jinja, которая хранится вместе с токенизатором чекпойнта.

Шаблон этого чекпойнта дописывает к системному сообщению заголовок # Tools, описания функций в JSON по одному на строку между <tools> и </tools> и инструкцию: каждый вызов — объект с полями name и arguments между тегами <tool_call> и </tool_call>. Начало первого запроса в нашем примере (описания сокращены):

<|im_start|>system
Ты помогаешь диагностировать ошибки доступа к корпоративному порталу. …

# Tools

You may call one or more functions to assist with the user query.

You are provided with function signatures within <tools></tools> XML tags:
<tools>
{"type": "function", "function": {"name": "search_instruction", "description": "Ищет инструкцию …", …}}
{"type": "function", "function": {"name": "get_service_status", …}}
{"type": "function", "function": {"name": "ask_user", …}}
</tools>

For each function call, return a json object with function name and arguments within <tool_call></tool_call> XML tags:
…<|im_end|>
<|im_start|>user
При входе в портал получаю ACCESS_CHECK_FAILED. Что делать?<|im_end|>
<|im_start|>assistant

Последняя строка — заготовка хода ассистента, дальше пишет модель. Чтобы вызвать инструмент, она начинает ответ с <tool_call> и продолжает JSON:

<tool_call>
{"name": "search_instruction", "arguments": {"query": "ACCESS_CHECK_FAILED"}}
</tool_call><|im_end|>

В словаре этого токенизатора <tool_call> и </tool_call> — отдельные токены. Поэтому выбор «вызвать инструмент или отвечать» в простейшем случае — выбор первого токена ответа: <tool_call> или начало обычного текста. <|im_end|> входит в стоп-токены чекпойнта, и на нём сервер заканчивает генерацию.

Затем парсер вызовов (tool call parser) сервера ищет теги в тексте, разбирает JSON и возвращает клиенту не текст, а структуру: поле tool_calls с именем функции, аргументами в виде JSON-строки и идентификатором, а finish_reason равен "tool_calls". В vLLM этот формат разбирает парсер hermes; авторы Qwen3 рекомендуют для модели именно его. Исполнитель выполняет функцию и отправляет результат сообщением с ролью tool. Шаблон этого чекпойнта оборачивает результат в <tool_response>…</tool_response> и помещает в ход user. Для модели результат инструмента — ещё один фрагмент текста в контексте.

Формат — свойство чекпойнта, а не модели вообще. Qwen3-Coder из того же семейства обучен записывать вызов иначе: <function=имя> и каждый аргумент отдельным блоком <parameter=…>; для него в vLLM нужен парсер qwen3_xml. Шаблон Llama 3.1 записывает вызов JSON-объектом с полем parameters вместо arguments. Если шаблон или парсер не совпадает с тем, на чём обучали, сервер не сообщает об ошибке. Модель получает непривычную разметку, и качество вызовов может упасть, а вызов, который парсер не узнал, остаётся в тексте ответа.

Поля tools и tool_calls в API — обёртка вокруг шаблона чата и парсера. Закрытые API устроены так же по смыслу: например, Anthropic сообщает, что из описаний инструментов собирается специальный системный промпт. Сама модель ничего не исполняет: она генерирует текст, по которому код решает, исполнять ли действие.

Откуда модель знает формат

Обучение на траекториях

Модель пишет <tool_call> там, где нужен инструмент, потому что её дообучали на диалогах с вызовами в этом формате. Один обучающий пример — траектория целиком: системное сообщение с описаниями, вопрос, вызовы, результаты инструментов, финальный ответ. При обучении она подаётся за один прямой проход (teacher forcing): модель предсказывает каждый следующий токен по настоящему префиксу, результаты уже записаны в последовательность. Пошаговой генерации и исполнения инструментов здесь нет.

Функция потерь — cross-entropy следующего токена с маской. Для батча \(\mathcal{B}\) токенизированных траекторий \(x\):

\[\mathcal{L}(\theta)=-\frac{1}{\sum_{x\in\mathcal{B}}\sum_{t} m_t}\;\sum_{x\in\mathcal{B}}\sum_{t=1}^{|x|} m_t\,\log p_{\theta}(x_t\mid x_{<t}),\qquad m_t\in\{0,1\}.\]

Маска \(m_t\) относится к токену \(t\) своей траектории и равна 1 для токенов ходов ассистента — текста вызова, финального ответа и токена конца хода, по которому модель учится останавливаться. Для системного сообщения с описаниями инструментов, вопроса пользователя, результатов инструментов и разметки этих ходов \(m_t=0\). Нормировка на общее число токенов с \(m_t=1\) в батче — один из распространённых вариантов среднего, его использует, например, библиотека TRL. При нём длинные траектории весят больше коротких.

Маска не исключает результаты инструментов из обучения. Токен с \(m_t=0\) не предсказывается, но остаётся в условии \(x_{<t'}\) для всех последующих позиций. Градиент проходит через attention к его представлениям и учит модель использовать результат в следующем вызове и ответе. Не обучается только предсказание самого результата. Именно это и нужно: при использовании эти токены пишет исполняющий код. Если бы потеря включала их, модель училась бы ещё и угадывать ответы инструментов, хотя предложенный вызов и полученное наблюдение должны оставаться разными событиями.

В нашей траектории из 792 токенов маска выбирает 88, около 11%; описания трёх инструментов занимают 352 токена. Подсчёт выполнен токенизатором Qwen3-4B-Instruct-2507 по тексту, собранному шаблоном; режим «Обучение» на иллюстрации выше показывает эту маску.

Toolformer: модель сама размечает вызовы

Чтобы научить модель вызывать инструменты, нужны тексты, где вызовы уже стоят в нужных местах вместе с результатами. Размечать их вручную дорого. Toolformer (Schick et al., 2023) получает такую разметку от самой модели. Она предлагает вызовы в обычном тексте, код их исполняет, а фильтр оставляет только те, после которых модели легче предсказать следующие слова. Затем модель дообучается на тексте с оставленными вызовами. В статье так дообучали GPT-J на части веб-корпуса CCNet с пятью инструментами: вопросно-ответной системой, калькулятором, поиском по Википедии, переводчиком и календарём.

Вызов записывается прямо в текст: открывающая скобка, вызов, стрелка ->, результат, закрывающая скобка. Это обычные токены словаря, так что менять модель не нужно. Запись вызова \(c\) с результатом \(r\) обозначим \(e(c,r)\), без результата — \(e(c,\varepsilon)\). Условный пример с нашим инструментом поиска инструкций вместо поиска по Википедии:

Ошибка ACCESS_CHECK_FAILED означает, что [search_instruction("ACCESS_CHECK_FAILED") -> ACCESS_CHECK_FAILED: проверка доступа не завершилась. Проверьте статус auth…] проверка доступа не завершилась.

Такой текст получается из исходного за шесть шагов. Каждый инструмент обрабатывается отдельно, со своим промптом.

  1. Где может начаться вызов. Модель получает промпт \(P(x)\): инструкцию «добавь в текст вызовы поиска, которые помогают его дописать», несколько примеров «вход — выход с вызовами» и затем исходный текст \(x=x_1,\dots,x_n\) как новый вход. Модель как бы переписывает \(x\) и перед любым токеном \(x_i\) может открыть скобку. Вероятность этого \(p_i=p_M(\text{«[»}\mid P(x),\,x_{1:i-1})\) для всех позиций сразу даёт один прямой проход. Остаются позиции с \(p_i\ge\tau_s\), не больше \(k\) лучших; в статье \(\tau_s=0{,}05\), \(k=5\).
  2. Какие вызовы предложить. В каждой оставшейся позиции модель продолжает префикс \(P(x),\,x_{1:i-1}\) с открытой скобкой до закрывающей и так сэмплирует до \(m=5\) кандидатов \(c_i\).
  3. Исполнить. Код выполняет каждый кандидат настоящим инструментом и получает результат \(r_i\).
  4. Отфильтровать. Вызов остаётся, если с его результатом модели заметно легче предсказать текст после позиции \(i\). Как это измеряется, разобрано ниже.
  5. Дообучить. Оставшиеся вызовы вставляются в текст в позицию \(i\), и вызовы всех инструментов объединяются в корпус \(C^*\). Кроме вставок он совпадает с исходным корпусом. Модель дообучается на нём обычной задачей языкового моделирования и учится открывать скобку там, где вызов помог ей самой, не теряя навыка продолжать обычный текст.
  6. Генерировать с вызовами. После дообучения генерация обычная, пока модель не напишет ->. Тогда декодирование приостанавливается, код исполняет вызов, вставляет результат и ], и модель продолжает текст. Это тот же разрыв между предложением вызова и исполнением, что в агентном цикле, только внутри одного текста. Авторы начинали вызов, если скобка входила в 10 самых вероятных токенов, и разрешали не больше одного вызова на вход.

Фильтр: помог ли результат

Пусть кандидат \(c_i\) стоит перед токеном \(x_i\). Потеря продолжения \(x_i,\dots,x_n\) при префиксе \(z\) — взвешенная cross-entropy по токенам после позиции вызова:

\[L_i(z)=-\sum_{j=i}^{n} w_{j-i}\,\log p_M(x_j\mid z,\,x_{1:j-1}).\]

Веса \(w_t\) пропорциональны \(\max(0,\,1-0{,}2\,t)\) и нормированы к сумме 1: \(w_0,\dots,w_4=\tfrac{5}{15},\tfrac{4}{15},\tfrac{3}{15},\tfrac{2}{15},\tfrac{1}{15}\), дальше нули. Значит, вызов должен помочь тексту сразу после себя, и сильнее всего — первому токену. Префикс \(z\) сравнивается в трёх вариантах: пустой (\(z=\varepsilon\), вызова нет), вызов без результата и вызов с результатом:

\[L_i^{+}=L_i\bigl(e(c_i,r_i)\bigr),\qquad L_i^{-}=\min\bigl(L_i(\varepsilon),\;L_i(e(c_i,\varepsilon))\bigr),\qquad \text{вызов остаётся, если } L_i^{-}-L_i^{+}\ge\tau_f.\]

Зачем в \(L_i^{-}\) вариант «вызов без результата», видно на трёх кандидатах для нашей фразы в позиции перед словом «проверка». Потери в натах условные; порог \(\tau_f=1\), как в статье для большинства инструментов.

Кандидат \(c_i\)\(L_i(\varepsilon)\)\(L_i(e(c_i,\varepsilon))\)\(L_i^{+}\)\(L_i^{-}-L_i^{+}\)Итог
A: search_instruction("ACCESS_CHECK_FAILED"), результат — инструкция access-172,041,940,381,56остаётся
B: search_instruction("вход в портал"), результат — инструкция о входе2,041,941,820,12отбрасывается
C: search_instruction("проверка доступа не завершилась"), результат — инструкция access-172,040,420,340,08отбрасывается

A проходит: запрос по коду ошибки сам продолжение почти не подсказывает, а результат делает его почти предсказуемым. B возвращает чужую инструкцию, и потеря почти не меняется. У C самая низкая потеря с результатом, но продолжение уже написано в запросе. Чтобы составить такой запрос, модель должна была знать текст и без инструмента, поэтому вызов без результата даёт почти ту же потерю. Если бы \(L_i^{-}\) учитывал только вариант без вызова, C прошёл бы с разностью \(2{,}04-0{,}34=1{,}70\).

При фильтрации запись вызова стоит префиксом перед всем текстом, а не в позиции \(i\): ещё не дообученная модель не встречала вызовов посреди текста, и сама вставка повысила бы потерю. Порог \(\tau_f\) задаёт компромисс между числом и надёжностью примеров. Для поиска по Википедии в статье при \(\tau_f=0{,}5\), \(1\) и \(2\) осталось 207 241, 60 974 и 13 944 примера с вызовами. Для калькулятора и переводчика авторы заранее отбирали подходящие тексты, например с несколькими числами, и снижали пороги.

Многошаговые траектории

Toolformer учит вставлять отдельный вызов в текст. Агенту нужны многошаговые траектории в формате чата, где каждое решение принимается после нового наблюдения. В ToolLLM (Qin et al., 2023) такие данные собрали на 16 464 настоящих REST API из каталога RapidAPI: ChatGPT составлял задания и искал цепочки вызовов, исполняя API, а LLaMA дообучили на найденных траекториях. В обоих подходах результаты инструментов в данных получены исполнением, а не придуманы моделью.

Описание инструмента: схема и текст

Модель выбирает инструмент и аргументы только по тексту контекста, поэтому описание — всё, что она знает о функции. Определение get_service_status в формате OpenAI-совместимого API; шаблон Qwen выводит его в промпт одной строкой:

{
  "type": "function",
  "function": {
    "name": "get_service_status",
    "description": "Читает страницу статуса одного сервиса: есть ли зарегистрированный инцидент. Используй, когда инструкция велит проверить сервис. Не проверяет права пользователя.",
    "parameters": {
      "type": "object",
      "properties": {
        "service": {"type": "string", "enum": ["auth", "portal", "sso"],
                    "description": "Имя сервиса из инструкции."}
      },
      "required": ["service"],
      "additionalProperties": false
    }
  }
}

Набор сервисов в enum условный. Части определения отвечают за разное:

ЧастьЧто задаётЧего не задаёт
nameКлюч, по которому код найдёт функцию в реестре. Модель тоже видит имя, поэтому имена должны различаться по смыслу.Назначение функции: check_status рядом с get_service_status только запутает выбор.
descriptionЧто делает функция, когда её вызывать, что она возвращает и чего не делает. Фраза «Не проверяет права пользователя» предупреждает недопустимый вывод из нормального статуса о правах.Гарантий: описание — текст, который модель может прочитать неверно или проигнорировать.
parameters (JSON Schema)Типы, обязательные поля, допустимые значения через enum, запрет лишних полей через additionalProperties.Порядок вызовов («сначала инструкция»), связь значения с контекстом («сервис из инструкции»), права доступа и существование объекта.

Схема для модели — тоже текст в промпте. Пока декодирование не ограничено, модель следует ей так же, как формату вызова: по навыку из обучения, без гарантии. enum превращает свободную строку в выбор из трёх значений, но не гарантирует, что выбрано значение из инструкции. Отсюда разделение обязанностей: форму аргументов можно проверить механически, уместность вызова — только косвенно, через описание и последующую оценку агента.

Описания передаются в каждом запросе. В нашем примере три инструмента занимают 352 из 554 токенов первого запроса. Повторный prefill этих токенов экономит prefix caching, если описания стоят в начале промпта и не меняются между шагами. Место в окне контекста они занимают в любом случае.

Когда инструментов много

С ростом набора растёт не только число токенов: модели труднее различать похожие инструменты. Рекомендации провайдеров — эвристики, а не проверенные пороги. OpenAI советует держать в начале хода меньше 20 функций. Anthropic предлагает объединять близкие операции в один инструмент и снабжать имена префиксом сервиса, например github_list_prs и slack_send_message.

Другой путь — поиск инструментов (tool retrieval): описания индексируются, и в контекст попадают \(k\) наиболее подходящих к задаче. Это та же задача поиска, что в RAG, со знакомым ограничением: если нужного инструмента нет в первых \(k\), модель не может его вызвать. Поэтому recall@\(k\) поиска инструментов ограничивает сверху качество всего агента. Такой поиск API использует ToolLLM; у Anthropic есть серверный инструмент поиска, а остальные описания помечаются defer_loading. Кеш префикса добавляет инженерное условие: найденные описания выгоднее дописывать в конец контекста, чем перестраивать системное сообщение.

От текста к допустимому вызову

Между сгенерированным текстом и исполнением стоит цепочка проверок: парсер формата, разбор JSON, поиск имени в реестре, проверка аргументов по схеме, проверки предметной области. Каждая ловит свой класс ошибок. Варианты ответа модели во втором решении нашего примера:

Ограниченное декодирование

При ограниченном декодировании (constrained decoding) сервер на каждом шаге обнуляет вероятности токенов, после которых текст нельзя продолжить до допустимого вызова, и перенормирует остальные. Пусть \(\mathcal{A}\) — множество допустимых последовательностей токенов вызова: по грамматике формата и JSON Schema аргументов. Через \(\operatorname{Pref}(\mathcal{A})\) обозначим множество их префиксов, \(V\) — словарь, \(C\) — контекст. Тогда очередной токен выбирается из распределения

\[\tilde p(y_t\mid y_{<t},C)=\frac{p_{\theta}(y_t\mid y_{<t},C)\,\mathbb{1}\bigl[(y_{<t},y_t)\in\operatorname{Pref}(\mathcal{A})\bigr]}{\sum_{v\in V}p_{\theta}(v\mid y_{<t},C)\,\mathbb{1}\bigl[(y_{<t},v)\in\operatorname{Pref}(\mathcal{A})\bigr]}.\]

Формула объясняет и гарантию, и её границы.

  • Каждый сгенерированный префикс можно дополнить до допустимого вызова, поэтому строки 2–4 таблицы невозможны. Знаменатель положителен: у префикса из \(\operatorname{Pref}(\mathcal{A})\) по определению есть допустимое продолжение, а softmax даёт каждому токену ненулевую вероятность. Последовательности из \(\mathcal{A}\) считаем завершёнными закрывающим токеном вызова.
  • О длине маска ничего не знает. Если лимит max_tokens наступил раньше конца вызова, префикс допустим, а вызов не закончен — первая строка остаётся.
  • Среди разрешённых токенов сохраняются относительные вероятности модели. Если модель предпочитает portal, маска не исправит выбор: пятая строка остаётся.
  • Произведение перенормированных вероятностей по шагам, вообще говоря, не равно распределению модели при условии допустимости всей строки \(p_{\theta}(y\mid C,\ y\in\mathcal{A})\). Маска узнаёт о тупике, только когда до него дошла, а вероятность, ведущая в тупики, перераспределяется локально (Park et al., 2024).

Как построить такую маску из регулярного выражения или грамматики через конечный автомат над словарём и не перебирать словарь на каждом шаге, показали Willard и Louf (2023). По документации vLLM (стабильная версия на 8 октября 2026) ограничение действует при именованном и обязательном выборе инструмента, а в режиме auto — для инструментов с strict: true. Без него вызов извлекается из сырого текста, и аргументы могут нарушать схему. Документация vLLM формулирует гарантию так: «validly-parsable function call - not a high-quality one». В OpenAI и Anthropic API строгий режим включается тем же полем strict: true и требует закрытых схем с additionalProperties: false.

Будет ли вызов: tool_choice

В формате Qwen решение «вызывать ли инструмент» сводится к первым токенам ответа. Параметр tool_choice управляет именно этой точкой:

ЗначениеЧто разрешено моделиЧто это меняет
autoВызов, несколько вызовов или текстовый ответМодель сама решает, нужен ли инструмент; значение по умолчанию при наличии tools
required (у Anthropic — any)Хотя бы один вызов, инструмент выбирает модельДействие гарантировано, уместность — нет: если правильный ход — ответить, модели всё равно придётся что-то вызвать
Именованная функцияТолько вызов указанной функцииВыбор действия переходит из модели в код; LLM заполняет аргументы. Это шаг workflow, а не агентное решение
noneТолько текстМодель отвечает так, будто инструментов нет

Обязательный и именованный выбор реализуют ограниченным декодированием, как vLLM, или дописыванием начала ответа. Anthropic описывает второй способ прямо: при any и tool начало ответа заполняется за модель, поэтому перед вызовом она не пишет пояснений. В нашем контракте завершение — обычный текстовый ответ, поэтому подходит только auto.

Ошибка вызова как наблюдение

В первом разделе исполнитель прерывал запуск исключением, если аргументы не прошли проверку. Это правильно для ошибки программы, но слишком строго для ошибки, которую модель может исправить сама. Пусть без ограниченного декодирования модель предложила get_service_status(service="Auth"). Код записывает вызов в журнал, инструмент не исполняет и возвращает наблюдение:

{"ok": false, "error": "invalid_arguments",
 "details": "service: 'Auth' is not one of ['auth', 'portal', 'sso']"}

Следующее решение принимается по контексту, где есть и вызов, и сообщение об ошибке, поэтому модель может повторить вызов с service="auth". Формула обновления \(H_{t+1}=H_t\mathbin{\Vert}[D_t,O_t]\) из первого раздела не меняется. Отличие в том, что наблюдение \(O_t\) выдала проверка, а не инструмент, и среда не затронута. Повтор стоит одного решения из бюджета, так что модель, которая раз за разом повторяет одну ошибку, остановится по step_limit.

Класс ошибкиПримерОбработка
Ошибка вызоваНеизвестное имя, service="Auth", нарушение правил предметной областиНаблюдение с указанием, что исправить; решение расходуется
Ошибка исполнения инструментаТайм-аут чтения страницы статусаНаблюдение "ok": false, как в первом разделе
Ответ не разобранОбрыв по max_tokens, нераспознанный тег вызова, пустой ответВызова с идентификатором нет, наблюдение не к чему привязать. Адаптер сообщает об ошибке, вызывающий код решает, повторить запрос или остановиться
Ошибка программыЖурнал неверного форматаИсключение

Сообщение об ошибке читает модель, поэтому оно должно указывать, что исправить: поле и допустимые значения, а не код ошибки или трассировку стека. Это же правило относится к проверкам, которых нет в схеме. Если бы инструмент принимал идентификатор пользователя, ответ «пользователь не найден» стал бы наблюдением, а не исключением.

Несколько вызовов в одном ответе

Формат допускает несколько <tool_call> подряд, и API возвращает их списком. Это экономит решения, когда вызовы независимы: например, прочитать статусы auth и sso одновременно. Исполнитель выполняет каждый вызов и возвращает каждый результат со своим идентификатором. В шаблоне Qwen идентификаторы в текст не попадают: результаты подряд идут в одном ходе user, и сопоставить их с вызовами модель может только по порядку. Значит, результаты нужно возвращать в порядке вызовов.

Зависимые вызовы так не объединить: статус auth имеет смысл читать только после того, как инструкция назвала сервис. Кроме того, бюджет в решениях перестаёт ограничивать число исполнений, и нужен отдельный предел на вызовы инструментов. Наш адаптер требует ровно один вызов в ответе и иначе сообщает об ошибке.

Адаптер к OpenAI-совместимому серверу

Ниже адаптер для цикла из первого раздела к серверу с OpenAI-совместимым API, например vLLM 0.31 с Qwen3-4B-Instruct-2507. Команда запуска сервера по документации vLLM и Qwen; в рамках конспекта модель не запускалась:

vllm serve Qwen/Qwen3-4B-Instruct-2507 --enable-auto-tool-choice --tool-call-parser hermes

Код использует пакеты openai и jsonschema. Классы Call, Finish и функции search_instruction, get_service_status берутся из первого раздела без изменений. Контракт меняется в трёх местах. Finish теперь означает только текстовый ответ без вызова, то есть completed. Исход blocked модель выбирает вызовом служебного инструмента ask_user: код проверяет его аргументы, но не исполняет, а завершает запуск. Ошибки вызова возвращаются наблюдениями.

import json
from copy import deepcopy

from jsonschema import Draft202012Validator
from openai import OpenAI

# Call, Finish, search_instruction, get_service_status — из первого раздела.


def tool(name, description, properties):
    return {"type": "function", "function": {
        "name": name,
        "description": description,
        "parameters": {"type": "object", "properties": properties,
                       "required": list(properties),
                       "additionalProperties": False},
    }}


TOOL_SCHEMAS = [
    tool("search_instruction",
         "Ищет инструкцию во внутренней базе по коду или тексту ошибки. "
         "Возвращает идентификатор и текст инструкции либо found=false. "
         "Не сообщает о состоянии сервисов.",
         {"query": {"type": "string", "minLength": 3,
                    "description": "Код или текст ошибки."}}),
    tool("get_service_status",
         "Читает страницу статуса одного сервиса: есть ли "
         "зарегистрированный инцидент. Используй, когда инструкция "
         "велит проверить сервис. Не проверяет права пользователя.",
         {"service": {"type": "string", "enum": ["auth", "portal", "sso"],
                      "description": "Имя сервиса из инструкции."}}),
    tool("ask_user",
         "Завершает запуск, когда для продолжения нужны сведения, "
         "которых нет у инструментов. Не выполняет действий.",
         {"message": {"type": "string",
                      "description": "Какие сведения нужны от пользователя."}}),
]
VALIDATORS = {spec["function"]["name"]:
              Draft202012Validator(spec["function"]["parameters"])
              for spec in TOOL_SCHEMAS}
RUNNERS = {"search_instruction": search_instruction,
           "get_service_status": get_service_status}

RULES = (
    "Ты помогаешь диагностировать ошибки доступа к корпоративному порталу. "
    "Опирайся только на результаты инструментов и не утверждай причину без данных. "
    "Вызывай не больше одного инструмента за ответ. "
    "Когда данных достаточно, ответь пользователю текстом без вызова инструмента. "
    "Если продолжить нельзя, вызови ask_user и перечисли недостающие сведения."
)

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY",
                timeout=60.0)
MODEL = "Qwen/Qwen3-4B-Instruct-2507"


class ModelOutputError(Exception):
    """Ответ модели нельзя превратить в Call или Finish."""


def to_messages(context):
    messages = [{"role": "system", "content": context["instructions"]}]
    for item in context["history"]:
        if item["kind"] == "user":
            messages.append({"role": "user", "content": item["text"]})
        elif item["kind"] == "call":
            arguments = json.dumps(item["args"], ensure_ascii=False)
            messages.append({"role": "assistant", "content": None,
                             "tool_calls": [{
                                 "id": item["id"], "type": "function",
                                 "function": {"name": item["name"],
                                              "arguments": arguments}}]})
        else:
            result = {key: value for key, value in item.items()
                      if key not in ("kind", "call_id")}
            messages.append({"role": "tool", "tool_call_id": item["call_id"],
                             "content": json.dumps(result, ensure_ascii=False)})
    return messages


def call_model(context) -> Call | Finish:
    response = client.chat.completions.create(
        model=MODEL,
        messages=to_messages(context),
        tools=context["tools"],
        tool_choice="auto",
        max_tokens=512,
    )
    choice = response.choices[0]
    if choice.finish_reason == "length":
        raise ModelOutputError("Ответ оборван по max_tokens")
    calls = choice.message.tool_calls or []
    text = choice.message.content or ""
    if not calls:
        if "<tool_call>" in text:  # формат Hermes: парсер не разобрал вызов
            raise ModelOutputError("Вызов остался в тексте ответа")
        if not text.strip():
            raise ModelOutputError("Пустой ответ без вызова")
        return Finish("completed", text)
    if len(calls) != 1:
        raise ModelOutputError(f"Ожидался один вызов, получено {len(calls)}")
    try:
        args = json.loads(calls[0].function.arguments)
    except json.JSONDecodeError as error:
        raise ModelOutputError("Аргументы вызова — не JSON") from error
    return Call(calls[0].function.name, args)

Адаптер не исполняет инструменты и не проверяет схему: он только переводит журнал в сообщения API и ответ API — в Call или Finish. Идентификатор вызова, присвоенный сервером, не используется: в журнал исполнитель пишет собственный call-N, и он же уходит в историю следующего запроса. Проверка <tool_call> в тексте относится к формату Hermes: при неудачном разборе парсер vLLM возвращает весь ответ как content.

Аргумент ensure_ascii=False влияет на стоимость. По умолчанию json.dumps экранирует кириллицу последовательностями вида п. Результат поиска инструкции занимает тогда 692 токена вместо 80 (токенизатор Qwen3-4B-Instruct-2507), а модель читает экранированный текст вместо обычного.

Исполняющий цикл меняется в одном месте: перед исполнением вызов проверяется, и ошибки становятся наблюдениями.

def check_call(decision):
    validator = VALIDATORS.get(decision.name)
    if validator is None:
        return {"ok": False, "error": "unknown_tool",
                "details": "Доступны: " + ", ".join(VALIDATORS)}
    problems = [
        f"{'.'.join(map(str, error.path)) or 'arguments'}: {error.message}"
        for error in validator.iter_errors(decision.args)
    ]
    if problems:
        return {"ok": False, "error": "invalid_arguments",
                "details": "; ".join(problems)}
    return None


def run_agent(question, model=call_model, max_steps=4):
    if type(max_steps) is not int or max_steps < 1:
        raise ValueError("max_steps должен быть положительным целым")
    history = [{"kind": "user", "text": question}]

    for step in range(max_steps):
        context = {"instructions": RULES, "tools": TOOL_SCHEMAS,
                   "history": history}
        decision = model(deepcopy(context))

        if isinstance(decision, Finish):
            if (decision.status != "completed"
                    or not isinstance(decision.message, str)
                    or not decision.message.strip()):
                raise ValueError("Ожидался Finish('completed', текст)")
            return {"status": "completed", "message": decision.message,
                    "steps": step + 1, "history": history}
        if not isinstance(decision, Call) or not isinstance(decision.name, str):
            raise ValueError("Ожидался Call или Finish")

        call_id = f"call-{step + 1}"
        history.append({"kind": "call", "id": call_id,
                        "name": decision.name, "args": deepcopy(decision.args)})
        observation = check_call(decision)
        if observation is None and decision.name == "ask_user":
            return {"status": "blocked", "message": decision.args["message"],
                    "steps": step + 1, "history": history}
        if observation is None:
            try:
                data = RUNNERS[decision.name](**decision.args)
                observation = {"ok": True, "data": data}
            except OSError as error:
                observation = {"ok": False, "error": type(error).__name__}
        history.append({"kind": "observation", "call_id": call_id,
                        **observation})

    return {
        "status": "step_limit",
        "message": "Диагностика не завершена: исчерпан предел решений.",
        "steps": max_steps,
        "history": history,
    }

Ошибки адаптера ModelOutputError цикл не перехватывает: к ним нельзя привязать наблюдение, и решение о повторе запроса принимает вызывающий код. Счётчик решений ограничивает и повторы после ошибок вызова, поэтому предел по умолчанию увеличен до четырёх.

Учебный прогон без модели

Подстановка возвращает заранее записанные решения, среди них одно с ошибкой в аргументе. Это проверка механики возврата ошибки, а не качества модели; сервер для прогона не нужен.

decisions = iter([
    Call("search_instruction", {"query": "ACCESS_CHECK_FAILED"}),
    Call("get_service_status", {"service": "Auth"}),
    Call("get_service_status", {"service": "auth"}),
    Finish("completed", "Инцидент auth может объяснять ошибку. "
           "Дождитесь восстановления и повторите вход; "
           "если ошибка сохранится, пришлите подробный текст и время."),
])

result = run_agent(
    "При входе в портал получаю ACCESS_CHECK_FAILED. Что делать?",
    model=lambda context: next(decisions),
)
print(result["status"], result["steps"])  # completed 4
print(result["history"][4]["details"])
# service: 'Auth' is not one of ['auth', 'portal', 'sso']

Вызов с "Auth" остаётся в журнале вместе с наблюдением об ошибке, следующий вызов исполняется. С max_steps=3 тот же прогон закончится step_limit после третьего решения: на финальный ответ решения не останется.

Если дообучать на своих траекториях

В TRL (версия 1.14) SFTTrainer принимает диалоги с tool_calls и сообщениями роли tool, а описания инструментов — в колонке tools. По умолчанию assistant_only_loss=False, и для диалогов в формате messages потеря считается по всей последовательности, включая описания и результаты инструментов. Маску из раздела выше включает assistant_only_loss=True. Ей нужны пометки {% generation %} в шаблоне чата; для известных семейств, например Qwen3, TRL подставляет такой шаблон сам. Обучающий шаблон должен давать те же токены, что и шаблон сервера: для нашей траектории версия TRL с пометками и исходный шаблон Qwen3-4B-Instruct-2507 дают одинаковый текст.
