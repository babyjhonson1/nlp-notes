Помощник ищет бумажного «Маленького принца» на русском: вместе с доставкой он должен стоить не больше 1500 рублей и приехать к 9 октября 2026 года. Поиск нашёл книгу за 950 рублей, но без стоимости доставки этого недостаточно для ответа. Модель должна запросить недостающие данные, а программа — выполнить запрос и вернуть результат в следующий ход. Разберём этот обмен на уровне функций и сообщений, затем ограничим набор инструментов, видимый модели. Практический пример на LangGraph покажет один такой ход; все магазины и данные условные, дата сценария — 8 октября 2026 года.

От функции к описанию инструмента

Предположим, что программист уже написал search_books(title) и get_offer_details(offer_id). Первая функция находит предложения по названию и возвращает их идентификаторы — например, "A" для магазина «Лист». Вторая принимает такой идентификатор и возвращает цену книги, стоимость и дату доставки. Именно вторая операция нужна после поиска: сама LLM текущих условий магазина не знает.

Чтобы модель могла выбрать функцию, ей передают описание инструмента (tool definition): имя, назначение и схему аргументов. Схема — правила устройства входного объекта. Для get_offer_details это объект с обязательным строковым полем offer_id. В сокращённом виде описание выглядит так:

{
  "name": "get_offer_details",
  "description": "Прочитать цену книги, стоимость и дату доставки. Ничего не покупает.",
  "parameters": {
    "type": "object",
    "properties": {
      "offer_id": {
        "type": "string",
        "description": "Идентификатор из результата search_books"
      }
    },
    "required": ["offer_id"],
    "additionalProperties": false
  }
}

Тело Python-функции модели не требуется. Ей нужно понять, когда выбрать операцию и что передать. Поэтому «получить данные» — слабое описание: оно не отличает поиск книги от чтения условий конкретного предложения. Фраза «идентификатор из результата search_books» объясняет зависимость между операциями. Она помогает выбрать аргумент, но не доказывает, что модель действительно взяла его из результата поиска.

В LangChain декоратор @tool создаёт объект инструмента из функции: сохраняет исполняемый код и извлекает описание из строки документации, а схему — из аннотаций типов или явно заданной модели Pydantic. LangGraph использует эти же объекты в узле исполнения ToolNode. Модели и исполнителю передают разные стороны одного объекта: описание и вызываемую функцию. Это разделение видно в документации инструментов.

Где здесь API и REST

Программный интерфейс (application programming interface, API) — договор о доступных операциях, входах и результатах. У нашей Python-функции уже есть такой интерфейс; интернет для него необязателен. Если данные лежат у магазина, внутри функции можно отправить запрос его серверу и преобразовать ответ в словарь. HTTP — протокол обмена запросами и ответами в вебе. REST (representational state transfer) — архитектурный стиль таких систем с обращением к ресурсам через единый интерфейс; это не другое название любой функции или любого HTTP-запроса. Для агентного цикла достаточно знать контракт get_offer_details: за ним может стоять локальный словарь, база данных или веб-сервис. См. определение API и исходное описание REST.

Что проходит между моделью и исполнителем

Список инструментов обычно передают отдельным параметром запроса, а не дописывают вручную в сообщение пользователя. Это удобство интерфейса: модель всё равно должна получить их описания во входной последовательности. У открытых моделей способ записи задаёт шаблон чата (chat template): он превращает сообщения и описания в токены. Конкретная разметка зависит от модели; например, вызов может записываться JSON внутри тегов <tool_call>. Парсер или адаптер затем превращает сгенерированную запись в структурированный вызов. Это устройство показано в документации Transformers.

На уровне LangChain программный обмен выглядит следующим образом. Здесь model обозначает уже настроенную чат-модель с поддержкой инструментов; фрагмент показывает интерфейс, а исполняемый пример без ключа приведён ниже.

bound_model = model.bind_tools([get_offer_details])
reply = bound_model.invoke(messages)
print(reply.tool_calls)
# [{'name': 'get_offer_details', 'args': {'offer_id': 'A'},
#   'id': 'call_1', 'type': 'tool_call'}]

bind_tools подготавливает передачу описаний при запросе. Этот метод не обучает модель и не запускает функции. reply — сообщение ассистента AIMessage; поле tool_calls содержит предложенные вызовы. Только следующий шаг исполняющего кода обращается к get_offer_details. После исполнения история должна содержать и запрос действия, и связанный с ним результат:

СообщениеКто его создаётСодержание в нашем примере
AIMessageАдаптер из ответа моделиВызов get_offer_details(offer_id="A") с идентификатором call_1.
ToolMessageИсполняющий кодtool_call_id="call_1"; цена 950, доставка 350, прибытие 2026-10-09.
Следующее AIMessageАдаптер после нового обращения к моделиОтвет о полной цене 1300 рублей либо другой вызов, если данных ещё недостаточно.

Идентификатор связывает наблюдение с конкретным вызовом. Одного имени функции недостаточно: помощник может запросить условия сразу для A и B. В историю добавляют всё сообщение ассистента с вызовами и по одному результату на каждый из них; только затем выполняют следующий запрос к модели. Результат ошибки тоже занимает своё место в этой паре. Такой обмен описан в документации чат-моделей LangChain.

Здесь есть два разных вида «нескольких вызовов». Поиск книги и чтение условий требуют двух ходов: идентификатор предложения появляется только после поиска. А условия уже найденных A и B можно запросить в одном ходе, двумя независимыми вызовами. ToolNode умеет исполнять такой пакет параллельно. Порядок записей в tool_calls не следует использовать как способ передать результат первой функции во вторую: такой зависимости нужен новый ход или явный последовательный код.

Что проверяет код

Предложение модели ещё не является допустимым вызовом. У исполнителя есть реестр — словарь «имя → объект инструмента». По нему выбирается функция; затем её схема проверяет аргументы, а тело функции проверяет условия, которые зависят от данных. Для неизвестного offer_id="Z" тип str совершенно корректен, но предложения Z в каталоге нет.

ОшибкаКакая проверка нужнаЧто делать дальше
Аргументы оборваны или не разбираются как JSONРазбор ответа в адаптере; проверка признака обрыва генерацииНе исполнять фрагмент и не считать его готовым ответом. Повтор или остановку выбирает вызывающий код.
Имени нет среди разрешённых на этом ходеПоиск в реестре выбранного набораВернуть ошибку вызова. Нельзя искать одноимённую произвольную Python-функцию и запускать её.

В LangGraph результат такой проверки можно вернуть как ToolMessage со статусом error. Следующая генерация увидит, например, «неизвестный идентификатор, возьми его из поиска». Это даёт модели возможность исправиться, но не гарантирует исправления; предел шагов из первого раздела по-прежнему нужен. Ошибки программы вроде случайного KeyError лучше оставлять исключениями: превращать любую поломку кода в совет модели «попробуй ещё» затрудняет диагностику.

Показать описание и разрешить исполнение — две отдельные операции. Если модель видела один инструмент, а исполнитель принимает весь реестр, она всё ещё может предложить скрытое имя из прежней истории или угадать его. В нашем примере исполнитель получает тот же выбранный набор, что и модель.

Дополнение: что гарантирует ограниченное декодирование

Часть ошибок можно предотвратить ещё во время генерации. При ограниченном декодировании (constrained decoding) запрещают токены, после которых текст уже нельзя дополнить до допустимого вызова. Пусть \(\mathcal A\) — множество разрешённых последовательностей, включая токен завершения, \(\operatorname{Pref}(\mathcal A)\) — их префиксы, \(V\) — словарь, \(C\) — вход модели. На незавершённом префиксе распределение имеет вид

\[\tilde p(y_t\mid y_{<t},C)=\frac{p_{\theta}(y_t\mid y_{<t},C)\,\mathbb{1}\bigl[(y_{<t},y_t)\in\operatorname{Pref}(\mathcal A)\bigr]}{\sum_{v\in V}p_{\theta}(v\mid y_{<t},C)\,\mathbb{1}\bigl[(y_{<t},v)\in\operatorname{Pref}(\mathcal A)\bigr]}.\]

При существовании допустимого продолжения и положительных исходных вероятностях знаменатель ненулевой. Маска убирает запрещённые варианты и сохраняет относительные вероятности остальных. Поэтому её возможности зависят от того, какие ограничения включены в \(\mathcal A\):

Что ограничилиЧто исключается у завершённого вызоваЧто остаётся возможным
Только синтаксис JSONНеразбираемый JSONНеизвестное имя, неправильные поля и значения.
Имена и поддерживаемые ограничения схем аргументовНеизвестное имя, отсутствие обязательного поля, нарушение поддержанного типа или enum"Z", если схема разрешает любую строку; допустимый, но неуместный вызов.
Любой из этих вариантовНедопустимое продолжениеОбрыв по лимиту длины до закрывающего токена: префикс допустим, целого вызова ещё нет.

Такая пошаговая перенормировка в общем случае не равна исходному распределению, условному на допустимости всей строки, \(p_\theta(y\mid C,\,y\in\mathcal A)\): масса перераспределяется локально без учёта вероятности всех допустимых будущих продолжений. Это различие разбирают Park et al. (2024). Включение строгого режима и поддерживаемые части схемы зависят от сервера; bind_tools само по себе такой гарантии не даёт. Валидация перед исполнением остаётся самостоятельной границей.

Как выбирать из большого каталога

Для двух функций разумно передать обе. Проблема возникает, когда в реестре сотни операций: поиск книг, доставка, возвраты, состояние заказа, личный кабинет. Если передавать полные описания всех операций в каждом запросе, они занимают контекст и затрудняют различение похожих функций. Хранить функцию в программе дёшево; помещать её описание в каждый вход LLM — отдельная стоимость.

Обозначим полный реестр через \(\mathcal T\), выбранный на ходе набор через \(S_t\subseteq\mathcal T\), а актуальное описание недостающих данных — через \(q_t\). Выбор \(S_t\) происходит до генерации вызова. Поэтому у системы появляются два решения: какие операции показать и какую из показанных операций вызвать. У них могут быть разные исполнители.

Сначала — набор по этапу

Если приложение знает, что сейчас происходит, хватит обычного условия в коде. На этапе search виден search_books; после появления предложений на этапе compare — get_offer_details. Это уменьшает число описаний без дополнительной LLM. Именно такой отбор реализован ниже.

Цена простоты — жёсткая граница сценария. Если после сравнения пользователь спрашивает об условиях возврата, а этап compare разрешает только чтение цены и доставки, модель не получит нужной операции. Код должен переключить этап или расширить набор. Такой фильтр подходит для хорошо определённого процесса; для произвольных запросов удобнее искать описания.

Поиск описаний инструментов

В поиске инструментов (tool retrieval) документом служит карточка функции: имя, назначение, условия применения и аргументы. Например, «стоимость и дата доставки конкретного предложения» должна находить get_offer_details. Поиск можно построить теми же методами, что разобраны в лексическом и векторном поиске; детали ретривера здесь не меняют агентный цикл. В варианте с фиксированным числом кандидатов

\[S_t=\operatorname{TopK}_{u\in\mathcal T}\;s\bigl(q_t,d(u)\bigr),\]

где \(d(u)\) — индексируемое описание инструмента, \(s\) — оценка релевантности. В запрос к LLM загружают полные схемы найденных функций: одного имени из поисковой выдачи недостаточно, чтобы надёжно составить аргументы. В ToolLLM авторы отдельно обучали ретривер описаний API и подавали найденные операции модели, решающей задачу; это конкретная реализация общего разделения поиска и вызова.

Число кандидатов ограничивает количество карточек, но не их суммарную длину. При большом разбросе размеров нужен ещё бюджет токенов: на этапе сборки входа должно выполняться

\[\operatorname{tokens}\bigl(\operatorname{render}(H_t,S_t)\bigr)+B_{\text{output}}\le W,\]

где \(H_t\) содержит инструкции и сообщения, \(\operatorname{render}\) применяет формат конкретной модели, \(B_{\text{output}}\) — резерв генерации, \(W\) — окно контекста. Считать нужно весь собранный вход, включая схемы. Кеширование повторяющегося префикса может удешевить его обработку, но не освобождает место в окне.

Запрос поиска должен отражать текущий пробел, а не каждый раз повторять «найди Маленького принца». После получения предложений нужен запрос «доставка и полная цена предложения». Его может составить код из этапа задачи или модель отдельным решением. Если другая LLM выбирает функции, читая весь каталог, нагрузка на основной запрос уменьшается, но стоимость чтения каталога переносится в вызов селектора.

Что делать, если нужная функция не попала в выдачу

Допустим, поиск по слову «доставка» вернул get_order_status, который проверяет уже оформленный заказ и требует order_id. У нас заказа ещё нет. Придумывать этот аргумент бессмысленно: нужная операция относится к предложению, а не к заказу. Должен существовать путь обратно к поиску.

Один вариант — всегда оставлять модели служебный инструмент find_tools(query). Он возвращает подходящие карточки, а код добавляет соответствующие схемы в набор следующего хода. Тогда модель может уточнить запрос до «стоимость доставки предложения до покупки». Если этот поиск тоже ничего не дал, можно увеличить число кандидатов в пределах бюджета, выбрать другую категорию или завершить с указанием недостающей возможности. Количество таких попыток ограничивают общим бюджетом шагов. Это устройство контроллера, а не автоматическое свойство LangGraph.

Отсюда две разные причины неуспеха: нужное действие не было доступно после отбора или модель неверно распорядилась доступным набором. При диагностике нужно сохранять выбранные имена, запрос селектора и предложенный вызов. Увеличение набора может исправить первую проблему, но не обязано исправлять вторую.

Где в этой схеме MCP

Протокол контекста модели (Model Context Protocol, MCP) задаёт, как приложение подключается к внешнему поставщику инструментов. В спецификации инструментов запрос tools/list получает их описания, а tools/call вызывает конкретную операцию. Если магазин предоставляет MCP-сервер, клиентская обёртка может стать ещё одной функцией нашего реестра. Обнаруженный каталог всё равно нужно отобрать для текущего входа LLM: подключение MCP само по себе эту задачу не решает.

Почему модель умеет выбирать инструменты

Эта способность приобретается при обучении модели, а не при регистрации Python-функции. В демонстрациях после описаний и вопроса записаны вызовы, результаты и ответы; модель учится предсказывать следующие действия по доступным наблюдениям. Разные инструменты обучают общие параметры, поэтому отдельная LLM на каждую функцию не нужна. bind_tools лишь передаёт контракты уже обученной модели.

Как получают обучающие вызовы и учат несколько последовательных действий, разобрано в следующем разделе: от Toolformer до многошаговых траекторий и маски потерь. Запись токенов и режим обучения в шаблоне Qwen показаны в разборе функции потерь.

Практика: один ход на LangGraph

Соберём исполняемый компонент select → model → tools. Состояние — словарь, узел — функция, которая читает его и возвращает изменённые поля, ребро задаёт следующий узел. Здесь один запуск графа обрабатывает один ответ модели: если в нём есть вызовы, исполняет их и возвращает наблюдения; иначе возвращает текстовый ответ. Полный агент повторяет такие ходы и управляет остановкой, как в первом разделе. Эта граница позволяет отдельно проверить инструменты, не пряча их внутри готового агента.

Блоки ниже составляют одну Python-программу и выполняются сверху вниз. Нужны langgraph и langchain-core из окружения первого практикума; пример проверен на версиях 1.2.14 и 1.6.9 соответственно. Локальные функции работают с фиксированными данными, а ответы модели в конце подставляются явно. Ключ, сеть и веса для такого запуска не нужны.

Функции, схемы и реестр

У поиска схема выводится из сигнатуры. Для чтения условий зададим её явно через OfferArgs, чтобы запретить лишние поля и приведение типов. Поле offer_id описывает вход; данные OFFERS остаются в программе. Исключение ToolException обозначает ожидаемую ошибку, которую можно вернуть модели.

import json
from typing import Annotated, Literal, TypedDict

from pydantic import BaseModel, ConfigDict, Field
from langchain_core.messages import AIMessage, AnyMessage, HumanMessage
from langchain_core.tools import tool, ToolException
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode


# Условные данные на 2026-10-08. Все суммы в рублях.
OFFERS = {
    "A": {"shop": "Лист", "book_price": 950, "delivery": 350,
          "arrival": "2026-10-09", "language": "ru", "format": "paper"},
    "B": {"shop": "Полка", "book_price": 900, "delivery": 650,
          "arrival": "2026-10-09", "language": "ru", "format": "paper"},
}


@tool
def search_books(title: str) -> list[dict]:
    """Найти предложения по названию. Возвращает offer_id и цену без доставки."""
    if title.casefold().strip() != "маленький принц":
        return []
    return [{"offer_id": key, "title": "Маленький принц",
             **{k: v for k, v in row.items() if k not in ("delivery", "arrival")}}
            for key, row in OFFERS.items()]


class OfferArgs(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    offer_id: str = Field(description="Идентификатор из результата search_books")


@tool(args_schema=OfferArgs)
def get_offer_details(offer_id: str) -> dict:
    """Прочитать цену книги, стоимость и дату доставки. Ничего не покупает."""
    if offer_id not in OFFERS:
        raise ToolException("Неизвестный offer_id; возьми его из search_books.")
    return {"offer_id": offer_id, **OFFERS[offer_id]}


REGISTRY = {t.name: t for t in (search_books, get_offer_details)}
TOOLS_BY_STAGE = {
    "search": ("search_books",),
    "compare": ("get_offer_details",),
}

Сейчас две функции; структура реестра останется такой же при добавлении новых. TOOLS_BY_STAGE реализует отбор кодом. Для поиска по каталогу меняется способ получения имён в узле select; остальные границы — передача описаний и исполнение выбранного набора — сохраняются.

Отбор, решение и исполнение как разные узлы

Поле available сохраняет, что показали модели на этом ходе. add_messages задаёт правило обновления истории: новые сообщения дописываются, а сообщение с уже существующим ID заменяется. Поэтому узлы возвращают только новые сообщения. Остальные поля здесь просто перезаписываются.

class TurnState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    stage: Literal["search", "compare"]
    available: list[str]
    status: str


def build_tool_turn(model):
    def select(state):
        return {"available": list(TOOLS_BY_STAGE[state["stage"]])}

    def decide(state):
        selected = [REGISTRY[name] for name in state["available"]]
        reply = model.bind_tools(selected).invoke(state["messages"])
        if reply.invalid_tool_calls:
            raise ValueError("Адаптер не разобрал аргументы вызова")
        if not reply.tool_calls and not reply.content:
            raise ValueError("Пустой ответ модели")
        return {"messages": [reply],
                "status": "pending" if reply.tool_calls else "answered"}

    def execute(state):
        # Разрешаем ровно тот набор, который показали модели на этом ходе.
        selected = [REGISTRY[name] for name in state["available"]]
        executor = ToolNode(selected, handle_tool_errors=ToolException)
        update = executor.invoke({"messages": state["messages"]})
        return {"messages": update["messages"], "status": "observed"}

    graph = StateGraph(TurnState)
    graph.add_node("select", select)
    graph.add_node("model", decide)
    graph.add_node("tools", execute)
    graph.add_edge(START, "select")
    graph.add_edge("select", "model")
    graph.add_conditional_edges(
        "model", lambda s: "tools" if s["messages"][-1].tool_calls else END,
        {"tools": "tools", END: END},
    )
    graph.add_edge("tools", END)
    return graph.compile()

В select нет модели: этап задаёт вызывающая программа. В model нет исполнения: bind_tools передаёт выбранные описания. В tools нет нового решения LLM: ToolNode читает вызовы из последнего сообщения, находит функции, проверяет входы и создаёт результаты с соответствующими идентификаторами. В указанной версии ошибка валидации аргументов внутри узла является разновидностью ToolException; выбранный обработчик превращает её и наши предметные ошибки в сообщения, сохраняя прочие исключения для диагностики.

observed означает только «результаты добавлены», включая возможные ошибки. Этот статус не означает успешного подбора книги. Ветка answered также фиксирует форму ответа модели, а не доказательство его правильности. Проверка ограничений пользователя остаётся задачей всего агента.

Прогон с заранее записанными решениями

ReplayModel — явная заглушка, а не упрощённая LLM: она возвращает следующий подготовленный ответ и сохраняет имена показанных инструментов. Два запуска графа изображают поиск, затем чтение условий обоих предложений. Переход этапа search → compare в этом прогоне задан вручную.

class ReplayModel:
    """Заглушка: возвращает записанные ответы, не запускает LLM."""
    def __init__(self, replies):
        self.replies = iter(replies)
        self.seen_tools = []

    def bind_tools(self, tools):
        self.seen_tools.append([t.name for t in tools])
        return self

    def invoke(self, messages):
        return next(self.replies)


scripted = ReplayModel([
    AIMessage(content="", tool_calls=[
        {"name": "search_books", "args": {"title": "Маленький принц"}, "id": "s1"}
    ]),
    AIMessage(content="", tool_calls=[
        {"name": "get_offer_details", "args": {"offer_id": "A"}, "id": "d1"},
        {"name": "get_offer_details", "args": {"offer_id": "B"}, "id": "d2"},
    ]),
])
turn = build_tool_turn(scripted)
first = turn.invoke({
    "messages": [HumanMessage(content=(
        "Найди бумажного Маленького принца на русском. "
        "До 1500 рублей с доставкой к 2026-10-09."))],
    "stage": "search",
})
second = turn.invoke({"messages": first["messages"], "stage": "compare"})
print(scripted.seen_tools)
for message in second["messages"][-2:]:
    data = json.loads(message.content)
    print(message.tool_call_id, data["offer_id"],
          data["book_price"] + data["delivery"], data["arrival"])

Вывод:

[['search_books'], ['get_offer_details']]
d1 A 1300 2026-10-09
d2 B 1550 2026-10-09

На первом ходе LLM получила бы только описание поиска. На втором — только описание чтения условий, но предложила бы два его вызова с разными аргументами. Исполнитель вернул оба наблюдения. Теперь есть основания отбросить B по полной цене, хотя сама книга там дешевле; A укладывается и в бюджет, и в срок. Следующий ход полного агента может составить ответ по этим данным. Прогон проверяет передачу сообщений и работу функций; он ничего не измеряет в качестве выбора настоящей модели.

Для подключения LLM вместо ReplayModel нужен адаптер чат-модели с методами bind_tools и invoke, возвращающий AIMessage. Саму модель и сервер нужно выбирать с поддержкой вызовов инструментов; LangGraph не добавляет этой способности. В первой тетради ты самостоятельно собираешь полный цикл, а подключение через Hugging Face вынесено в отдельный необязательный этап.
