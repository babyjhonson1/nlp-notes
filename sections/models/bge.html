BGE (BAAI General Embedding) — семейство моделей, которые обучают не писать ответ, а представлять тексты для поиска. В исходном рецепте сначала учат вектор текста сохранять информацию о нём, затем — отличать связанные тексты от посторонних, наконец — решать конкретные задачи с размеченными примерами. BGE-M3 продолжает эту идею: один кодировщик даёт три разных способа оценить пару «запрос — документ», и их совместное мнение используется при обучении каждого выхода. Чтобы понять рецепт, пройдём этапы в порядке обучения: на каждом выясним, что подаётся на вход, что считается правильным ответом и через какую ошибку обновляется модель.

Что должен уметь итоговый кодировщик

Начнём с BGE v1 — моделей с одним вектором на текст. Запрос и документ независимо проходят через один и тот же BERT-подобный кодировщик с параметрами \(\theta\). Из матрицы выходных состояний \(H_\theta(x)\) берут выход первого токена [CLS] и нормируют:

\[e_\theta(x)=\frac{H_\theta(x)[0]}{\lVert H_\theta(x)[0]\rVert_2},\qquad s_\theta(q,p)=e_\theta(q)^\top e_\theta(p).\]

Это и есть оценка пары (score): скалярное произведение единичных векторов, то есть косинус. Отдельной сети, которая получает пару и выдаёт оценку, здесь нет. Для запроса «забыл пароль, почта не открывается» нам нужен высокий косинус с инструкцией по восстановлению без почты, а не просто с любым документом о паролях.

Само устройство BERT этого не гарантирует. При обычном MLM скрытое слово восстанавливают по его токенному состоянию; задачу можно решать, не собирая достаточное представление всего текста в [CLS]. Поэтому рецепт BGE начинает с отдельного задания именно для этого вектора. Ниже разбирается исходный рецепт C-Pack; изменения v1.5 и BGE-M3 отмечены отдельно.

Этап 1. RetroMAE: восстановление текста через один вектор

Для чего нужен декодер

На время предобучения к кодировщику добавляют маленький декодер — один трансформерный слой и предсказание токенов словаря. Его задача — восстановить исходный текст, пользуясь вектором [CLS] и неполным контекстом. Это вспомогательная обучающая сеть: после предобучения её отбрасывают, для поиска остаётся кодировщик. Декодер не получает все выходные состояния кодировщика, как в обычном encoder–decoder: от него приходит только один вектор.

Данные на этом этапе — обычные тексты, не пары «запрос — ответ». Для китайского BGE в C-Pack использован Wudao. Покажем условный русский пример; для наглядности каждое слово считается одним токеном, реальный токенизатор может разбить его иначе.

ЧтоПример
Исходный текст \(x\)Без почты доступ восстанавливают через поддержку
Вход кодировщика \(\tilde x_{\mathrm{enc}}\)Без почты [MASK] восстанавливают [MASK] поддержку
Вход декодера \(\tilde x_{\mathrm{dec}}\), базовый вариантБез [MASK] доступ [MASK] через [MASK]
Цели декодера в скрытых позицияхпозиция \(2\): «почты»; \(4\): «восстанавливают»; \(6\): «поддержку»

Маски двух входов выбираются независимо. Кодировщику оставляют больше текста, чтобы он мог построить содержательный вектор \(h=H_\theta(\tilde x_{\mathrm{enc}})[0]\); декодеру — меньше, чтобы одного локального контекста часто было недостаточно. В RetroMAE скрывают около \(15\)–\(30\%\) токенов у кодировщика и \(50\)–\(70\%\) у декодера.

Что именно предсказывается — и почему это не генерация слева направо

Декодер получает последовательность из \(h\) и эмбеддингов замаскированного текста с позициями. Один проход даёт для каждой восстанавливаемой позиции распределение по всему словарю. В позиции \(2\) правильный класс — токен «почты», а не следующий за ним «доступ». Видимый контекст может находиться и слева, и справа. Предсказание для позиции \(2\) не подставляется во вход перед вычислением позиции \(4\): они вычисляются параллельно.

Обозначим распределение в позиции \(i\) через \(P_{\theta,\phi}(v\mid h,\tilde x_{\mathrm{dec}},i)\), где \(\phi\) — параметры декодера, \(v\) — токен словаря, а \(D\) — множество скрытых у декодера позиций. Тогда:

\[\mathcal L_{\mathrm{dec}}=-\sum_{i\in D}\log P_{\theta,\phi}(x_i\mid h,\tilde x_{\mathrm{dec}},i),\qquad \mathcal L_{\mathrm{RetroMAE}}=\mathcal L_{\mathrm{MLM,enc}}+\mathcal L_{\mathrm{dec}}.\]

Цель \(x_i\) берут из чистого текста, до маскирования. Ошибка декодера проходит назад через \(h\) в кодировщик; его параметры учатся делать этот вектор полезным для восстановления. Одновременно обучается сам декодер и сохраняется MLM-задача кодировщика. Слабый декодер и неполный контекст создают стимул использовать \(h\), но не гарантируют, что вектор без потерь запомнит каждое слово.

Улучшенное декодирование: своя маска внимания для каждой позиции

В базовом варианте выше сигнал дают только скрытые позиции, причём все они видят один и тот же контекст. В улучшенном декодировании (enhanced decoding) из статьи RetroMAE, §3.3 восстанавливают каждую позицию по своей случайной части остальных токенов. Здесь у декодера уже не одна строка с [MASK], а маска доступности в механизме внимания.

Запрос внимания для позиции \(i\) строится из \(h\) и её позиционного эмбеддинга, без самого \(x_i\). Ключи и значения берутся из \(h\) и входных эмбеддингов чистого текста. Маска разрешает видеть \(h\) и выбранное подмножество \(V_i\) других позиций, но запрещает прямой доступ к \(x_i\). Это не запрет кодировщику учитывать \(x_i\): если он не скрыт на входе кодировщика, информация о нём может прийти через \(h\), что и требуется.

Например, для восстановления «почты» декодеру можно открыть «Без», «через», «поддержку»; для восстановления «поддержку» — «Без», «доступ», «восстанавливают». Все такие строки внимания обрабатываются одновременно. Потери теперь суммируются по всем текстовым позициям:

\[\mathcal L_{\mathrm{dec}}^{\mathrm{enh}}=-\sum_{i=1}^{n}\log P_{\theta,\phi}(x_i\mid h,\{x_j:j\in V_i\},i),\qquad i\notin V_i.\]

Итог этапа — кодировщик, чей [CLS] обучали помогать восстановлению текста. Но «сохранить информацию о своём тексте» и «приблизить запрос к правильному документу» — разные задачи. Вторую задачу ставит следующий этап.

Этапы 2 и 3. От связанных текстов к поисковым задачам

Слабые пары: какая оценка входит в InfoNCE

Теперь декодер не нужен. На вход подаются два целых текста, без масок RetroMAE. Связь между ними извлекают из структуры источника: например, заголовок и соответствующий текст считаются положительной парой. В китайском C-MTP такие пары отфильтровали готовой моделью Text2Vec-Chinese; детали состава и масштаба не меняют механизм обучения.

Источник и связьУсловный обучающий примерОткуда негатив
C-MTP: заголовок и текст страницы (например, Baike); связанные фрагменты одного источника\(q\): «Восстановление доступа без почты»
\(p^+\): «Если почта недоступна, подтвердите личность через форму поддержки.»		Тексты других положительных пар в том же батче, например статья о тарифах.

Пусть батч содержит \(B\) пар \((q_i,p_i^+)\). Для каждого запроса считаются косинусы его нормированного [CLS] со всеми документами батча. Матрица оценок имеет размер \(B\times B\), а правильный документ запроса \(q_i\) стоит в столбце \(i\):

\[s_{ij}=e_\theta(q_i)^\top e_\theta(p_j^+),\qquad P_i(j)=\frac{\exp(s_{ij}/\tau)}{\sum_{k=1}^{B}\exp(s_{ik}/\tau)},\qquad \mathcal L_i=-\log P_i(i).\]

Это InfoNCE в обозначениях BGE. Сначала получаем косинус \(s\), затем делим его на температуру \(\tau\), затем применяем softmax по документам, не по токенам словаря. Ошибка двигает параметры общего кодировщика через обе стороны пары; цель — увеличить вероятность правильного столбца. В среднем по батчу минимизируют \(\frac1B\sum_i\mathcal L_i\).

Размеченные задачи: тот же косинус, другие примеры

На третьем этапе используют размеченные пары, в частности поисковые наборы T2Ranking и DuReader, и добавляют к каждому запросу трудный негатив из поиска по корпусу. Документы других запросов батча также остаются негативами. Теперь нужно различать не только разные темы, но и похожие инструкции, одна из которых не решает задачу пользователя.

Часть примераУсловный текст для поисковой задачиРоль
Запрос«Найди подходящую инструкцию: забыл пароль, почта не открывается»Инструкция задачи и исходный запрос кодируются вместе.
Позитив \(p^+\)«Если почта недоступна, подтвердите личность через форму поддержки.»Релевантный документ по разметке.
Трудный негатив \(p^-\)«Сменить пароль можно по ссылке из письма на вашу почту.»Найден по сходству, но требует доступной почты.

Инструкция сообщает задачу, но не превращает кодировщик в генератор ответа. Если обозначить соединение инструкции \(I_t\) и запроса через \(I_t\oplus q\), то:

\[s_t(q,p)=e_\theta(I_t\oplus q)^\top e_\theta(p),\qquad \mathcal L_q=-\log\frac{\exp(s_t(q,p^+)/\tau)}{\sum_{p\in C_q}\exp(s_t(q,p)/\tau)}.\]

В \(C_q\) входят позитив и используемые негативы. Функция сходства по-прежнему косинус; изменились вход запроса и состав кандидатов. Для английских поисковых моделей инструкция — Represent this sentence for searching relevant passages: ; русский текст выше лишь иллюстрирует формат.

Небольшой условный расчёт: косинусы для позитива, трудного негатива и статьи о тарифах равны \(0.72,\ 0.68,\ 0.12\). При демонстрационной \(\tau=0.1\) softmax даёт \(0.598,\ 0.401,\ 0.0015\), а потери — около \(0.515\). Ошибка ещё заметна: модель почти путает две инструкции. Это не восстановление слов и не регрессия к заранее заданному косинусу — обучение выбору правильного документа среди конкурентов.

Так устроена последовательность исходного рецепта C-Pack. Английские данные и последующие v1.5 не следует приравнивать к китайскому эксперименту во всех деталях: полный рецепт английских v1.5 не опубликован. В model card авторы сообщают об изменённом распределении сходств и меньшей зависимости v1.5 от инструкции; это не другой тип функции сходства.

BGE-M3: от плотного поиска к трём оценкам

Сначала — снова один плотный вектор

BGE-M3 — отдельная ветвь семейства на основе XLM-RoBERTa-large, а не ещё один размер английской BGE. Кодировщик адаптируют к длинному входу через RetroMAE, затем контрастивно обучают только плотный выход по тому же принципу, что выше. Данные становятся многоязычными: кроме пар из структуры страниц, используются предложения и их переводы.

ИсточникУсловная пара / группаЗачем она нужна на этом этапе
Википедия, S2ORC, новости; заголовок — текст«Почему почта нужна для сброса пароля» ↔ «Ссылка из письма позволяет подтвердить владение аккаунтом…»Контрастное обучение плотного выхода на связанных текстах.
NLLB, CCMatrix; оригинал — перевод«Обратитесь в поддержку» ↔ “Contact support”Связать языки в общем пространстве плотных векторов.

Затем — ещё два способа оценить те же документы

Один вектор удобен для быстрого поиска, но не сохраняет все детали текста. Поэтому на этапе размеченного дообучения к плотному выходу добавляют лексический и многовекторный. Все три выхода обучают по одним группам «запрос — позитив — негативы»:

ИсточникУсловный примерОткуда цель
MS MARCO, MIRACL и другие размеченные задачиЗапрос: «Как восстановить доступ без почты?»
Позитив: инструкция обращения в поддержку.
Негатив: смена пароля по письму.		Релевантный документ отмечен в датасете; трудные негативы подбирают поиском.
MultiLongDocТот же вопрос ↔ длинная инструкция целиком, нужное условие в середине; негативы — другие документы.Вопрос сгенерирован по абзацу; позитивом назначен весь исходный документ.

Последняя строка учит искать ответ в длинном документе, а не только в его начале: само увеличение числа позиций этого не обеспечивает. Теперь разберём, как три выхода оценивают кандидата. Все они используют одну матрицу \(H_\theta(x)\):

\[s_{\mathrm{dense}}(q,p)=e_\theta(q)^\top e_\theta(p).\]

Плотный выход уже знаком: нормированный первый токен. У XLM-R это <s>, который играет роль [CLS].

\[w_{x,t}=\max_{i:x_i=t}\operatorname{ReLU}(W_{\mathrm{lex}}^\top H_\theta(x)[i]+b_{\mathrm{lex}}),\qquad s_{\mathrm{lex}}(q,p)=\sum_{t\in q\cap p}w_{q,t}w_{p,t}.\]

Лексическая голова учит контекстный вес токена. Совпадают именно идентификаторы токенов, не обязательно целые слова; повторы объединяются максимумом, служебные токены исключаются. \(W_{\mathrm{lex}}\) — обучаемая проекция в одно число; в реализации есть и смещение \(b_{\mathrm{lex}}\). Это поиск по совпадениям, но веса не вычисляются формулой BM25.

\[E_x[i]=\operatorname{norm}(W_{\mathrm{mul}}^\top H_\theta(x)[i]+b_{\mathrm{mul}}),\qquad s_{\mathrm{mul}}(q,p)=\frac1{N_q}\sum_{i=1}^{N_q}\max_j E_q[i]^\top E_p[j].\]

Многовекторная голова обучает проекцию токенных состояний. Для каждого токена запроса берётся лучшее совпадение с токеном документа; затем максимумы усредняются. Это вариант MaxSim: первый токен исключён, паддинг замаскирован, запрос не дополняется [MASK]. \(N_q\) — число участвующих в оценке токенов запроса. В опубликованной реализации проекция со смещением сохраняет размерность \(1024\), а не уменьшает её до \(128\), как у ColBERT.

Важно, что в обучающем наборе нет отдельных «правильных весов слов» или «правильных векторов токенов». Есть правильный документ. Каждая из трёх оценок должна помогать выбрать его, поэтому градиент от ошибки ранжирования обучает и головы, и общий кодировщик.

Самодистилляция: кто учитель и чему учатся выходы

Сначала научить выходы выбирать позитив по разметке

Возьмём один запрос и общий список кандидатов \(C_q=(p^+,p^-_1,\ldots)\). В обучении M3 используют трудные негативы и, в зависимости от режима, документы других запросов батча. Каждый выход даёт по этому списку свою строку оценок. Чтобы не путать косинусы с входами softmax, введём логиты:

\[z_{m,j}=\frac{s_m(q,p_j)}{\tau},\qquad P_m(j)=\operatorname{softmax}(z_m)_j,\qquad m\in\{\mathrm{dense},\mathrm{lex},\mathrm{mul}\}.\]

Все softmax ниже вычисляются по одному и тому же списку документов. В проверенной реализации FlagEmbedding три оценки делятся на общую температуру до объединения; её значение в исходном обучении статья не уточняет. Также считают интегральную строку:

\[z_{\mathrm{ens}}=z_{\mathrm{dense}}+0.3z_{\mathrm{lex}}+z_{\mathrm{mul}},\qquad P_{\mathrm{ens}}=\operatorname{softmax}(z_{\mathrm{ens}}).\]

Сначала три выхода и их смесь учатся по обычной метке позитива: \(\mathcal L_m=-\log P_m(+)\), в том числе для \(m=\mathrm{ens}\). Взвешенная ошибка этого этапа:

\[\mathcal L_{\mathrm{sup}}=\frac{\mathcal L_{\mathrm{dense}}+0.1\mathcal L_{\mathrm{lex}}+\mathcal L_{\mathrm{mul}}+\mathcal L_{\mathrm{ens}}}{4}.\]

Именно здесь появляется исходный сигнал о том, что правильно: в разметке, а не в мнении случайной сети. В M3 перед включением самодистилляции выходы разогревают совместным обучением. Малый вес лексического выхода ограничивает влияние его первоначально случайной головы.

Потом использовать смесь как мягкую цель

Разметка требует выбрать один позитив, но не выражает степень близости остальных кандидатов. Дополнительная идея: если разные выходы видят разные признаки, их смесь может дать отдельному выходу полезный сигнал. Это гипотеза о качестве ансамбля, не гарантия, что он всегда прав.

На текущем прямом проходе сохраняют распределение смеси как цель \(T\), отключив у этой копии градиент:

\[T=\operatorname{stopgrad}(P_{\mathrm{ens}}),\qquad \mathcal L^{\mathrm{KD}}_m=-\sum_{j\in C_q}T_j\log P_m(j).\]

Каждый выход сравнивает собственное распределение с одним и тем же \(T\). Это дистилляция оценок, только внешнего cross-encoder-учителя здесь нет: цель получена от текущей модели. Для фиксированного \(T\) мягкая кросс-энтропия и KL имеют одинаковый градиент по ученику.

Условный пример с тем же запросом о недоступной почте. В таблице логиты, уже поделённые на температуру, а не сырые косинусы. Никакая модель для этих чисел не запускалась.

Кандидат\(z_{\mathrm{dense}}\)\(z_{\mathrm{lex}}\)\(z_{\mathrm{mul}}\)\(z_{\mathrm{ens}}\)
\(p_1\): восстановление через поддержку, позитив\(2\)\(1\)\(2\)\(4.3\)
\(p_2\): смена пароля по письму, трудный негатив\(1\)\(1.5\)\(0.5\)\(1.95\)
\(p_3\): тарифы, негатив\(0\)\(0\)\(0\)\(0\)

Лексический выход ошибочно предпочитает вторую инструкцию: \(P_{\mathrm{lex}}\approx(0.331,0.547,0.122)\). Смесь предпочитает правильную: \(T\approx(0.902,0.086,0.012)\). Ошибка дистилляции требует не скопировать чужие векторы, а изменить собственные оценки так, чтобы распределения сблизились.

Направление изменения видно из градиента по логиту лексического выхода, до общего взвешивания потерь:

\[\frac{\partial\mathcal L^{\mathrm{KD}}_{\mathrm{lex}}}{\partial z_{\mathrm{lex},j}}=P_{\mathrm{lex}}(j)-T_j\approx(-0.570,\ 0.461,\ 0.110)_j.\]

Градиентный спуск вычитает эту величину: позитиву нужно повысить логит, двум негативам — понизить. В настоящей сети оптимизатор меняет не таблицу оценок напрямую, а \(W_{\mathrm{lex}}\), смещение и общий кодировщик через правило цепочки. Плотный и многовекторный выходы аналогично получают свои ошибки.

Что обновляется после шага

Мягкая цель дополняет разметку, не заменяет её. Полные потери объединяют обе части:

\[\mathcal L_{\mathrm{KD}}=\frac{\mathcal L^{\mathrm{KD}}_{\mathrm{dense}}+0.1\mathcal L^{\mathrm{KD}}_{\mathrm{lex}}+\mathcal L^{\mathrm{KD}}_{\mathrm{mul}}}{3},\qquad \mathcal L_{\mathrm{final}}=\frac{\mathcal L_{\mathrm{sup}}+\mathcal L_{\mathrm{KD}}}{2}.\]

Здесь записаны потери для одного запроса; в обучении их усредняют по батчу. Веса смеси логитов \((1,0.3,1)\) и веса ошибок выходов \((1,0.1,1)\) решают разные задачи: первые задают мнение учителя, вторые — вклад выходов в обновление параметров.

Последовательность одного шага: кодировать тексты → вычислить три строки логитов → составить смесь и её отсоединённую копию \(T\) → посчитать обе ошибки → обновить параметры. На следующем шаге \(T\) вычисляется заново уже из изменившейся сети.

detach не замораживает модель-учителя навсегда. Он запрещает градиент через целевое распределение в текущем шаге. Через выходы-ученики и через \(\mathcal L_{\mathrm{ens}}\) градиент продолжает идти в общий кодировщик и головы. Отдельного плотного «обучаемого слоя» нет: плотный выход — нормированный [CLS].

Формулы и порядок этапов описаны в статье M3, §3.3; размещение температуры и отключение градиента сверены с реализацией FlagEmbedding. Выигрыш — экспериментальный: в абляции статьи лексический поиск на MIRACL получает \(36.7\) без самодистилляции и \(53.9\) с ней (nDCG@\(10\)). Для конкретного нового корпуса улучшение всё равно нужно проверять.

Что важно при использовании

Инструкция только у запроса

У bge-*-en-v1.5 инструкция Represent this sentence for searching relevant passages: нужна коротким запросам при поиске документов. К документам и к текстам в симметричных задачах вроде поиска дубликатов её не приписывают. В конфигурации sentence-transformers у этих моделей промптов нет, поэтому библиотека сама инструкцию не добавит: её передают при загрузке или кодировании. Для v1.5 авторы пишут, что без инструкции поиск лишь немного хуже, и советуют выбирать вариант по качеству на своих данных. BGE-M3, по model card, инструкций у запроса не требует.

Вектор — [CLS], а не среднее

Способ пулинга хранится в конфигурации чекпойнта (pooling_mode_cls_token: true), и sentence-transformers применяет его сам. При ручном кодировании через transformers берут выход первого токена и нормируют. Нельзя автоматически переносить сюда усреднение токенов из многих моделей E5 и SBERT: у BGE это вектор, на котором модель не обучалась, а сообщения об ошибке не будет.

Уровень косинусов

Для BGE v1 авторы отмечают сжатое распределение сходств — примерно \(0.6\)–\(1\): высокий косинус сам по себе не доказывает релевантность. v1.5 смягчает эту проблему. Сравнивают порядок кандидатов, а порог, если нужен, подбирают на своих размеченных данных.

Длина входа

У английских v1.5 предел 512 токенов. У BGE-M3 8192, и sentence-transformers берёт этот предел из конфигурации. В FlagEmbedding у BGEM3FlagModel пределы длины запроса и документа по умолчанию — 512 токенов (проверено по исходному коду): если не передать max_length, длинный документ молча обрежется. Стоимость кодирования растёт с длиной, а внимание — квадратично, поэтому длину ограничивают по реальной нужде.

Какой выход BGE-M3 загружен

Веса лексической и многовекторной голов лежат в отдельных файлах sparse_linear.pt и colbert_linear.pt. Конфигурация sentence-transformers описывает только плотный выход ([CLS] и нормировка), поэтому SentenceTransformer("BAAI/bge-m3") даёт плотные векторы и ничего больше. Попытка получить векторы токенов через MultiVectorEncoder("BAAI/bge-m3") хуже: библиотека считает чекпойнт обычной моделью эмбеддингов, предупреждает лишь о конвертации и добавляет случайно инициализированную проекцию до 128 измерений вместо обученной \(W_{\text{mul}}\) (проверено по исходному коду sentence-transformers 6.1.0). Все три выхода с обученными головами отдаёт FlagEmbedding.

Шкалы трёх оценок разные

В примере из model card для запроса «What is BGE M3?» и описания BGE-M3 плотная оценка равна \(0.626\), лексическая — \(0.196\), многовекторная — \(0.780\). Лексическая оценка — сумма произведений весов, её уровень зависит от числа совпавших токенов. Поэтому веса смеси подбирают на своих данных; веса обучающего ансамбля не обязаны быть лучшими при поиске. В схеме выше использованы \((0.4,\,0.2,\,0.4)\) из примера model card. Метод compute_score в FlagEmbedding делит взвешенную сумму на сумму весов.

Когда какой выход

Плотный выход — простой исходный вариант; лексический добавляет точные совпадения; многовекторный позволяет сопоставить отдельные части запроса и документа. Это не иерархия «каждый следующий всегда лучше». Например, в статье на MIRACL плотный поиск лучше лексического, а на длинных документах MLDR — наоборот. Правдоподобное объяснение второго результата: один вектор теряет детали длинного текста, а совпадения терминов сохраняются; сама таблица результатов не доказывает причину.

У лексического выхода есть ограничение: совпадают токены SentencePiece, не леммы. «почта» и «почту» разбиваются как ▁почта и ▁поч, ту (проверено токенизатором BGE-M3), поэтому прямого совпадения между этими словами нет.

Размер многовекторного индекса

Векторы токенов BGE-M3 имеют размерность \(1024\), у ColBERT до сжатия — \(128\). При одинаковом числе токенов и формате чисел хранение самих несжатых векторов требует в \(8\) раз больше памяти; эту пропорцию нельзя переносить на полный сжатый индекс ColBERT. В экспериментах M3 многовекторную оценку применяют для переранжирования кандидатов, а не перебора всего корпуса.

Язык и лицензия

bge-*-en-v1.5 — английские модели со словарём BERT и приведением к нижнему регистру; из разобранных здесь вариантов для русского подходит BGE-M3. Лицензия весов bge-*-en-v1.5 и BGE-M3 в model card — MIT.

BGE на практике

bge-base-en-v1.5 в sentence-transformers

Инструкция передаётся как промпт запроса; документы кодируются без неё. Пулинг [CLS] и нормировка уже записаны в конфигурации модели. Код сверен с исходным кодом sentence-transformers 6.1.0, модель не запускалась.

from sentence_transformers import SentenceTransformer

model = SentenceTransformer(
    "BAAI/bge-base-en-v1.5",
    prompts={"query": "Represent this sentence for searching relevant passages: "},
)
q = model.encode_query(["how much protein should a female eat"])   # с инструкцией
d = model.encode_document([                                         # без инструкции
    "Women need about 46 grams of protein a day.",
    "Men need about 56 grams of protein per day.",
])
scores = model.similarity(q, d)                                     # косинус

BGE-M3: три выхода в FlagEmbedding

Пример на фрагментах базы поддержки из раздела о dense retrieval. Параметры методов сверены с исходным кодом FlagEmbedding и примерами model card; модель не запускалась, поэтому значений в комментариях нет.

from FlagEmbedding import BGEM3FlagModel

model = BGEM3FlagModel("BAAI/bge-m3", use_fp16=True)
docs = [
    "Восстановление доступа. Если вы не помните пароль, а привязанный электронный ящик недоступен, подтвердите личность через форму поддержки.",
    "Смена пароля. Чтобы сменить пароль, откройте настройки профиля и перейдите по ссылке из письма, которое придёт на вашу почту.",
]
kw = dict(max_length=8192, return_dense=True, return_sparse=True, return_colbert_vecs=True)   # иначе предел 512
d = model.encode(docs, **kw)
q = model.encode(["забыл пароль, почта не открывается"], **kw)

dense = q["dense_vecs"] @ d["dense_vecs"].T                                    # косинусы векторов [CLS]
lex = [model.compute_lexical_matching_score(q["lexical_weights"][0], w) for w in d["lexical_weights"]]
mul = [model.colbert_score(q["colbert_vecs"][0], v) for v in d["colbert_vecs"]]  # MaxSim / N
print(model.convert_id_to_token(q["lexical_weights"][0]))                       # веса токенов запроса

Лексические веса возвращаются словарём «идентификатор токена — вес» только для токенов с положительным весом. Для поиска по корпусу их кладут в разреженный инвертированный индекс (в статье — Lucene), плотные векторы — в ANN-индекс, а многовекторную оценку считают для объединения кандидатов.
