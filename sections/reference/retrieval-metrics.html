Метрика поиска сводит ранжированный список к числу, но разные числа отвечают на разные вопросы. Recall@\(k\) проверяет, не потерял ли retriever релевантные объекты; MRR смотрит только на первый успех; MAP учитывает порядок нескольких релевантных результатов; nDCG поддерживает несколько степеней релевантности. Поэтому метрику выбирают по пользовательскому сценарию и стадии RAG-конвейера, а не по тому, какое число выглядит привычнее.

Постановка и обозначения

Пусть \(Q\) — множество тестовых запросов, а система для запроса \(q\) возвращает упорядоченный список \(d_{q,1},\ldots,d_{q,k}\). Оценка релевантности результата на позиции \(i\) обозначается \(\operatorname{rel}_{q}(i)\). Для бинарной разметки она равна нулю или единице; для градуированной разметки может принимать, например, значения от нуля до трёх.

Таблица соответствий между запросами и релевантными объектами называется qrels (query relevance judgments). До расчёта метрик нужно зафиксировать, что считается объектом: документ, passage, чанк или конкретный ответ. Метрика по чанкам и метрика по документам различаются, даже если получены одним retriever.

Offline-метрика корректна только относительно qrels. Неразмеченный документ не обязательно нерелевантен: при неполной разметке его часто лишь не оценивали.

Precision@\(k\) и recall@\(k\)

Точность на срезе (precision at \(k\)) — доля релевантных результатов среди первых \(k\). Полнота на срезе (recall at \(k\)) — доля всех известных релевантных объектов, попавших в первые \(k\):

\[ \operatorname{Precision@}k(q) = \frac{1}{k}\sum_{i=1}^{k}\mathbb{1}\!\left[\operatorname{rel}_{q}(i) > 0\right], \qquad \operatorname{Recall@}k(q) = \frac{1}{R_q}\sum_{i=1}^{k}\mathbb{1}\!\left[\operatorname{rel}_{q}(i) > 0\right], \]

где \(R_q\) — общее число известных релевантных объектов для запроса. Precision@\(k\) штрафует нерелевантные элементы в выдаче, а recall@\(k\) — пропущенные релевантные элементы. Если в RAG retriever сначала отдаёт широкий пул реранкеру, обычно важнее высокий recall: нерелевантного кандидата ещё можно отбросить, а потерянный документ восстановить уже нечем.

При \(R_q=0\) recall не определён. Такие запросы либо исключают из агрегата, либо заранее задают явную конвенцию. Молча подставлять ноль опасно: доля запросов без размеченных релевантных объектов начнёт влиять на сравнение систем.

MRR

Среднее обратное место (mean reciprocal rank, MRR) оценивает, насколько высоко расположен первый релевантный результат. Пусть \(r_q\) — его ранг. Reciprocal rank одного запроса и среднее по запросам равны

\[ \operatorname{RR}(q) = \begin{cases} \dfrac{1}{r_q}, & \text{если релевантный результат найден},\\ 0, & \text{иначе}, \end{cases} \qquad \operatorname{MRR} = \frac{1}{|Q|}\sum_{q\in Q}\operatorname{RR}(q). \]

Если первые релевантные результаты четырёх запросов находятся на позициях \(1\), \(2\), \(5\) и отсутствуют, то

\[ \operatorname{MRR} = \frac{1+\frac{1}{2}+\frac{1}{5}+0}{4} = 0.425. \]

MRR хорошо соответствует сценарию «найти один правильный ответ как можно выше»: FAQ, entity lookup или retrieval единственного фрагмента-доказательства. После первого релевантного результата метрика полностью игнорирует хвост списка. Поэтому она не различит выдачи с одним и десятью полезными документами, если первый полезный документ стоит на одинаковой позиции.

AP и MAP

Средняя точность (average precision, AP) учитывает позиции всех бинарно релевантных результатов. Для каждого релевантного элемента берётся precision на его позиции, после чего значения усредняются:

\[ \operatorname{AP@}k(q) = \frac{1}{R_q} \sum_{i=1}^{k} \operatorname{Precision@}i(q)\, \mathbb{1}\!\left[\operatorname{rel}_{q}(i) > 0\right], \qquad \operatorname{MAP@}k = \frac{1}{|Q|} \sum_{q\in Q}\operatorname{AP@}k(q). \]

В знаменателе AP обычно стоит полное число релевантных объектов \(R_q\), поэтому документы, не попавшие в первые \(k\), снижают результат. Некоторые библиотеки используют другую конвенцию для AP@\(k\), например \(\min(R_q,k)\); сравнивать числа между инструментами можно только после проверки определения.

MAP чувствителен ко всему порядку релевантных документов, но предполагает бинарную релевантность. Он подходит, когда полезных объектов несколько и каждый из них одинаково важен. Для оценок вроде «идеально подходит», «частично подходит» и «не подходит» естественнее nDCG.

DCG и nDCG

Дисконтированная накопленная полезность (discounted cumulative gain, DCG) суммирует gain результатов, уменьшая вклад нижних позиций логарифмическим дисконтом. Одна из наиболее распространённых форм:

\[ \operatorname{DCG@}k(q) = \sum_{i=1}^{k} \frac{2^{\operatorname{rel}_{q}(i)}-1}{\log_2(i+1)}. \]

Экспоненциальный gain делает переход от оценки \(2\) к \(3\) важнее перехода от \(0\) к \(1\), а логарифм штрафует поздние результаты. Существует и линейный вариант с числителем \(\operatorname{rel}_{q}(i)\); при публикации результата формулу нужно указывать явно.

Значение DCG нельзя напрямую сравнивать между запросами с разным числом и уровнем релевантных объектов. Поэтому строят идеальное ранжирование всех известных объектов запроса, сортируя их оценки по убыванию, вычисляют \(\operatorname{IDCG@}k(q)\) и нормируют:

\[ \operatorname{nDCG@}k(q) = \begin{cases} \dfrac{\operatorname{DCG@}k(q)} {\operatorname{IDCG@}k(q)}, & \operatorname{IDCG@}k(q) > 0,\\ 0, & \operatorname{IDCG@}k(q)=0. \end{cases} \]

При такой конвенции nDCG лежит между нулём и единицей, а идеальная перестановка получает единицу. Запросы без положительного gain некоторые реализации исключают, а некоторые оценивают нулём — это ещё одна настройка, которую нужно фиксировать рядом с числом.

Один список — все метрики

Посчитаем метрики для одного запроса, чтобы увидеть, какие решения скрыты в определениях. Разметка градуированная: для запроса известны четыре объекта с положительными оценками \(3\), \(2\), \(1\) и \(1\). Система вернула пять результатов, и один из релевантных объектов с оценкой \(1\) в выдачу не попал. Зафиксируем конвенции: cutoff \(k=5\); для бинарных метрик релевантным считается объект с оценкой больше нуля, поэтому \(R_q=4\); gain для DCG экспоненциальный.

Позиция \(i\)\(\operatorname{rel}_{q}(i)\)Бинарно\(\operatorname{Precision@}i\)Вклад в DCG
\(1\)\(0\)\(0\)\(0\)\(0\)
\(2\)\(3\)\(1\)\(1/2\)\(7/\log_2 3\approx4.417\)
\(3\)\(1\)\(1\)\(2/3\)\(1/\log_2 4=0.5\)
\(4\)\(0\)\(0\)\(1/2\)\(0\)
\(5\)\(2\)\(1\)\(3/5\)\(3/\log_2 6\approx1.161\)

Простые метрики: \(\operatorname{Precision@}5=3/5=0.6\), \(\operatorname{Recall@}5=3/4=0.75\), а первый релевантный результат стоит на второй позиции, поэтому \(\operatorname{RR}=1/2\). Для MRR это вклад одного запроса; AP и nDCG ниже тоже считаются для одного запроса, а MAP и средний nDCG получаются усреднением по \(Q\).

AP усредняет precision на позициях релевантных результатов и делит на все известные релевантные объекты, включая ненайденный:

\[ \operatorname{AP@}5=\frac{1}{4}\left(\frac{1}{2}+\frac{2}{3}+\frac{3}{5}\right)\approx0.442. \]

Здесь \(R_q=4\le k\), поэтому конвенция \(\min(R_q,k)\) даёт то же число. При cutoff \(k=3\) они расходятся: \((1/2+2/3)/4\approx0.292\) против \((1/2+2/3)/3\approx0.389\). Оценки \(3\) и \(1\) для AP одинаковы: после бинаризации метрика их не различает.

nDCG использует градации. DCG выдачи — сумма последнего столбца, \(\operatorname{DCG@}5\approx6.077\). Идеальный порядок строится по всем известным оценкам запроса, \(3, 2, 1, 1\), а не только по найденным:

\[ \operatorname{IDCG@}5=\frac{7}{\log_2 2}+\frac{3}{\log_2 3}+\frac{1}{\log_2 4}+\frac{1}{\log_2 5}\approx9.823, \qquad \operatorname{nDCG@}5\approx\frac{6.077}{9.823}\approx0.619. \]

Если по ошибке построить идеальный порядок только из найденных оценок \(3, 2, 1\), получится \(0.647\): пропущенный релевантный объект перестанет штрафовать систему. Вся разница между метриками здесь — в знаменателях и бинаризации, поэтому их фиксируют вместе с числом.

Как выбирать метрику

ВопросМетрикаЧто она не видит
Сколько полезного в первых \(k\)?Precision@\(k\)релевантные объекты ниже cutoff
Попал ли нужный материал в пул кандидатов?Recall@\(k\)порядок внутри первых \(k\)
Как высоко первый правильный результат?MRRвсе результаты после первого релевантного
Хорошо ли упорядочены несколько бинарно релевантных объектов?MAPстепени релевантности
Стоят ли наиболее полезные объекты выше остальных?nDCGабсолютную полноту при неполных qrels

Для двухступенчатого retrieval обычно нужны как минимум две оценки: recall@\(k_{\text{retrieve}}\) до реранкера и MRR либо nDCG@\(k_{\text{context}}\) после него. Первая проверяет наличие доказательства в кандидатах, вторая — его положение в коротком списке, который реально попадёт в контекст.

Одна агрегированная метрика скрывает причину ошибки. Сохраняйте результаты по запросам и отдельно анализируйте срезы: тип источника, язык, длину запроса, необходимость фильтрации, число релевантных документов и временную актуальность.

Покрытие необходимых доказательств

Полнота по документам не отвечает на вопрос, достаточно ли сведений для полного ответа. Пусть \(E_q\) — непустое множество обязательных элементов доказательства, а \(h(e,C)\) равно единице, если набор фрагментов \(C\) достаточно подтверждает элемент \(e\), и нулю иначе. Определим покрытие доказательств (evidence coverage) и индикатор полной достаточности:

\[\operatorname{EC}(q,C)=\frac{1}{|E_q|}\sum_{e\in E_q}h(e,C),\qquad \operatorname{Complete}(q,C)=\mathbb{1}[\operatorname{EC}(q,C)=1].\]

Это явная конвенция оценки по размеченным потребностям, а не универсальная библиотечная метрика. Элемент может подтверждаться одним из нескольких эквивалентных диапазонов или совокупностью источников. Для вопроса «порядок восстановления и срок» два повторяющих процедуру фрагмента покрывают один элемент из двух: EC равна \(1/2\), Complete — нулю. Добавление фрагмента со сроком даёт единицу обоим показателям. Так не приходится считать все дубли обязательными релевантными документами.

Для каждого элемента сохраняют проверяемые диапазоны и условия версии. Переход от пула к упакованному контексту оценивают той же разметкой. При пустом \(E_q\) обе оценки здесь не определены: вопрос без ответа не должен автоматически получать полное покрытие. Отсутствие разметки также не доказывает отсутствие ответа в корпусе.

MMR: критерий отбора контекста

Максимальная маргинальная релевантность (Maximal Marginal Relevance, MMR) — алгоритм выбора набора, а не метрика его качества по эталону. Для кандидатов \(C\), выбранных \(S\), релевантности \(r_i\) и попарного сходства \(s_{ij}\) следующий элемент выбирается по правилу:

\[i^\star=\operatorname*{arg\,max}_{i\in C\setminus S}\left[\lambda r_i-(1-\lambda)\max_{j\in S}s_{ij}\right],\qquad 0\le\lambda\le1.\]

Для пустого \(S\) в наших примерах первым выбирается максимум релевантности. Далее штраф определяется максимальным сходством со всем выбранным набором. Масштабы релевантности и сходства согласуют; при \(\lambda=1\) остаётся сортировка по релевантности, при \(\lambda=0\) после первого выбора — только разнообразие. Увеличение значения критерия не гарантирует рост покрытия доказательств. Пошаговый расчёт и код сохранены в разделе RAG; MMR не следует путать с MRR, средним обратным местом.

Метрики на практике

Минимальную реализацию полезно уметь написать без фреймворка: так проще проверить конвенции библиотеки и воспроизвести отдельный запрос.

import math

def reciprocal_rank(binary_relevance):
    for rank, relevant in enumerate(binary_relevance, start=1):
        if relevant:
            return 1.0 / rank
    return 0.0

def average_precision(binary_relevance, num_relevant, k):
    hits, total = 0, 0.0
    for rank, relevant in enumerate(binary_relevance[:k], start=1):
        if relevant:
            hits += 1
            total += hits / rank             # Precision@rank на позиции релевантного
    return total / num_relevant if num_relevant else 0.0

def dcg(grades, k):
    return sum(
        (2**grade - 1) / math.log2(rank + 1)
        for rank, grade in enumerate(grades[:k], start=1)
    )

def ndcg(retrieved_grades, all_judged_grades, k):
    actual = dcg(retrieved_grades, k)
    ideal = dcg(sorted(all_judged_grades, reverse=True), k)
    return actual / ideal if ideal > 0 else 0.0

grades = [0, 3, 1, 0, 2]                  # выдача из примера выше
binary = [g > 0 for g in grades]
print(reciprocal_rank(binary))                          # 0.5
print(round(average_precision(binary, 4, k=5), 3))      # 0.442
print(round(ndcg(grades, [3, 2, 1, 1], k=5), 3))        # 0.619

Перед сравнением систем зафиксируйте cutoff, правило дедупликации, тип объекта, шкалу релевантности и обработку запросов без положительных оценок. Усредняйте метрики по запросам, а не по отдельным документам; вместе со средним полезно приводить доверительный интервал, полученный bootstrap-перевыборкой запросов.

В RAG дополнительно разделяйте document-level и chunk-level оценку. Несколько почти одинаковых релевантных чанков одного документа могут заполнить top-\(k\), и chunk precision останется высокой: каждый из них по отдельности релевантен. Страдают разнообразие и покрытие разных доказательств: другие релевантные документы и фрагменты вытесняются за срез. Это видно по document recall или по доле покрытых доказательств, а не по precision; precision падает, только если повторяющиеся чанки нерелевантны. И наоборот, document recall не гарантирует, что retriever выбрал именно тот фрагмент, в котором находится доказательство.

Ключевые статьи

  • Voorhees. The TREC-8 Question Answering Track Report, 1999 — использование reciprocal rank и MRR для ранжированных ответов на вопросы.
  • Järvelin, Kekäläinen. Cumulated Gain-Based Evaluation of IR Techniques, 2002 — DCG и нормированная оценка ранжирования с градуированной релевантностью.
  • Manning, Raghavan, Schütze. Introduction to Information Retrieval, 2008 — систематическое изложение precision, recall, MAP и оценки ранжированного поиска.
  • Goldstein, Carbonell. Summarization: (1) Using MMR for Diversity-Based Reranking and (2) Evaluating Summaries, 1998 — критерий отбора релевантного и неповторяющегося материала; не метрика качества по qrels.
