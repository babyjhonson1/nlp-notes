Лексический поиск (lexical retrieval) ранжирует документы по совпадениям токенов запроса с токенами документа. Он не пытается вывести смысл текста: его сила в другом — редкое точное совпадение получает большой вес, а поиск выполняется по компактному инвертированному индексу без прохода по всему корпусу. TF–IDF задаёт базовую схему взвешивания терминов, а BM25 добавляет к ней насыщение частоты и явную поправку на длину документа. Для RAG это надёжный ретривер для имён, артикулов, кодов ошибок и других строк, где буквальное совпадение важнее семантической близости.

Токенизация и нормализация

До ранжирования и документ, и запрос проходят один и тот же анализатор (analyzer): строка превращается в последовательность индексируемых терминов. Типичный конвейер включает:

  1. Нормализацию Unicode. Канонически эквивалентные последовательности приводятся к одной форме; типографские варианты кавычек, дефисов и пробелов при необходимости унифицируются.
  2. Токенизацию. Текст делится на слова, числа и знаки. Простого разбиения по пробелам недостаточно для адресов электронной почты, версий, составных слов и языков без пробелов.
  3. Нормализацию регистра и формы. Case folding устраняет различия регистра; стемминг отбрасывает окончания по правилам, а лемматизация приводит словоформу к словарной форме. Лемматизация точнее, но дороже и зависит от морфологического анализатора.
  4. Фильтрацию. Стоп-слова можно исключить, если они дают длинные списки почти без сигнала. Для фразового поиска позиции токенов сохраняют даже тогда, когда часть токенов не участвует в обычном ранжировании.

Анализатор задаёт само пространство поиска. Если при индексации HTTP-503 превратился в два токена, а запрос обрабатывается как один, точного совпадения не будет. Для технических корпусов часто заводят два поля: нормализованное текстовое и поле точных значений, где идентификаторы сохраняются целиком. Полезно отдельно проверить обработку строк вроде ERR_CONN_RESET, Qwen2.5-7B, 10.4.2 и кириллических словоформ.

Изменение токенизатора, списка стоп-слов или правил нормализации меняет термины во всём корпусе. Это не настройка запроса, а версия индекса: после изменения анализатора индекс обычно строят заново.

Инвертированный индекс

Прямое представление хранит для каждого документа список его терминов. Поиск устроен наоборот, поэтому нужен инвертированный индекс (inverted index): словарь отображает каждый термин в список вхождений (posting list). Элемент списка обычно содержит идентификатор документа, частоту термина и, если нужны фразы или подсветка, позиции и смещения.

ТерминСписок вхождений: документ, частота, позиции
bm25\((d_1, 2, [3, 17]),\ (d_4, 1, [8]),\ (d_9, 4, [2, 11, 19, 25])\)
индекс\((d_1, 1, [7]),\ (d_2, 3, [4, 15, 28])\)

Для запроса из нескольких терминов движок читает только соответствующие списки и объединяет их по идентификаторам документов. Списки отсортированы, дельта-кодированы и сжаты; частые термины занимают много места, редкие — мало. Верхние границы вклада блока позволяют алгоритмам вроде WAND и Block-Max WAND пропускать документы, которые уже не могут попасть в текущий top-\(k\). Поэтому время зависит прежде всего от длин списков запроса, а не от полного числа документов \(N\).

Кроме списков индекс хранит статистики коллекции: число документов \(N\), документную частоту \(n_t\), длину каждого документа \(|d|\) и среднюю длину \(\operatorname{avgdl}\). Именно эти величины нужны BM25.

TF–IDF: частота в документе и редкость в корпусе

TF–IDF представляет документ разреженным вектором по словарю. Вес термина \(t\) в документе \(d\) — произведение двух факторов:

\[w_{t,d} = \operatorname{tf}(t,d)\cdot \operatorname{idf}(t).\]

Частота термина (term frequency, TF) повышает вес слова, которое повторяется внутри документа. Сырая частота \(f_{t,d}\) растёт линейно и позволяет длинным документам доминировать, поэтому часто используют сублинейный вариант:

\[\operatorname{tf}(t,d) = \begin{cases}1 + \log f_{t,d}, & f_{t,d} > 0,\\0, & f_{t,d}=0.\end{cases}\]

Обратная документная частота (inverse document frequency, IDF) понижает вес терминов, встречающихся во многих документах:

\[\operatorname{idf}(t)=\log\frac{N}{n_t},\]

где \(n_t\) — число документов, содержащих \(t\). Совпадение по слову, которое есть в десяти документах из миллиона, информативнее совпадения по слову, которое есть почти везде.

Запрос строится тем же способом. Документы можно ранжировать по скалярному произведению, но чаще используют косинусную близость, чтобы нормировать общую массу весов:

\[\operatorname{score}_{\text{tf-idf}}(q,d)=\frac{\sum_t w_{t,q}w_{t,d}}{\sqrt{\sum_t w_{t,q}^{2}}\sqrt{\sum_t w_{t,d}^{2}}}.\]

TF–IDF — не одна формула, а семейство вариантов: бинарная, сырая или логарифмическая TF; сглаженная IDF; разные способы нормировки. Это делает название удобным описанием принципа, но недостаточно точной спецификацией реализации.

Вероятностная мотивация BM25

Вероятностная модель релевантности начинает с принципа ранжирования по вероятности (probability ranking principle): при бинарной релевантности документы нужно упорядочить по убыванию \(P(R=1\mid d,q)\). В бинарной модели независимости (binary independence model) учитывается только наличие термина, а вклады терминов складываются как логарифмы отношений шансов.

Если известны оценки релевантности, вес термина сравнивает вероятность встретить его среди релевантных документов с вероятностью среди нерелевантных. Пусть \(R\) — число известных релевантных документов, \(r_t\) из них содержат термин, а \(n_t\) — число документов с термином во всей коллекции. Тогда вес Робертсона–Спарк Джонс имеет вид:

\[\operatorname{RSJ}(t)=\log\frac{(r_t+0.5)/(R-r_t+0.5)}{(n_t-r_t+0.5)/(N-n_t-R+r_t+0.5)}.\]

Без оценок релевантности полагают \(R=r_t=0\), и остаётся величина, близкая к IDF: редкий термин сильнее свидетельствует в пользу релевантности. На практике часто применяют всегда положительное сглаживание:

\[\operatorname{idf}_{+}(t)=\log\left(1+\frac{N-n_t+0.5}{n_t+0.5}\right).\]

Бинарная модель не различает одно и десять вхождений. BM25 расширяет её эвристикой частоты, мотивированной двухпуассоновской моделью: документы условно делятся на те, для которых термин является содержательным, и остальные; повторения повышают уверенность в первой группе, но каждое следующее повторение даёт всё меньше новой информации. Итоговая формула BM25 — практическая аппроксимация вероятностного рассуждения, а не калиброванная вероятность релевантности.

Формула BM25 и смысл множителей

Для короткого запроса без отдельного учёта частоты термина в запросе распространённая форма BM25 такова:

\[\operatorname{BM25}(q,d)=\sum_{t\in q\cap d}\underbrace{\operatorname{idf}_{+}(t)}_{\text{редкость в корпусе}}\cdot\underbrace{\frac{f_{t,d}(k_1+1)}{f_{t,d}+k_1\left(1-b+b\frac{|d|}{\operatorname{avgdl}}\right)}}_{\text{частота с насыщением и поправкой на длину}}.\]

У каждого множителя отдельная роль:

  • \(\operatorname{idf}_{+}(t)\). Совпадение по редкому термину сильнее повышает оценку. Конкретные реализации BM25 могут использовать другую сглаженную IDF, поэтому абсолютные оценки между движками сравнивать нельзя.
  • \(f_{t,d}\). Чем чаще термин встречается в документе, тем больше вклад, но зависимость не линейна.
  • \(k_1 > 0\). Управляет насыщением TF. При \(k_1\to 0\) наличие термина почти бинарно: любое положительное \(f_{t,d}\) даёт множитель около единицы. Чем больше \(k_1\), тем дольше повторения продолжают увеличивать оценку. При \(f_{t,d}\to\infty\) множитель стремится к \(k_1+1\).
  • \(b\in[0,1]\). Управляет нормализацией длины. При \(b=0\) длина игнорируется. При \(b=1\) частота полностью масштабируется отношением \(|d|/\operatorname{avgdl}\); одинаковое число вхождений сильнее ценится в коротком документе.
  • \(|d|/\operatorname{avgdl}\). Сравнивает длину документа со средней. Для документа средней длины этот множитель равен единице, поэтому \(b\) на его оценку не влияет.

Если обозначить \(K_d=k_1(1-b+b|d|/\operatorname{avgdl})\), TF-множитель равен \(f_{t,d}(k_1+1)/(f_{t,d}+K_d)\). Это прямоугольная гипербола: первый переход от нуля к одному вхождению важен сильнее, чем переход от девяти к десяти. Длинный документ получает большее \(K_d\), поэтому его кривая насыщения лежит ниже.

В классических вариантах BM25 встречается ещё множитель частоты термина в запросе с параметром \(k_3\). Для коротких поисковых запросов одна и та же лексема редко повторяется осмысленно, поэтому современные реализации обычно не используют этот множитель; формула выше суммирует вклад каждого уникального термина запроса один раз.

BM25 оценивает не «похожесть текстов вообще», а сумму независимых свидетельств от совпавших терминов. Его оценка не нормирована, не является вероятностью и имеет смысл только для сравнения документов внутри одного запроса и одного индекса.

Численный пример ранжирования

Пусть в коллекции \(N=1000\) документов, \(\operatorname{avgdl}=100\), а запрос состоит из терминов bm25 и index. Первый встречается в \(n_{\text{bm25}}=10\) документах, второй — в \(n_{\text{index}}=100\). Тогда:

\[\operatorname{idf}_{+}(\text{bm25})=\log\left(1+\frac{990.5}{10.5}\right)\approx 4.557,\qquad \operatorname{idf}_{+}(\text{index})=\log\left(1+\frac{900.5}{100.5}\right)\approx 2.299.\]

Возьмём \(k_1=1.2\), \(b=0.75\) и три документа:

Документ\(|d|\)\(f_{\text{bm25},d}\)\(f_{\text{index},d}\)\(K_d\)BM25
A80211,02\(4.557\cdot 1.457+2.299\cdot 1.089=9.143\)
B150401,65\(4.557\cdot 1.558=7.098\)
C60130,84\(4.557\cdot 1.196+2.299\cdot 1.719=9.400\)

Итоговый порядок: C, A, B. Документ B повторяет редкий термин четыре раза, но не содержит второй термин, длиннее среднего и уже находится в области насыщения TF. Короткий C выигрывает за счёт покрытия обоих терминов и трёх вхождений index. При \(b=0\) длина перестала бы помогать C, а при большом \(k_1\) повторения в B имели бы больший вес; порядок может измениться.

Сильные стороны и ограничения

Где лексический поиск особенно силён

  • Точные термины. Редкое название библиотеки, фамилия или доменный термин получают высокий IDF и не растворяются среди общих слов.
  • Идентификаторы. Артикулы, номера тикетов, коды ошибок, версии и имена функций часто нельзя надёжно восстановить из семантики. При корректном анализаторе буквальное совпадение почти идеально.
  • Интерпретируемость. Вклад каждого термина можно вывести, а причину ранжирования — проверить через статистики частоты и длины.
  • Стоимость. Индекс строится без обучения модели и GPU; добавления обрабатываются инкрементально, а запрос читает лишь несколько posting lists.

Что модель не видит

  • Лексический разрыв. «Сброс пароля» не совпадает с «восстановлением доступа», если синонимы не добавлены анализатором или расширением запроса.
  • Контекст и смысл. Мешок слов почти не учитывает порядок, отрицание и многозначность. Позиции позволяют искать фразы, но базовый BM25 их не использует.
  • Зависимость от анализа. Агрессивный стемминг смешивает разные термины, а слабая нормализация дробит одну сущность на варианты. Ошибка особенно дорога для идентификаторов.
  • Смещение по длине. Один глобальный \(b\) предполагает, что длины документов сопоставимы. Смесь коротких заголовков и длинных страниц лучше индексировать отдельными полями или единицами поиска.
  • Повторный шум. Шаблонные меню, футеры и ключевые слова могут искусственно повышать TF; их нужно удалять при подготовке документов.

BM25 в RAG на практике

  1. Определите единицу поиска. BM25 ранжирует то, что считает документом. После чанкинга \(|d|\), \(\operatorname{avgdl}\) и \(n_t\) считаются по чанкам, а не по исходным файлам. Слишком мелкие фрагменты получают преимущество от длины, слишком крупные размывают частоты.
  2. Разделите поля. Заголовок, основной текст и точные идентификаторы требуют разных анализаторов и весов. Для идентификатора полезно хранить нормализованное точное поле; для текста — языковой анализатор.
  3. Начните с \(k_1\) около \(1.2\) и \(b\) около \(0.75\), затем валидируйте. Это разумная стартовая точка, не универсальный оптимум. Подбирайте параметры по размеченным запросам и retrieval-метрикам; при одинаковой длине чанков влияние \(b\) почти исчезает.
  4. Проверяйте анализ и объяснение оценки. Для провального запроса сначала выведите токены запроса и документа, затем \(n_t\), \(f_{t,d}\), длину и вклад каждого термина. Это быстрее, чем менять параметры вслепую.
  5. Учитывайте обновления корпуса. IDF и \(\operatorname{avgdl}\) зависят от всей коллекции. Сегментированные индексы поддерживают добавления без полной перестройки, но удалённые документы и слияния сегментов могут немного менять оценки.

BM25 есть в движках на базе Lucene, например Elasticsearch и OpenSearch; лёгкие локальные варианты доступны в SQLite FTS5 и поисковых библиотеках. API различаются, но инженерная схема одна: зафиксировать анализатор, проиндексировать поля, запросить top-\(k\), измерить качество на собственных запросах и сохранить возможность объяснить оценку.

Минимальная реализация формулы полезна для тестов и сверки с движком:

from math import log

def bm25_term(tf, doc_len, avg_len, n_docs, doc_freq, k1=1.2, b=0.75):
    idf = log(1 + (n_docs - doc_freq + 0.5) / (doc_freq + 0.5))
    length_norm = 1 - b + b * doc_len / avg_len
    tf_weight = tf * (k1 + 1) / (tf + k1 * length_norm)
    return idf * tf_weight

score = sum(bm25_term(**stats) for stats in matched_query_terms)

Производственный движок дополнительно решает задачи сжатия posting lists, конкурентных обновлений, фильтров, фраз, нескольких полей и раннего завершения top-\(k\). Самописный цикл по всем документам воспроизводит формулу, но не производительность инвертированного индекса.

  • Robertson, Spärck Jones. Relevance Weighting of Search Terms, 1976 — вероятностное взвешивание терминов и RSJ weight.
