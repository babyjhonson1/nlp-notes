Пользователь задаёт вопрос в контексте разговора, поисковый индекс получает отдельную строку, а генератор читает только те фрагменты, которые поместились во вход. Между этими представлениями легко потерять условие: кто восстанавливает доступ, доступна ли почта, какая версия правил нужна. Преобразование запроса делает информационную потребность явной для поиска; сборка контекста сохраняет найденные доказательства в ограниченном бюджете. Разберём оба перехода на одном примере и увидим, почему даже хорошо ранжированный список нельзя просто целиком передать генератору.

Из реплики диалога в поисковый запрос

Продолжим условный пример документации сервиса из раздела о чанкинге. Пользователь сообщает: «У меня корпоративная учётная запись, доступа к привязанной почте нет. Смотрим правила версии v3». Следующая реплика: «Как теперь восстановить доступ и сколько это займёт?» Если отправить в поиск только её, потеряются тип аккаунта, недоступность почты и версия. Ретривер может вернуть инструкцию сброса по почтовой ссылке — хороший ответ на другой вопрос.

Переформулировка запроса (query rewriting) превращает текущую реплику и нужные части истории в самостоятельный запрос. Здесь результат может быть таким: «Восстановление доступа к корпоративной учётной записи без доступа к привязанной почте: порядок и срок по правилам v3». Генератору ответа при этом сохраняют исходную реплику и её контекст: поисковая формулировка — промежуточное представление задачи.

Формально, если \(q\) — реплика, \(h\) — выбранная история, а \(W\) — преобразователь, то поиск выполняется по \(\tilde q=W(q,h)\). Правильность \(W\) определяется сохранением условий вопроса, а не литературным качеством текста. Замена «почта недоступна» на «забыл пароль» уже меняет множество подходящих инструкций.

Преобразователь может быть шаблоном, правилами или LLM. В последнем случае полезно отдельно передавать список уже установленных условий и проверять сохранение идентификаторов, версий и отрицаний. Если местоимение допускает несколько интерпретаций, уточнение пользователя лучше выдуманной конкретизации. История помогает восстановить вопрос, но прежний ответ ассистента сам по себе не подтверждает правила сервиса.

Работа Ma et al. рассматривает схему Rewrite–Retrieve–Read и обучение преобразователя по обратной связи от читающей модели. Здесь нам достаточно общего интерфейса: преобразовать запрос, найти документы, проверить, улучшилось ли покрытие нужных доказательств. Польза переформулировки на конкретном корпусе требует проверки.

Когда одной формулировки мало

Несколько формулировок одной потребности

После уточнения вопроса остаётся лексический разрыв: пользователь говорит «вернуть доступ», а справка — «восстановление учётной записи». Поиск по нескольким запросам (multi-query retrieval) запускает поиск по нескольким выражениям той же потребности. Например, вместе с \(\tilde q\) используем «корпоративная учётная запись: подтверждение личности без почты, порядок и срок, v3». Критические условия сохраняются в каждой формулировке.

Если по каждому запросу извлечено не более \(m\) кандидатов, объединяем их по устойчивому идентификатору:

\[C=\bigcup_{j=0}^{J}\operatorname{Retrieve}(q_j,m),\qquad q_0=\tilde q,\qquad |C|\le (J+1)m.\]

Один документ, найденный несколько раз, остаётся одним кандидатом. Для слияния порядков подходит уже разобранный RRF; затем кандидаты можно оценить реранкером относительно полной уточнённой потребности. Почти одинаковые запросы дают коррелированные выдачи: многократное обнаружение документа не означает несколько независимых подтверждений. Число запросов и общий размер пула ограничивают, чтобы увеличение полноты не привело к неконтролируемой стоимости следующего этапа.

HyDE: искать по образцу возможного документа

Иногда короткий вопрос плохо похож на стиль искомого документа. Метод эмбеддингов гипотетического документа (Hypothetical Document Embeddings, HyDE) сначала генерирует текст, похожий на возможный ответный документ, кодирует его и ищет реальные документы в окрестности полученного вектора:

\[\hat d\sim G(\,\cdot\mid\tilde q),\qquad z=g(\hat d),\qquad C_{\mathrm{HyDE}}=\operatorname{Top}_m\bigl(\mathcal D;\ d\mapsto s(z,g(d))\bigr).\]

Здесь \(G\) — генератор, \(g\) — кодировщик, \(s\) — мера сходства; \(\operatorname{Top}_m\) возвращает \(m\) документов коллекции \(\mathcal D\) с наибольшими оценками. В исходной работе использован контрастивно обученный кодировщик без разметки релевантности. Переход к документу помогает выразить ожидаемую тему более развёрнуто; перенос на другой кодировщик с особыми префиксами нужно проверять отдельно.

Для нашего вопроса гипотетический текст мог бы упомянуть проверку личности и подтверждение администратором, но также выдумать срок. Поэтому \(\hat d\) служит только для поиска: доказательствами остаются найденные реальные источники. Если модель уверенно придумала неверную процедуру, её вектор может увести поиск к неподходящим документам. Сохранение обычной поисковой ветки уменьшает зависимость от одной гипотезы, но не гарантирует правильный результат.

Декомпозиция: найти разные части ответа

Декомпозиция запроса (query decomposition) решает другую проблему: одного документа может быть недостаточно. Вопрос содержит два подзапроса: «Как восстановить корпоративный аккаунт без почты по v3?» и «Каков срок этого восстановления по v3 и с какого момента он считается?». Они ищут разные доказательства. В отличие от multi-query, задача здесь — покрыть все части ответа, а не получить несколько перефразировок.

В нашем случае подзапросы можно выполнить параллельно. Если второй зависит от результата первого, например «какой срок установлен для найденного способа проверки?», конкретный способ подставляют после получения источника. Последовательные шаги добавляют задержку и распространяют ошибки промежуточного ответа. Ограниченные декомпозиции разобраны, например, в RERC; произвольные циклы поиска относятся к продвинутому RAG.

Эти преобразования устраняют разные причины промаха. Rewriting восстанавливает условия, multi-query меняет формулировки, HyDE создаёт поисковый образец, decomposition разделяет потребности. Добавлять все четыре к каждому запросу нет оснований: сначала найдите ошибку исходного поиска и проверьте, исправляет ли её выбранное преобразование.

Из результатов поиска в единицы контекста

Предположим, кандидаты уже найдены и оценены по полной потребности пользователя. Ниже — условное продолжение документации из чанкинга: срок добавлен для этого примера, а оценки заданы вручную и не являются результатом работы модели. Версия всех источников — v3.

IDСодержимое фрагментаРелевантность \(r_i\)
A«Восстановление без почты»: подтвердите личность через форму поддержки по телефону из профиля; для корпоративного аккаунта запрос дополнительно подтверждает администратор.\(0.90\)
B«FAQ для организаций»: если привязанная почта недоступна, восстановление оформляют через поддержку с подтверждением личности и участием администратора.\(0.88\)
C«Срок восстановления без почты»: доступ восстанавливают в течение двух рабочих дней после завершения всех проверок, включая подтверждение администратора.\(0.75\)
D«Тарифы для организаций»: стоимость зависит от числа участников рабочей области.\(0.30\)

Два первых результата оба описывают процедуру, но не срок. Даже идеальная оценка отдельных пар «запрос — фрагмент» не обязана дать лучший набор для ответа: полезность B зависит от того, выбран ли уже A.

До содержательного отбора устраняют простые повторы. Один и тот же чанк из нескольких поисковых веток объединяют по ключу «документ, версия, диапазон». Пересекающиеся диапазоны одного документа можно слить и восстановить текст из оригинала. Копии в разных источниках требуют сохранения происхождения: одинаковый текст не делает разные версии взаимозаменяемыми. B не является точной копией A, поэтому такая дедупликация его не уберёт.

Затем определяют единицу контекста. Если найдено только предложение о подтверждении администратором, восстанавливают заголовок и связанный абзац, как в parent–child или sentence-window retrieval. Соседство ограничивают тем же документом и версией; случайно захваченный раздел о тарифах ухудшит контекст. После расширения повторно объединяют пересечения. Далее сравнивают и считают размер уже тех блоков, которые реально собираются передать генератору.

MMR: полезность следующего фрагмента

Чтобы B не занимал место только благодаря высокой индивидуальной оценке, введём штраф за сходство с уже выбранным. Максимальная маргинальная релевантность (Maximal Marginal Relevance, ) задаёт жадный выбор следующего фрагмента:

\[i^\star=\operatorname*{arg\,max}_{i\in C\setminus S}\left[\lambda r_i-(1-\lambda)\max_{j\in S}s_{ij}\right],\qquad 0\le\lambda\le1.\]

Здесь \(C\) — пул кандидатов, \(S\) — уже выбранные, \(r_i\) — соответствие вопросу, \(s_{ij}\) — сходство содержимого двух фрагментов. Внутренний максимум отвечает на вопрос «насколько этот кандидат повторяет хотя бы один выбранный?». После каждого добавления \(S\) меняется, поэтому оценки оставшихся пересчитывают. Для пустого набора начнём с максимального \(r_i\); это явное правило инициализации, в том числе при \(\lambda=0\).

При \(\lambda=1\) штраф исчезает и остаётся обычный порядок релевантности. При \(\lambda=0\) после первого выбора учитывается только непохожесть на выбранное. Промежуточные значения определяют, сколько релевантности мы готовы уступить ради нового содержания.

Релевантность и сходство могут вычисляться разными моделями, но их масштабы должны быть согласованы. Вычитание косинуса из произвольного логита реранкера при фиксированном \(\lambda\) не задаёт устойчивого компромисса. В нашем условном расчёте обе оценки лежат в \([0,1]\), выше — сильнее; они не являются вероятностями. Даже одинаковый диапазон не заменяет подбор \(\lambda\) на dev-выборке.

Откуда меняется порядок

Первым выбирается A. Зададим сходства B с A равными \(0.95\), C с A — \(0.20\), D с A — \(0.05\). При \(\lambda=0.7\) получаем:

При \(\lambda=0.9\) повтор опять выигрывает. Наоборот, при \(\lambda=0.2\) вторым окажется D: чрезмерный штраф за повтор поощряет даже мало относящийся к вопросу текст.

Для третьего шага зададим ещё \(s_{BC}=0.25\), \(s_{BD}=0.10\), \(s_{CD}=0.15\). После A и C штраф B по-прежнему определяется A, а штраф D уже определяется C. Нельзя сравнивать только с последним выбранным: тогда B почти перестал бы штрафоваться, хотя повтор A никуда не исчез.

— эвристика состава набора. Она не доказывает, что каждый подзапрос получил ответ, и не оптимизирует автоматически число полезных фактов на токен. Семантически похожие фрагменты могут содержать разные необходимые условия или противоречие; их нельзя удалять лишь по высокому сходству. Если вопрос явно разделён на процедуру и срок, проверка покрытия обеих частей остаётся отдельным шагом. Краткая формула и отличие от MRR есть в справочнике. Идея релевантности с учётом уже выбранного описана в работе Goldstein и Carbonell.

Сжатие, порядок и токенный бюджет

Сколько места действительно осталось

Число фрагментов само по себе не задаёт длину входа. Пусть \(L\) — общий лимит последовательности генератора, \(O\) — резерв на вывод, \(H\) — размер инструкций, вопроса, истории и шаблона без найденных фрагментов, \(\delta\) — запас. Тогда предварительный бюджет источников:

\[B=L-O-H-\delta.\]

Это расчёт для модели с общим лимитом входа и вывода; отдельные лимиты конкретного сервера проверяются дополнительно. Если \(B<0\), сокращать нужно уже обязательный вход или резерв, а не молча отправлять переполненный запрос.

Для условного малого окна \(L=1024\), \(O=256\), \(H=420\), \(\delta=48\) остаётся \(B=300\) токенов. Пусть подготовленные блоки A, B, C, D вместе с заголовками и метаданными стоят соответственно \(140\), \(130\), \(100\), \(70\) токенов. Эти длины заданы для арифметики, а не измерены токенизатором. Первые по релевантности A и B займут \(270\), но не дадут срока. A и C займут \(240\) и покроют обе части вопроса.

Порядок при \(\lambda=0.7\) начинается с A, C, B. При упаковке B уже не помещается. Можно проверить следующие кандидаты, но свободное место не требуется заполнять любой ценой. Пропуск слишком длинного кандидата — жадное правило, а не точное решение задачи оптимального набора. После изменения или сокращения блоков их размеры и сходства могут измениться; настройки отбора нужно сверять с итоговым контекстом.

Сократить текст, сохранив доказательство

Сжатие контекста (context compression) убирает части найденного материала, не нужные для конкретного вопроса. Экстрактивный вариант сохраняет предложения или диапазоны оригинала. Абстрактивный пересказывает их и может сильнее сократить текст, но добавляет риск изменить смысл. Для C опасно получить «восстановление за два дня»: исчезли рабочие дни и момент начала отсчёта. Сохранять нужно всю зависимость «два рабочих дня после завершения всех проверок».

Сокращённому блоку сохраняют идентификатор документа, версию и связь с исходными диапазонами; координаты оригинала нельзя выдавать за координаты нового пересказа. Если два источника расходятся, сжатие не должно незаметно превращать их в одну согласованную формулировку. Формат цитат и решение при недостатке доказательств относятся к разделу о генерации.

Отбор и порядок чтения — разные решения

задаёт порядок выбора, но генератору можно расположить выбранные блоки иначе. Для нашего вопроса естественна последовательность «условия и процедура A → срок C»; соседние абзацы одного документа сохраняют исходный порядок. У каждого блока остаются заголовок, версия и ID, чтобы местоимения и условия не оторвались от источника.

В Lost in the Middle качество исследованных моделей зависело от положения нужного фрагмента: середина длинного контекста часто использовалась хуже краёв. Это эмпирический результат, а не универсальный закон для всех моделей. Практический вывод — сравнивать несколько порядков на своём генераторе при одном и том же наборе, а не считать более длинный вход автоматически более полезным.

Последняя проверка бюджета делается токенизатором генератора по полностью собранному входу: с разделителями, ролями, заголовками и метаданными. Сумма длин отдельных строк может отличаться от длины их сериализованного объединения. После сжатия и перестановки проверьте и длину, и сохранность необходимых условий.

Сборка конвейера на практике

Ниже воспроизводимый на заданных оценках. Для равных значений используем исходный порядок кандидатов; первый выбор всегда по релевантности. Максимальный штраф обновляется только относительно нового выбранного элемента: при готовых сходствах это \(O(|C|k)\) операций для отбора \(k\) фрагментов. В примере хранится полная матрица; в большом пуле сходство с новым выбранным можно считать по мере надобности.

IDS = ["A", "B", "C", "D"]
REL = [0.90, 0.88, 0.75, 0.30]
SIM = [
    [1.00, 0.95, 0.20, 0.05],
    [0.95, 1.00, 0.25, 0.10],
    [0.20, 0.25, 1.00, 0.15],
    [0.05, 0.10, 0.15, 1.00],
]

def mmr(rel, sim, k, weight=0.7):
    if not 0 <= weight <= 1 or k < 0:
        raise ValueError("Некорректные параметры")
    remaining = list(range(len(rel)))
    selected = []
    redundancy = [0.0] * len(rel)  # sim в этом примере неотрицательна
    while remaining and len(selected) < k:
        def score(i):
            if not selected:
                return rel[i]
            return weight * rel[i] - (1 - weight) * redundancy[i]
        chosen = max(remaining, key=score)
        selected.append(chosen)
        remaining.remove(chosen)
        for i in remaining:
            redundancy[i] = max(redundancy[i], sim[i][chosen])
    return selected

order = mmr(REL, SIM, k=3)
print([IDS[i] for i in order])  # ['A', 'C', 'B']

# Демонстрационная упаковка по порядку MMR и заданным стоимостям.
# Это не подсчёт токенов реальной моделью.
costs = [140, 130, 100, 70]
budget, used, packed = 300, 0, []
for i in order:
    if used + costs[i] <= budget:
        packed.append(IDS[i])
        used += costs[i]
print(packed, used)  # ['A', 'C'] 240

В рабочем конвейере сначала восстанавливают запрос и фиксируют условия, затем выполняют выбранные поисковые ветки, объединяют кандидатов, применяют реранкер и строят единицы контекста. Далее удаляют повторы, выбирают состав, при необходимости сжимают текст, задают порядок и проверяют полный вход. Если сжатие удалило условие или расширение подтянуло новую тему, возвращаются к отбору, а не только уменьшают число токенов.

Поисковый движок, например Lucene, отвечает за извлечение кандидатов; модель эмбеддингов может давать попарные сходства, а cross-encoder — релевантность. поверх готовых оценок не требует отдельного фреймворка. Версии моделей, их формат входа и шкалу оценок фиксируют так же, как в плотном поиске и реранкинге.

Для диагностики сохраняют исходный и преобразованный вопросы, происхождение кандидатов, выбранные диапазоны и итоговый контекст. Сравнивают исходный поиск с преобразованием по наличию нужных доказательств в пуле; затем обычный top-\(k\) с — при одинаковом токенном бюджете. Если срок найден, но пропал при упаковке, расширение поискового пула не исправляет эту ошибку. Проверять нужно конкретный переход конвейера; протокол разобран в разделе об оценке RAG.

  • Goldstein, Carbonell. Summarization: (1) Using MMR for Diversity-Based Reranking and (2) Evaluating Summaries, 1998 — совместный учёт релевантности и новизны относительно уже выбранного материала.

  • Liu et al. Lost in the Middle: How Language Models Use Long Contexts, 2024 — экспериментальная зависимость качества от позиции нужных сведений в длинном входе.
