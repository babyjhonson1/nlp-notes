Хороший результат поиска ещё не означает хороший ответ: нужный фрагмент можно потерять при упаковке, а найденное условие — исказить при генерации. Поэтому RAG оценивают одновременно по конечной задаче и по промежуточным результатам. В этом разделе строим проверочный набор, разделяем ошибки поиска, контекста, ответа и ссылок, затем ставим диагностический эксперимент на вопросе о восстановлении аккаунта. Формулы и соглашения о пустых ответах находятся в справочнике; здесь важно выбрать, что измерять и какие выводы допускает измерение.

Сначала зафиксировать задачу и разметку

Продолжим пример предыдущего раздела. Пользователь потерял доступ к привязанной почте корпоративного аккаунта и спрашивает: «Как восстановить доступ и сколько это займёт?» В действующей версии правил процедура требует формы поддержки, проверки личности по телефону и подтверждения администратора; срок — до двух рабочих дней после завершения всех проверок. Поисковая строка без истории диалога не задаёт эту задачу полностью.

Проверочный набор (evaluation set) хранит не только вопрос и эталонный ответ. Нужны история диалога, версия корпуса, доступные этому пользователю источники, время действия правил и разметка доказательств. Иначе система может получить штраф за корректный ответ по другой версии документа или балл за сведения, которые ей запрещено использовать.

Разметка релевантности запросу (query relevance judgments, qrels) связывает запрос с документами или фрагментами и их степенью релевантности. Для сравнения чанкинга исходные доказательства лучше хранить как диапазоны текста в версии документа, а не только как ID чанков: после изменения границ ID меняются. Для одного факта допускаются альтернативные доказательства; для вывода из нескольких источников отмечают, какие части нужны совместно. Правило пересчёта диапазонов в релевантность чанков фиксируют до эксперимента.

Отсутствие qrel не доказывает нерелевантность. Практический способ расширять разметку — объединить верхние результаты нескольких разных систем и проверить их вручную: это пулинг (pooling). Он уменьшает объём работы, но не делает разметку полной; новый ретривер может находить полезные документы вне старого пула. Храните различие «проверен и нерелевантен» и «не проверен», долю непроверенных результатов и принятую конвенцию расчёта.

В набор включают вопросы, на которые корпус действительно не содержит ответа, а также неоднозначные и частично ответимые запросы. Для вопроса «гарантируете восстановление за час?» правильный ответ не должен превращать верхнюю границу в обещание. Для вопроса о неописанном внутреннем процессе нужен отказ или уточнение по рубрике. Метка «неответим» требует проверки доступного корпуса; пустой список релевантных документов сам по себе такой меткой не является.

От релевантной выдачи к достаточным доказательствам

Сначала проверяем, попали ли нужные сведения в пул кандидатов. подходит, когда важно собрать известные релевантные объекты; — когда достаточно быстро найти первый релевантный результат; учитывает порядок и градации полезности. Их определения и ограничения приведены в справочнике метрик поиска. Глубину среза выбирают по реальному месту в конвейере: большой пул до реранкера и короткий список после него отвечают на разные вопросы.

В нашем примере A и B — два пересказа процедуры, C — срок. Если все три фрагмента размечены релевантными, выдачи A, B и A, C имеют одинаковую полноту по фрагментам \(2/3\), а первый результат в обеих релевантен. Однако только A, C позволяют ответить на обе части вопроса. Значит, одной релевантности отдельных объектов недостаточно: нужно измерять покрытие обязательных доказательств.

Введём две единицы доказательства: процедуру и срок. Покрытие доказательств () показывает долю покрытых единиц, а строгий индикатор требует покрыть все. В A, B покрытие равно \(1/2\), в A, C — \(1\). Это не универсальная библиотечная метрика: состав единиц и критерий достаточности определяет рубрика задачи. Формула и правила разметки вынесены в справочник.

Измеряем это покрытие в трёх точках: пул кандидатов, список после реранкера и фактический вход генератора. Последняя проверка выполняется после расширения фрагментов, дедупликации, сжатия и обрезки. Если C найден, но не поместился, исправлять ретривер преждевременно. Если сжатие оставило «два дня», ID источника всё ещё присутствует, но доказательство срока с необходимыми условиями уже потеряно.

ANN-recall относительно точного векторного поиска, полнота по размеченным документам и покрытие доказательств — разные величины. Первая проверяет индекс, вторая — выдачу, третья — достаточность сведений для задачи. Высокое значение одной не гарантирует высоких остальных.

Правильность, подтверждённость и цитирование

Пусть генератор получил только A, B и ответил: «Подайте форму поддержки, подтвердите личность по телефону и получите подтверждение администратора». Подтверждённость контекстом () равна \(1\). Но срок пропущен, поэтому полная правильность ответа () по нашей бинарной рубрике равна \(0\). Из трёх обязательных фактов названы два без лишних утверждений: фактическая F1 () равна \(0.8\). Эти числа описывают разные свойства одного ответа, а не спорят между собой.

Обратная ошибка: генератор получил A, C, но написал «восстановят через два дня после обращения». Сведения были найдены, однако потерялись «рабочих», верхняя граница «до» и условие начала отсчёта. По разметке из трёх утверждений подтверждены и совпадают с эталоном только два; и равны \(2/3\). Такой дефект следует искать в генерации или инструкции, а не в отсутствии документа.

Правильность сравнивают с проверенными действующими правилами; подтверждённость — с реально переданным контекстом. Пересказ устаревшего документа может быть полностью подтверждённым и неверным для текущего запроса. Поэтому судья правильности не должен использовать найденный контекст как единственную истину.

Ссылки проверяются отдельно. Если полный правильный ответ ссылается на A для процедуры и администратора, но не даёт ссылки на C для срока, точность цитирования () равна \(1\), а полнота цитирования () — \(2/3\). Это доля подтверждённых связей и доля утверждений с подтверждающими ссылками соответственно. Ссылка на тарифы вместо C не исправит полноту, но снизит точность до \(2/3\). В справочнике явно оговорены единица подсчёта и случай совместного доказательства несколькими источниками.

Отказы нельзя просто выкинуть из отчёта. Вместе с качеством выданных ответов показывают долю ответов () и избирательный риск (): на какой доле вопросов система отвечает и как часто ошибается среди этих ответов. Иначе отказ от трудных вопросов выдаёт себя за улучшение качества. Отдельно проверяют отказы на ответимых запросах и выдуманные ответы на неответимых; правила частичного ответа задают заранее.

Полные определения, нулевые знаменатели и различие макро- и микроусреднения собраны в справочнике метрик генерации. В частности, пустой ответ не получает автоматически идеальную подтверждённость или точность цитирования.

Локализация ошибки экспериментом

Диагностика начинается с сохранённой трассы одного неудачного запроса: исходный и преобразованный вопрос, кандидаты с оценками, результат реранкера, точный контекст, ответ и ссылки. Для нашего вопроса сравним упаковку по релевантности и отбор через . Данные и ответы ниже условные: это разбор механизма, а не результат запуска модели.

В первых двух строках не меняются rewriting, поиск, реранкер, генератор и общий бюджет. Используем условные стоимости предыдущего раздела: A и B занимают \(270\) токенов, A и C — \(240\), доступно \(300\). Пакеты не обязаны иметь одинаковую длину, но оба удовлетворяют одному ограничению. В этом примере проблема базового режима локализована в отборе: доказательство срока уже было в пуле. Выигрыш не следует приписывать улучшению поиска.

Эталонный контекст (oracle context) собирают из размеченных доказательств и подают тому же генератору, сохраняя вопрос, инструкцию, формат и бюджет. Если это исправляет ответ, качество доступного контекста было ограничением. Если ошибка остаётся, проверяют генерацию, рубрику и сам эталон. Oracle — диагностическое вмешательство, а не гарантированная математическая верхняя граница: порядок, длина и взаимодействие источников тоже влияют на генератор. Эталон, не помещающийся в бюджет, требует отдельного эксперимента, а не скрытого увеличения окна.

Чтобы различить поиск и упаковку, одного oracle недостаточно: нужны промежуточные измерения из таблицы. Если доказательство отсутствует в пуле, отдельно проверяют исходный и переписанный запрос, фильтры доступа и версий, индекс и поиск. Если оно есть в пуле, но отсутствует после реранкера, смотрят второй этап и его предел входа. Если оно дошло до генератора, но ответ неверен, увеличение числа кандидатов само по себе не объясняет, как устранить ошибку.

Абляция (ablation) — эксперимент с удалением или заменой компонента при фиксированных остальных условиях. Например, отключение rewriting проверяет, насколько сохранение истории помогает на диалоговых запросах, а отключение — нужен ли разнообразный контекст при данном бюджете. Это вклад в конкретный конвейер, не свойство метода вне него. Если два компонента взаимодействуют, нужны все четыре комбинации их включения; отдельные выигрыши нельзя просто сложить.

Модель-судья и проверка разметки

Модель-судья (LLM-as-judge) может выделять утверждения и проверять их по источникам. Но результат её вызова — предсказанная разметка, а не автоматически истинное значение метрики. Схема из RAGAs полезна для масштабирования проверки, если отделить выделение фактов от проверки поддержки и сохранить промежуточные решения.

В проверке подтверждённости судье дают утверждение и фактический контекст; требуют указать подтверждающий диапазон либо метку «противоречит» или «нет сведений». В проверке правильности дают вопрос с условиями, ответ и проверенную рубрику. В проверке ссылок — только привязанные источники, а не весь корпус: иначе судья оправдает неправильную ссылку фактом из другого документа. Ответ судьи разбирают как структурированные данные, ошибки формата считают отдельно, не превращая их молча в нули.

В нашем примере тест для судьи — различить «до двух рабочих дней после проверок» и «два дня после обращения». Высокое сходство слов не означает логического следования. Человек проверяет не только итоговую оценку, но и то, не пропустил ли этап выделения утверждений ошибочное условие. На размеченной вручную подвыборке отдельно считают случаи ложного подтверждения и ложного отклонения; смешанная итоговая доля совпадений может скрывать редкие, но опасные ошибки.

Подвыборка должна включать корректные ответы, пропуски, противоречия, неответимые запросы, разные языки и длины. Спорные примеры независимо размечают два человека, затем согласуют трактовку рубрики. Только после этого масштабируют автоматическую разметку и периодически перепроверяют её. Изменение модели-судьи или её инструкции требует повторной калибровки.

Работа Zheng et al. показывает смещения судей к позиции, многословию и собственным ответам в задачах сравнения ассистентов; это не даёт готовой гарантии для нашего RAG. При парном сравнении скрывают название системы, меняют порядок ответов и проверяют устойчивость вердикта. Фиксируют версию судьи, инструкцию, параметры генерации и исходный ответ судьи; даже низкая температура сама по себе не доказывает воспроизводимость.

Честное сравнение систем

Выбор параметров, порога отказа и инструкции судье выполняют на настроечной выборке (development set, dev); итоговую оценку — на отложенной тестовой (test set). Перефразировки одного вопроса и реплики одного диалога нельзя случайно раскидать между частями. Если проверяется перенос на новые документы, разделяют по документам; если работа с будущими правилами — по времени. Документы тестовых вопросов могут входить в доступный поиску корпус по постановке RAG, но ответы и qrels теста не должны участвовать в настройке.

Синтетические вопросы полезны для заполнения редких сценариев, но вопрос, сгенерированный из конкретного абзаца, может слишком легко совпадать с ним по словам и не отражать реальные запросы. В отчёте указывают происхождение вопросов и отдельно показывают результаты на пользовательских и синтетических данных. Эталонные ответы проверяют, а не принимают автоматически из той же модели, которую оценивают.

Сравнение проводят попарно на одних вопросах, версии корпуса и правилах доступа. Для каждой системы фиксируют число кандидатов, бюджет контекста и ответа, задержку и стоимость запросного контура. Изменение чанкинга может требовать перестроения индекса; изменение только упаковки — нет. Не называют ускорением результат, полученный за счёт меньшего бюджета или пропуска трудных запросов, без указания этого обмена.

Средние дополняют срезами: запросы с точными идентификаторами, диалоговые, требующие нескольких доказательств, неответимые, старые и новые версии правил. Срезы выбирают заранее, рядом показывают число вопросов. Одинаковое среднее может скрывать улучшение простых случаев и деградацию критичного сценария без почты.

Для разности средних используют парный бутстреп, сохраняя оценки обеих систем для каждого перевыбранного вопроса вместе. Связанные вопросы перевыбирают группами. Интервал, пересекающий ноль, не доказывает равенство систем; он означает, что данных и принятого протокола недостаточно для уверенного вывода о знаке эффекта. Интервал не исправляет утечку, плохой эталон или систематическую ошибку судьи. При стохастической генерации повторные прогоны нужны для оценки дополнительной вариативности; бутстреп одного сохранённого ответа на вопрос её полностью не измеряет.

Выбор конфигурации — решение с ограничениями: повысить успех задачи при допустимой задержке, стоимости и частоте неподтверждённых ответов. Одно взвешенное «качество RAG» скрывает, какой именно компромисс произошёл. Сначала показывайте компоненты и знаменатели, затем правило принятия решения.

Применение на практике

Минимальный артефакт эксперимента — одна запись на вопрос и конфигурацию: ID вопроса и группы, версия корпуса и разметки, параметры компонентов, ID и тексты кандидатов, точный вход генератора, ответ, ссылки, оценки и время этапов. Тексты и доступ к трассам ограничивают так же, как доступ к исходным данным. Иначе сравнение нельзя воспроизвести или объяснить по одному итоговому среднему.

from statistics import mean

baseline = [0, 1, 0, 1, 0, 1, 0, 0]
candidate = [1, 1, 1, 0, 0, 1, 1, 0]
assert len(baseline) == len(candidate) and baseline
diff = [new - old for old, new in zip(baseline, candidate)]
delta = mean(diff)

rng = Random(7)
n = len(diff)
samples = sorted(
    mean(diff[rng.randrange(n)] for _ in range(n))
    for _ in range(5000)
)

# Эмпирический квантиль с линейной интерполяцией.
def quantile(values, p):
    x = (len(values) - 1) * p
    lo = int(x)
    hi = min(lo + 1, len(values) - 1)
    return values[lo] + (x - lo) * (values[hi] - values[lo])

interval = (quantile(samples, 0.025), quantile(samples, 0.975))
print(mean(baseline), mean(candidate), delta)
print(interval)
assert delta == 0.25
assert interval[0] <= 0 <= interval[1]

В этом расчёте средние равны \(0.375\) и \(0.625\), прирост — \(0.25\), то есть \(25\) процентных пунктов. Но интервал включает ноль: несколько изменившихся ответов на малой выборке не дают устойчивого вывода. В рабочем отчёте сохраняют также число перевыборок, способ построения интервала и единицу перевыборки; после просмотра test не подбирают параметры по этим результатам.

Метрики ранжирования удобно считать готовыми инструментами вроде trec_eval; RAGAs — краткий пример автоматизации разметки ответов. Ни один инструмент не выбирает за вас рубрику, гранулярность доказательств и обработку пустых значений. До интеграции проверьте ручной пример, дубликаты, пустую выдачу, отказ и неправильный ID цитаты; зафиксируйте реализацию и версию. Реальные прогоны генераторов и судей требуют отдельного бюджета — приведённый код проверяет только арифметику отчёта.
