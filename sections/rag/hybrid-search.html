BM25 и плотный поиск ошибаются на разных запросах. Первый не видит перефразирования, второй путает точные идентификаторы, которые почти не влияют на вектор текста. Гибридный поиск (hybrid search) запускает оба поиска и объединяет их выдачи в одну. Главная трудность — в объединении: оценки BM25 и косинусы лежат в несравнимых шкалах, и простое сложение отдаёт решение тому поиску, у которого числа больше. Разберём два способа решить эту проблему — нормализацию оценок и объединение по местам, Reciprocal Rank Fusion, — а затем фильтрацию по метаданным, которая меняет сами списки кандидатов.

Зачем объединять два поиска

Вернёмся к документации сервиса из предыдущих разделов. На запросе «забыл пароль, почта не открывается» BM25 ставит «Смену пароля» выше «Восстановления доступа»: у первой больше общих слов с запросом, хотя отвечает вторая (разбор в разделе о dense retrieval). Плотный поиск здесь справляется лучше, потому что сопоставляет перефразирования.

Теперь возьмём запрос с идентификатором: «не проходит оплата картой, ошибка ERR-4031». Для этого примера возьмём пять близких по теме чанков:

ЧанкСодержание
AERR-4031: банк отклонил платёж — что означает код и что делать.
BERR-4013: превышен лимит попыток входа.
CОплата картой: какие карты принимаются.
DСправочник кодов ошибок: длинная таблица всех кодов, в том числе ERR-4031.
EСмена способа оплаты.

Отвечает на вопрос чанк A. BM25 ставит первым справочник D: в нём есть и редкий термин err-4031, и многократные «ошибка» и «оплата». Плотный поиск ставит первым общий чанк C об оплате картой, а на третье место — B с похожим кодом другой ошибки. Справочник D в его выдачу не попадает вовсе: одна строка про ERR-4031 тонет в среднем векторе длинной таблицы. Правильный чанк A каждый из поисков ставит только вторым.

Здесь и далее считаем, что каждый поиск вернул четыре кандидата. Оценки обоих поисков условные: оценки BM25 имеют типичный для формулы BM25 масштаб, косинусы — демонстрационные. Важны их шкалы и порядок, а всё дальнейшее вычисляется из них.

Каждый поиск ошибается по-своему, но правильный ответ высоко в обоих списках. Задача гибридного поиска — построить из двух списков третий, в котором A окажется первым.

Объединение кандидатов

Схема гибридного поиска: каждый поиск независимо возвращает свои первые \(k'\) кандидатов, затем кандидатов объединяют и каждому назначают общую оценку. Обозначим списки \(R_{\text{lex}}\) и \(R_{\text{dense}}\). Множество кандидатов

\[C=R_{\text{lex}}\cup R_{\text{dense}}\]

содержит всё, что нашёл хотя бы один поиск. Поэтому доля релевантных документов, попавших в \(C\), не меньше, чем в каждом из списков по отдельности. В примере \(C=\{A,B,C,D,E\}\). Но \(C\) больше каждого списка, а дальше по конвейеру передаётся только \(k\) лучших. Полнота \(C\) — это верхняя граница: дальше её может только потерять правило объединения, если поставит релевантный документ ниже \(k\)-го места.

Сразу возникает вопрос: какую оценку от плотного поиска получает D, которого в его списке нет? Отсутствие в списке не означает нулевую релевантность: просто оценка D ниже, чем у четвёртого кандидата. Правила объединения ниже по-разному обходятся с такими пропусками. Если нужна точность, недостающие оценки можно досчитать: вектор D хранится в индексе, и его косинус с запросом вычисляется одним скалярным произведением. BM25 для конкретного документа тоже считается по его частотам терминов.

Объединение оценок: нормализация и веса

Почему нельзя просто сложить

Самое простое правило — сумма оценок, где отсутствующей оценке приписан ноль. Тогда D получает \(12.4\), а A — \(11.0+0.81=11.81\), и первым остаётся D. Косинус не превышает единицы, а оценки BM25 различаются на единицы и десятки. Поэтому вклад плотного поиска почти никогда не меняет порядок BM25: сумма фактически совпадает с лексической выдачей.

Шкала BM25 к тому же не фиксирована: оценка — сумма вкладов терминов запроса, поэтому длинный запрос из редких слов получает большие числа, а короткий из частых — маленькие. Никакой постоянный множитель не приведёт её к шкале косинуса сразу для всех запросов.

Min-max нормализация

Распространённое решение — для каждого запроса отдельно отобразить оценки каждого списка в отрезок \([0,1]\):

\[\hat{s}(d)=\frac{s(d)-\min_{d'\in R}s(d')}{\max_{d'\in R}s(d')-\min_{d'\in R}s(d')},\]

а затем взять взвешенную сумму с весом \(\alpha\in[0,1]\):

\[S(d)=\alpha\,\hat{s}_{\text{lex}}(d)+(1-\alpha)\,\hat{s}_{\text{dense}}(d).\]

Отсутствующему документу нормированная оценка приписывается равной нулю. В примере для BM25 \(\min=4.0\), \(\max=12.4\), для плотного поиска \(\min=0.74\), \(\max=0.83\). При \(\alpha=0.5\):

Чанк\(\hat{s}_{\text{lex}}\)\(\hat{s}_{\text{dense}}\)\(S\)
A\(0.833\)\(0.778\)\(0.806\)
D\(1\)\(0\), нет в списке\(0.5\)
C\(0\)\(1\)\(0.5\)
B\(0\), нет в списке\(0.556\)\(0.278\)
E\(0.131\)\(0\)\(0.065\)

Теперь A первый. Но у нормализации есть три свойства, о которых нужно помнить.

  • Оценки зависят от состава списка. \(\min\) и \(\max\) берутся по найденным кандидатам. Если поиск вернёт ещё один документ с меньшей оценкой, нормированные значения всех остальных изменятся.
  • Последний найденный неотличим от ненайденного. C получил \(\hat{s}_{\text{lex}}=0\), потому что стоит последним в списке BM25, а D получил \(\hat{s}_{\text{dense}}=0\), потому что в список не попал. В итоге у них одинаковые \(S=0.5\).
  • Растягивание стирает силу сигнала. Лучший документ любого списка получает единицу, даже если весь список слаб: BM25 по запросу, где совпало только частое слово, или косинусы, различающиеся в третьем знаке. В примере разброс косинусов \(0.09\) растянут на тот же отрезок \([0,1]\), что и разброс оценок BM25 \(8.4\).

Вес \(\alpha\) подбирают на размеченных запросах из dev-выборки. Один вес для всех запросов — компромисс: запросам с идентификаторами выгоднее больший вес BM25, перефразированным вопросам — меньший.

Объединение по местам: Reciprocal Rank Fusion

Формула

Можно вообще не сравнивать оценки, а использовать только места документов в списках. Пусть \(r_i(d)\) — место документа \(d\) в \(i\)-м списке. Reciprocal Rank Fusion (RRF) назначает оценку

\[\operatorname{RRF}(d)=\sum_{i:\;d\in R_i}\frac{1}{k+r_i(d)},\]

где сумма идёт только по спискам, в которых документ есть, а \(k>0\) — константа сглаживания. Документ, отсутствующий в списке, получает от него ноль. Места не зависят от шкалы оценок, поэтому нормализация не нужна. В исходной работе \(k=60\), и это значение остаётся стандартным по умолчанию.

Посчитаем пример при \(k=60\). Чанк A стоит вторым в обоих списках, C — четвёртым и первым:

\[\operatorname{RRF}(A)=\frac{1}{62}+\frac{1}{62}\approx0.03226,\qquad \operatorname{RRF}(C)=\frac{1}{64}+\frac{1}{61}\approx0.03202.\]

ЧанкМесто в BM25Место в плотном поиске\(\operatorname{RRF}\), \(k=60\)
A\(2\)\(2\)\(0.03226\)
C\(4\)\(1\)\(0.03202\)
E\(3\)\(4\)\(0.03150\)
D\(1\)—\(0.01639\)
B—\(3\)\(0.01587\)

A первый. Заметно и другое: E, который оба поиска поставили в нижнюю половину, обходит D, лидера выдачи BM25.

Что делает константа k

Отношение вкладов первого и \(r\)-го места равно \((k+r)/(k+1)\). При \(k=60\) первое место весит лишь в \(64/61\approx1.05\) раза больше четвёртого, при \(k=1\) — в \(2.5\) раза. Большое \(k\) почти выравнивает места внутри списка. Сравним документ на первом месте одного списка с документом на месте \(r\) в обоих списках. Они получают равные оценки, когда

\[\frac{1}{k+1}=\frac{2}{k+r}\quad\Longleftrightarrow\quad r=k+2.\]

При \(k=60\) документ, вошедший в оба списка на места не ниже \(61\)-го, обходит лидера одного списка. Это и случилось с E и D. В пределе большого \(k\), раскладывая \(1/(k+r)=1/k-r/k^{2}+O(1/k^{3})\), получаем, что RRF сначала упорядочивает документы по числу списков, в которые они вошли, а при равенстве — по сумме мест. Малое \(k\), наоборот, приближает RRF к правилу «доверять первым местам». При \(k=1\) в нашем примере первым становится C: \(1/5+1/2=0.7\) против \(2/3\approx0.667\) у A.

Чем RRF платит за устойчивость

RRF не требует нормализации и подбора шкал, поэтому его удобно применять как правило объединения по умолчанию. Но он отбрасывает величины оценок. BM25 уверенно отделил D и A от остальных (\(12.4\) и \(11.0\) против \(5.1\)), а RRF видит только места \(1\) и \(2\). Если один из поисков на данном запросе вернул бесполезный список, RRF всё равно учитывает его наравне со вторым. Распространённое расширение — веса списков: \(\sum_i w_i/(k+r_i(d))\). Веса, как и \(\alpha\), подбирают на dev-выборке.

Сравнение правил объединения на нескольких наборах данных показало, что выпуклая комбинация нормированных оценок с подобранным \(\alpha\) не уступает RRF и часто его превосходит, а результат RRF заметно зависит от \(k\). Выбор между ними определяется тем, есть ли размеченные запросы для подбора параметров.

Объединение оценок использует силу сигнала, но требует согласовать шкалы. Объединение по местам не требует шкал, но не различает уверенное и неуверенное решение. В обоих случаях параметры (\(\alpha\), \(k\), веса, глубину списков) выбирают по качеству на размеченных запросах, а не по умолчанию.

Фильтрация по метаданным

Часто поиск ограничивают метаданными чанка: версией правил, продуктом, языком. Пусть в документации есть правила 2025 и 2026 годов, и пользователю нужны только действующие: фильтр version = 2026. Пусть ему удовлетворяет доля \(p\) чанков — скажем, \(p=0.05\), если новая версия пока охватывает лишь часть документации. Фильтр можно применить до поиска или после него, и от этого зависит, кто окажется среди кандидатов.

Фильтр после поиска

Пост-фильтрация (post-filtering): найти \(k'\) кандидатов без фильтра, затем выбросить неподходящие. Если подходящие документы распределены среди кандидатов так же, как в корпусе, после фильтра в среднем остаётся \(p\,k'\) кандидатов. При \(k'=50\) и \(p=0.05\) это \(2.5\) документа вместо нужных, скажем, \(10\), а нередко и ни одного. Чтобы получить \(k\) документов, нужно \(k'\approx k/p\), то есть \(200\) кандидатов. А если подходящие документы в среднем дальше от запроса — например, устаревшая версия описана подробнее и лучше совпадает с ним, — нужно ещё больше. Полнота теряется тем сильнее, чем жёстче фильтр.

Фильтр до поиска

Пре-фильтрация (pre-filtering): искать только среди документов, удовлетворяющих фильтру. Для BM25 это естественно: фильтр — ещё один список документов, который пересекают со списками терминов в инвертированном индексе. Для ANN-индекса сложнее. Граф HNSW строился по всем векторам, и если обходить только разрешённые вершины, при малом \(p\) граф распадается на несвязанные части, и поиск не доходит до нужных вершин. Поэтому реализации обходят и запрещённые вершины, но не включают их в результат. Чем меньше \(p\), тем больше вершин приходится просмотреть. При очень малом \(p\) выгоднее точный перебор разрешённых векторов: их немного. Хорошие векторные базы выбирают стратегию по оценке \(p\). Как именно работает ваша, стоит проверить, измерив полноту с фильтром относительно точного поиска по отфильтрованному подмножеству.

Фильтр в гибридном поиске

Фильтр должен одинаково действовать в обоих поисках. Допустим, BM25 применяет пре-фильтрацию, а плотный поиск — пост-фильтрацию с недостаточным \(k'\). Тогда подходящий документ, который плотный поиск нашёл бы с фильтром, отсутствует в его списке, получает вклад только от BM25 и в RRF проигрывает документам из обоих списков. Ухудшение выглядит как слабость плотного поиска, хотя причина в фильтрации.

Права доступа — тоже фильтр по метаданным, но с другим требованием: документ без прав не должен попасть ни в выдачу, ни в контекст генератора. Изоляцию пользователей и проверку прав разбираем в разделе о production-архитектуре.

Как проверить, что гибрид помогает

Выигрыш гибрида возникает только из различия ошибок. Если оба поиска находят одни и те же документы, объединение ничего не добавит, а задержка и сложность вырастут. Поэтому на размеченных запросах сравнивают три величины:

  1. recall@\(k\) каждого поиска по отдельности;
  2. полноту объединения \(C\) — потолок, которого может достичь любое правило объединения при данной глубине списков;
  3. recall@\(k\) после объединения — какую часть потолка правило реализовало.

Если потолок почти не выше лучшего из поисков, второй поиск не нужен. Если потолок высок, а результат объединения нет, дело в правиле или его параметрах. Если низок сам потолок, не хватает глубины списков или оба поиска не находят нужное. Тогда помогают увеличение \(k'\), исправление чанкинга или дообучение модели, а не другое правило объединения. Полезно считать метрики и по срезам: запросы с идентификаторами, перефразированные вопросы, запросы с фильтрами. Именно на них поиски расходятся сильнее всего.

Гибридный поиск на практике

Код воспроизводит расчёты раздела: сумму с min-max нормализацией и RRF для двух выдач из примера.

def min_max(scores):
    lo, hi = min(scores.values()), max(scores.values())
    return {d: (s - lo) / (hi - lo) if hi > lo else 1.0 for d, s in scores.items()}

def weighted_sum(lex, dense, alpha=0.5):
    nl, nd = min_max(lex), min_max(dense)
    docs = nl.keys() | nd.keys()
    return {d: alpha * nl.get(d, 0.0) + (1 - alpha) * nd.get(d, 0.0) for d in docs}

def rrf(rankings, k=60):
    fused = {}
    for ranking in rankings:                     # списки id в порядке выдачи
        for rank, d in enumerate(ranking, start=1):
            fused[d] = fused.get(d, 0.0) + 1 / (k + rank)
    return fused

lex = {"D": 12.4, "A": 11.0, "E": 5.1, "C": 4.0}      # BM25
dense = {"C": 0.83, "A": 0.81, "B": 0.79, "E": 0.74}  # косинусы, демонстрационные

top = lambda scores: sorted(scores, key=scores.get, reverse=True)
print(top(weighted_sum(lex, dense)))     # A первым; C и D делят 0.5
print(top(rrf([top(lex), top(dense)])))  # ['A', 'C', 'E', 'D', 'B']
print(top(rrf([top(lex), top(dense)], k=1)))  # ['C', 'A', 'D', 'E', 'B']

Во многих поисковых движках и векторных базах RRF встроен. Параметры при этом те же, что в формуле: константа \(k\) и глубина каждого списка \(k'\). В Elasticsearch, например, они называются rank_constant и rank_window_size. Глубину стоит задавать явно: документ, оказавшийся сразу за границей списка, получает от него ноль.

Практический порядок работы:

  • начать с RRF при \(k=60\) и глубине списков в несколько раз больше итогового \(k\);
  • измерить потолок объединения и результат на dev-выборке, в том числе по срезам запросов;
  • если есть размеченные запросы, сравнить с взвешенной суммой нормированных оценок и подобрать \(\alpha\);
  • проверить, что фильтры применяются одинаково в обоих поисках, и измерить полноту с самыми жёсткими фильтрами отдельно.

Объединённый список обычно передают реранкеру: он оценивает каждую пару «запрос — документ» точнее обоих поисков, и для него важно, чтобы правильный документ вообще попал в число кандидатов. Это предмет следующего раздела.

Ключевые статьи

  • Fox, Shaw. Combination of Multiple Searches, 1994 — первые правила объединения оценок нескольких поисков (CombSUM, CombMNZ).
  • Lee. Analyses of Multiple Evidence Combination, 1997 — нормализация оценок перед объединением и анализ того, почему объединение помогает.
  • Cormack, Clarke, Büttcher. Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods, 2009 — RRF и константа \(k=60\).
  • Bruch, Gai, Ingber. An Analysis of Fusion Functions for Hybrid Retrieval, 2023 — сравнение выпуклой комбинации оценок и RRF для объединения лексического и плотного поиска; чувствительность RRF к \(k\).
  • Gollapudi et al. Filtered-DiskANN: Graph Algorithms for Approximate Nearest Neighbor Search with Filters, 2023 — графовый ANN-индекс, учитывающий фильтры при построении.
