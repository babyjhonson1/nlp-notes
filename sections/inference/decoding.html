На выходе трансформера ещё нет выбранного токена: есть логиты — оценки всех токенов словаря. Правило декодирования (decoding) превращает эти оценки в следующий токен, который дописывается к контексту и меняет все последующие предсказания. Даже при неизменных весах жадный выбор, поиск нескольких продолжений и случайная выборка дают разные тексты. Температура меняет соотношение вероятностей, фильтры исключают часть кандидатов, а штрафы учитывают историю ответа. Чтобы управлять генерацией, нужно различать исходное распределение модели, распределение после этих преобразований и условие, по которому сервер завершает запрос.

Что предсказывает модель

Пусть \(x\) — промпт, \(y_{<t}\) — уже выбранные токены ответа, \(\mathcal V\) — словарь. На шаге \(t\) выходная проекция трансформера даёт вектор логитов (logits) \(z_t\in\mathbb R^{|\mathcal V|}\). После softmax получаем условную вероятность каждого токена:

\[p_t(v)=P_\theta(y_t=v\mid x,y_{<t})=\frac{\exp(z_{t,v})}{\sum_{u\in\mathcal V}\exp(z_{t,u})}.\]

Первое такое распределение получается из последней позиции промпта на prefill. Выбранный токен подаётся на следующий decode-шаг вместе с KV-cache; модель вычисляет новое распределение уже с учётом этого токена. Сэмплер (sampler) — код выбора токена — стоит после вычисления логитов. Он не меняет веса модели и не требует повторного прохода трансформера для каждого варианта температуры.

Дальше используем один условный пример: продолжение «В саду было» и словарь из шести токенов. Для наглядности каждому слову соответствует один токен, включая нужный начальный пробел; это не токенизация и не измерение конкретной LLM. В настоящем словаре есть также части слов, знаки и служебные токены.

Следующий токенИсходная вероятность \(p_t(v)\)Логит \(z_{t,v}=\log p_t(v)\), округлённо
« тихо»0,40−0,916
« спокойно»0,25−1,386
« темно»0,15−1,897
« холодно»0,10−2,303
« шумно»0,06−2,813
« квант»0,04−3,219

Логиты здесь специально выбраны как логарифмы вероятностей: softmax восстановит первую колонку чисел. В общем случае логит не равен логарифму вероятности: нормировка вычитает \(\log\sum_u\exp(z_{t,u})\). Добавление одной константы ко всем логитам распределение не меняет; поэтому для устойчивого вычисления softmax сначала вычитают максимальный логит.

Greedy и beam search: токен или последовательность

Жадное декодирование (greedy decoding) выбирает максимум на каждом шаге:

\[y_t=\operatorname*{arg\,max}_{v\in\mathcal V}z_{t,v}.\]

В примере это « тихо». Softmax для самого выбора не нужен: он сохраняет порядок логитов. Однако лучший токен сейчас не гарантирует самую вероятную последовательность целиком. Её вероятность складывается из условных вероятностей всех шагов, включая завершение:

\[\log P_\theta(y\mid x)=\sum_{t=1}^{|y|}\log P_\theta(y_t\mid x,y_{<t}).\]

Продолжим условный пример. Пусть после « тихо» наиболее вероятный следующий токен — EOS с вероятностью \(0{,}4\), а после « спокойно» — EOS с вероятностью \(0{,}9\). EOS (end of sequence) обозначает конец последовательности. Тогда greedy завершит ответ « тихо» с вероятностью пути \(0{,}4\cdot0{,}4=0{,}16\), хотя у пути « спокойно», EOS вероятность \(0{,}25\cdot0{,}9=0{,}225\). Первая локальная победа привела к худшему полному пути.

Лучевой поиск (beam search) сохраняет до \(w\) незавершённых гипотез вместо одной. Для каждой гипотезы считает распределение следующего токена, расширяет её кандидатами и сравнивает суммы логарифмов вероятностей по всем расширениям вместе. Лучшие незавершённые продолжения образуют следующий луч, завершённые сохраняются отдельно. В нашем примере ширина \(w=2\) сохраняет и « тихо», и « спокойно», поэтому второй путь не теряется на первом шаге. Это приближённый поиск: однажды отброшенная гипотеза уже не вернётся, даже если позже могла бы стать лучшей.

При сравнении разных длин появляется ещё один выбор. Каждый дополнительный множитель не больше единицы, и необработанная вероятность может предпочитать слишком короткие ответы. Например, оценка \(\log P_\theta(y\mid x)/|y|^\alpha\), где \(\alpha>0\), ослабляет этот эффект, но меняет цель поиска. Формула нормировки длины, учёт EOS и правило ранней остановки — часть конкретной реализации beam search. Увеличение ширины луча само по себе не гарантирует более полезного ответа.

В экспериментах Holtzman et al. на открытом продолжении текста GPT-2 максимизация вероятности часто приводила к шаблонным фразам и циклическим повторам. Это эмпирический результат для рассмотренных моделей и задач, а не доказательство бесполезности beam search. Важен сам разрыв: вероятность текста под моделью и качество ответа для пользователя — разные критерии. Кроме того, лучевой поиск держит несколько ветвей вычисления и KV-cache; совместное хранение префиксов экономит память, но не отменяет вычислений по разошедшимся ветвям.

Выборка и температура

Вместо поиска одного максимума можно делать случайную выборку (sampling): выбирать токен с вероятностями \(p_t\). В исходном примере « тихо» появляется в среднем в 40% независимых выборок из этого фиксированного распределения, « квант» — в 4%. После выбора контекст меняется: следующий токен нельзя снова выбирать из той же таблицы.

Температура (temperature) \(T>0\) масштабирует логиты до softmax. Обозначим изменённое распределение через \(q_T\), опуская индекс шага:

\[q_T(v)=\frac{\exp(z_v/T)}{\sum_u\exp(z_u/T)}=\frac{p(v)^{1/T}}{\sum_u p(u)^{1/T}},\qquad \frac{q_T(a)}{q_T(b)}=\exp\!\left(\frac{z_a-z_b}{T}\right).\]

Последнее равенство показывает механизм: температура меняет разрыв между кандидатами, сохраняя их порядок. При \(T=0{,}5\) вероятности из таблицы возводятся в квадрат и нормируются: « тихо» получает около 61,5%, « квант» — 0,6%. При \(T=2\) берутся квадратные корни: слабые кандидаты получают больше массы. Низкая температура усиливает уже имеющиеся предпочтения модели, но не проверяет их правильность.

При \(T\to0^+\) и единственном максимуме вся масса стремится к этому максимуму. Значение temperature=0 в движках обычно означает отдельную ветку greedy, а не деление на ноль. Если максимумы равны, математический предел распределяет массу между ними, тогда как greedy выбирает один по правилу разрешения равенств. При \(T\to\infty\) распределение стремится к равномерному по токенам с конечными логитами.

Температура сама по себе не удаляет хвост: при конечных логитах и положительной температуре все токены остаются возможными. Даже небольшой риск на отдельном шаге может накопиться за длинный ответ. Поэтому после изменения температуры часто ограничивают множество кандидатов.

Top-k, top-p и min-p: какие токены оставить

Все три фильтра выбирают множество разрешённых токенов \(S\), затем обнуляют остальные вероятности и перенормируют оставшиеся:

\[q_S(v)=\frac{q_T(v)\,\mathbf 1[v\in S]}{\sum_{u\in S}q_T(u)}.\]

Эквивалентная операция над логитами — поставить \(-\infty\) на исключённых позициях. Это жёсткое ограничение: удалённый токен уже не может выпасть, даже если он был допустимым редким продолжением. Ни один из этих фильтров не умеет отличать фактическую ошибку от редкой верной формулировки.

Top-k: фиксированное число кандидатов

Top-k sampling оставляет \(k\) наиболее вероятных токенов. При \(T=1\) и \(k=3\) это « тихо», « спокойно», « темно», суммарная масса — \(0{,}8\). После нормировки вероятности равны \(0{,}5\), \(0{,}3125\), \(0{,}1875\). При \(k=1\) выборка совпадает с greedy.

Число кандидатов не учитывает форму распределения: когда один токен почти несомненен, остальные могут быть лишними; когда много равноправных продолжений, фиксированное число отсекает часть хороших вариантов. Положительная температура не меняет ранжирование, поэтому сам набор top-k от неё не зависит, хотя вероятности внутри него меняются. При равенстве оценок на границе движки могут оставлять разное число токенов: это отдельная конвенция реализации.

Top-p: фиксированная суммарная масса

Ядерная выборка (nucleus sampling, top-p) сортирует кандидатов по убыванию вероятности и берёт минимальный начальный отрезок, набирающий заданную массу \(\rho\in(0,1]\):

\[m=\min\left\{j:\sum_{i=1}^{j}q_T(v_{(i)})\ge\rho\right\},\qquad S=\{v_{(1)},\ldots,v_{(m)}\}.\]

Токен, на котором сумма достигла или пересекла порог, включается. В нашем примере при \(T=1\) и \(\rho=0{,}8\) остаются те же три токена. При \(T=0{,}5\) первые два уже набирают около 85,5%, поэтому остаются только они. Если самый вероятный токен один превышает порог, top-p превращает выборку в детерминированную. Таким образом, температура меняет не только доли вероятностей, но и размер ядра.

Min-p: порог относительно лидера

Min-p sampling сохраняет токены, вероятность которых не меньше доли \(\mu\in[0,1]\) от вероятности лидера:

\[S=\{v:q_T(v)\ge\mu\max_u q_T(u)\}.\]

При \(T=1\) и \(\mu=0{,}2\) порог равен \(0{,}2\cdot0{,}4=0{,}08\): остаются первые четыре токена, включая « холодно». Их масса — \(0{,}9\), а вероятность « тихо» после фильтра — \(0{,}4/0{,}9\approx0{,}444\). Параметр не задаёт ни абсолютную минимальную вероятность, ни долю сохраняемой массы.

При \(\mu>0\) то же условие можно записать через логиты:

\[z_v\ge z_{\max}+T\log\mu.\]

Из него видно, почему при увеличении температуры min-p, применённый после температуры, допускает больший разрыв исходных логитов. При \(\mu=0\) фильтр отключён; при \(\mu=1\) остаются только максимумы. Nguyen et al. исследуют такой относительный порог как самостоятельный метод выборки; его результаты на конкретных задачах не означают, что он всегда лучше top-p.

Штрафы за повторы и порядок преобразований

Фильтры не знают истории: если повторяющаяся фраза стала самой вероятной, top-k, top-p и min-p сохранят её ведущий токен. Штрафы за повторы (repetition penalties) меняют логиты с учётом уже встреченных токенов. В аддитивной схеме \(c_v\) — число появлений токена в ответе, \(\lambda_f\) — штраф за частоту (frequency penalty), \(\lambda_p\) — штраф за присутствие (presence penalty):

\[z'_v=z_v-\lambda_f c_v-\lambda_p\mathbf 1[c_v>0].\]

Положительный presence penalty вычитается один раз независимо от числа повторов, frequency penalty растёт с их числом. Если « тихо» уже встретилось дважды, при \(\lambda_f=0{,}3\), \(\lambda_p=0{,}2\) его логит уменьшается на \(0{,}8\). В нашей таблице он станет около \(-1{,}716\), ниже « спокойно» с \(-1{,}386\), если остальные токены ещё не встречались. При последующей температуре \(T\) отношение вероятностей повторённого и неоштрафованного токенов дополнительно умножается на \(\exp(-0{,}8/T)\): сила штрафа зависит и от температуры.

У параметра repetition_penalty в vLLM и Transformers другая семантика. Для уже встреченного токена и множителя \(r>1\) используется преобразование по знаку логита:

\[z'_v=\begin{cases}z_v/r,& z_v>0,\\rz_v,& z_v\le0.\end{cases}\]

Обе ветви уменьшают оценку; простое деление отрицательного логита, наоборот, подняло бы её. Для невстреченных токенов логит не меняется. В отличие от softmax, такой штраф зависит от абсолютного уровня логитов: сдвиг всех оценок константой до штрафа может изменить итоговое распределение. Поэтому вычислять его из одних только нормированных вероятностей в общем случае нельзя. В vLLM 0.31 repetition penalty учитывает промпт и ответ, а frequency и presence — только сгенерированный ответ; это правило конкретного движка, которое нужно сверять при переносе настроек. Реализация штрафов vLLM.

Штраф применяется к идентификаторам токенов, а не к смыслу. Повтор имени, переменной в коде или окончания слова может быть необходим; перефразированный смысловой повтор может вовсе не попасть под штраф. Поэтому увеличение штрафа до исчезновения любых повторов не является критерием качества.

Почему порядок входит в определение сэмплера

Штрафы способны менять ранжирование, поэтому должны быть учтены до отбора кандидатов, если именно по изменённым оценкам мы хотим делать выбор. Для фильтров тоже важно, на каком распределении вычислен порог. На исходном примере top-p с \(\rho=0{,}8\) оставляет три токена. Если сначала применить top-k с \(k=3\) и нормировать, первые два получают суммарно \(0{,}8125\); последующий top-p оставит уже два. Это не пересечение двух множеств, независимо рассчитанных по исходному распределению.

В стандартном сэмплере V1 vLLM 0.31 основная последовательность для случайной выборки такова: обработчики ограничений и штрафов → температура → min-p → top-k/top-p → выбор токена. В приведённом ниже учебном коде top-p считается после нормировки оставшихся кандидатов; другие движки и бэкенды следует проверять отдельно, особенно на граничных вероятностях и равных логитах. Исходный код сэмплера vLLM фиксирует порядок для этой версии.

Параметры декодирования определяют новое распределение, а не просто «степень случайности». Для воспроизводимого сравнения нужно зафиксировать преобразования, их порядок и то, к каким токенам истории применяются штрафы.

Когда генерация заканчивается

Выбор следующего токена и остановка запроса — разные операции. Модель может сама выбрать служебный токен завершения; движок может остановить её раньше по строке или лимиту. Это различие нужно сохранять в результате:

УсловиеЧто проверяетсяСледствие
EOS или конец ходаВыбран один из терминальных token ID, заданных моделью и её конфигурацией генерацииЗавершение предложила модель. У чат-модели конец хода может отличаться от обычного EOS
Стоп-токенID выбранного токена входит в явно заданный списокСрабатывает на токен целиком; произвольная строка не обязана иметь один такой ID
Стоп-строкаВ декодированном тексте появилась заданная последовательность символовМожет пересекать границы токенов; при стриминге нужен буфер для возможного начала стоп-строки
Лимит новых токеновИсчерпан бюджет ответаЭто обрезка: текст или JSON могут остаться незавершёнными

Например, строка \nПользователь: может складываться из нескольких токенов. Запрет одного token ID не эквивалентен остановке на всей строке. Нужно также понимать, возвращает ли движок саму стоп-строку: в vLLM 0.31 она по умолчанию исключается из текста, а include_stop_str_in_output=True меняет это поведение.

Минимальная длина — ещё одно ограничение сэмплера: в vLLM min_tokens запрещает EOS и заданные стоп-токены до достижения минимума. Она не доказывает, что ответ должен быть такой длины; модель может продолжать уже законченную мысль. Напротив, max_tokens ограничивает число новых токенов, а допустимая длина контекста должна вмещать промпт вместе с ответом. Значение finish_reason="length" нельзя трактовать как успешное смысловое завершение.

Настройки EOS и шаблон чата нужно брать у конкретного чекпойнта: ручная замена служебных токенов может заставить модель дописывать следующий ход. Стоп-условия также не гарантируют корректный формат. Проверка грамматики при выборе каждого токена — отдельная задача структурированной генерации; одного top-p или строки } для неё недостаточно.

Logprobs и воспроизводимость

Логарифмы вероятностей (logprobs) позволяют оценить выбранный токен и ближайшие альтернативы. Но сначала нужно выяснить, какое распределение вернул движок: исходное \(p_t\), распределение после штрафов и температуры или окончательное после усечения. Например, для « тихо» без изменения температуры:

\[\log p_t(\text{« тихо»})=\log0{,}4\approx-0{,}916,\qquad \log q_S(\text{« тихо»})=\log(0{,}4/0{,}8)\approx-0{,}693\]

при top-k с \(k=3\). Оба числа верны, но отвечают на разные вопросы. При greedy токен выбирается детерминированно, хотя его исходная вероятность остаётся \(0{,}4\). Поэтому ненулевой отрицательный logprob при жадном выборе не является противоречием.

В vLLM 0.31 режим raw_logprobs возвращает логарифмы вероятностей до обработчиков; processed_logprobs — после обработки. Режимы raw_logits и processed_logits возвращают вообще не вероятности, а оценки. Для greedy «processed» также не следует автоматически понимать как логарифм точечной меры: сэмплер может вернуть log-softmax обработанных логитов до argmax. Режим задаётся параметром движка logprobs_mode; у prompt_logprobs нет преобразований выборки, так как токены промпта заданы заранее. Документация режимов vLLM.

Возвращённые лучшие несколько альтернатив обычно не покрывают весь словарь. Их вероятности не обязаны суммироваться в единицу; повторная нормировка изменила бы смысл оценок. Сумма исходных logprobs вдоль фактически выбранного пути даёт оценку этой токенной последовательности под моделью, но не вероятность её фактической выдачи сэмплером. Вероятность отдельного токена также не является калиброванной вероятностью истинности ответа: она зависит от формулировки, префикса и токенизации.

Что фиксирует seed

Начальное состояние генератора псевдослучайных чисел (seed) воспроизводит случайные решения только при том же вычислительном пути. Ему нужны те же распределения и тот же порядок расходования случайных чисел. Версия модели и токенизатора, шаблон чата, точный промпт, параметры и порядок преобразований, версия движка, точность вычислений и аппаратная конфигурация входят в условия воспроизводимости.

Даже без случайной выборки небольшое изменение логитов может поменять argmax у близких кандидатов. Причина зависимости от состава батча разобрана в continuous batching; ядра с инвариантностью к батчу устраняют этот источник расхождений в поддерживаемой конфигурации. Один и тот же seed не обещает побитово одинаковый ответ на другом движке или оборудовании. Ограничения vLLM приведены в документации воспроизводимости.

На практике

Один шаг без модели

Этот код использует только стандартную библиотеку Python. Он вычисляет распределение для конечных логитов: температура → min-p → top-k → top-p с нормировкой → выборка. При равных оценках top-k оставляет ровно заданное число токенов, предпочитая меньший индекс. Штрафы, служебные токены и стоп-условия здесь опущены; это проверяемая реализация механизма одного шага, а не замена серверного сэмплера.

import math
import random


def distribution(logits, temperature=1.0, top_k=0,
                 top_p=1.0, min_p=0.0):
    if not logits or not all(math.isfinite(z) for z in logits):
        raise ValueError("Нужны конечные логиты непустого словаря")
    if not math.isfinite(temperature) or temperature < 0:
        raise ValueError("Некорректная температура")
    if not isinstance(top_k, int) or top_k < 0:
        raise ValueError("top_k должен быть неотрицательным целым")
    if not (0 < top_p <= 1 and 0 <= min_p <= 1):
        raise ValueError("Некорректный порог")

    order = sorted(range(len(logits)), key=lambda i: (-logits[i], i))
    if temperature == 0:
        return [float(i == order[0]) for i in range(len(logits))]

    peak = logits[order[0]]
    weights = [math.exp((z - peak) / temperature) for z in logits]
    # max(weights) == 1: относительный порог можно проверить без softmax.
    keep = [i for i in order if weights[i] >= min_p]
    if top_k:
        keep = keep[:top_k]
    if top_p < 1:
        target = top_p * math.fsum(weights[i] for i in keep)
        prefix = []
        for i in keep:
            prefix.append(i)
            if math.fsum(weights[j] for j in prefix) >= target:
                break  # токен, пересёкший порог, уже включён
        keep = prefix
    total = math.fsum(weights[i] for i in keep)
    result = [0.0] * len(logits)
    for i in keep:
        result[i] = weights[i] / total
    return result


tokens = [" тихо", " спокойно", " темно", " холодно", " шумно", " квант"]
logits = [math.log(p) for p in [0.40, 0.25, 0.15, 0.10, 0.06, 0.04]]
q = distribution(logits, top_k=3, top_p=0.8)
print([round(p, 6) for p in q])
# [0.615385, 0.384615, 0.0, 0.0, 0.0, 0.0]

generator = random.Random(42)  # создать один раз, а не на каждом шаге
chosen = generator.choices(range(len(tokens)), weights=q, k=1)[0]
print(repr(tokens[chosen]))  # ' спокойно'

Код выше проверен запуском на условных логитах, включая граничные режимы фильтров. Распределения совпадают с расчётами в тексте и иллюстрации. Модель и GPU для этой проверки не использовались.

Перенос в движок

Пример настроек для vLLM 0.31.0, сверенный с документацией и исходниками на 9 октября 2026 года. Значения иллюстрируют выборку с top-p, а не рекомендуют универсальный режим для всех моделей. Параметры без явного значения могут прийти из generation_config.json чекпойнта; для чистого сравнения нужно фиксировать итоговую конфигурацию.

from vllm import LLM, SamplingParams

# llm — уже созданный экземпляр LLM на подходящем сервере.
# При его создании для исходных logprobs: logprobs_mode="raw_logprobs".
params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    top_k=0,                   # без ограничения top-k в vLLM 0.31
    min_p=0.0,                 # min-p выключен
    presence_penalty=0.0,
    frequency_penalty=0.0,
    repetition_penalty=1.0,    # нейтральное значение — один
    max_tokens=128,
    seed=42,
    logprobs=3,
)
outputs = llm.chat(
    [{"role": "user", "content": "Продолжи одной фразой: В саду было"}],
    sampling_params=params,
)
answer = outputs[0].outputs[0]
print(answer.text, answer.finish_reason)
if answer.logprobs:
    token_id = answer.token_ids[0]
    print(token_id, answer.logprobs[0][token_id].logprob)

Пример с vLLM не запускался: веса не загружались. SamplingParams описывает параметры; logprobs=3 запрашивает лучшие альтернативы и оценку выбранного токена, поэтому записей на позиции может быть больше трёх. В Transformers 4.57.1 случайную выборку включает do_sample=True; просто передать положительную температуру недостаточно, если выбран жадный режим. Beam search выбирается отдельно, через num_beams, и не равнозначен нескольким независимым выборкам.

Практический порядок настройки: сначала проверить шаблон чата, завершение ответа и базовый рецепт чекпойнта, затем сравнивать температуру и один фильтр на фиксированном наборе задач. Несколько фильтров имеют смысл, когда понятен вклад каждого; иначе изменение top-p может оказаться незаметным, потому что кандидатов уже удалил top-k. Для случайного режима нужны несколько seed и оценка разброса результатов. Вместе с качеством сохраняют длину ответа и причину остановки: более короткая обрезанная генерация может выглядеть быстрее, не решая задачу.
