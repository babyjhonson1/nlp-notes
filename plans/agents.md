# План главы «LLM-агенты»

Состояние на 2026-10-12. Правила — в [AGENTS.md](../AGENTS.md), опубликованные разделы — в [outline.json](../outline.json).

Цель — понимать механизмы агента и уметь реализовать основные архитектуры на LangGraph. Пользователь готовится к работе NLP-разработчиком: приоритет — переносимые навыки, исполняемый код и разбор решений по журналу. Не превращать главу в каталог технологий или общие советы. Основная линия блока: задача → ошибка первой реализации → изменение механизма → код → результат.

[Сверка 30 вопросов пользователя](notes/agents-question-coverage.md) указывает основные места ответов и состояние до уточнения плана. Вопросы — критерии полноты объяснения, а не отдельные короткие подразделы в формате FAQ. Покрытие планом не означает, что текст уже написан.

## Содержание и границы

1. **Устройство агента.** Сохранить объяснение отличия LLM от всей системы, цикл, разделение модели/исполнителя/среды и условия остановки. Связать с состоянием, узлами и переходами LangGraph; первый практикум уже показывает соответствие workflow и агентного цикла. Подробный контракт `state` и `invoke` раскрывается в `context-memory`, без переписывания удачного первого раздела.
2. **Инструменты.** Сохранить функцию → описание → предложенный вызов → проверку → исполнение → наблюдение; небольшой полный набор, выбор по этапу и поиск по каталогу с восстановлением после пропуска. Модель выбирает имя и аргументы по доступному контексту, код разрешает и выполняет вызов; `bind_tools` не обучает модель. API/REST и MCP уже введены: обнаружение через `tools/list` отделено от отбора описаний и выполнения через `tools/call`. При следующем уточнении явно сопоставить structured output, tool calling, разбор JSON и проверку Pydantic: соответствие схеме не доказывает истинность результата. Механика ограничений генерации — `inference/structured-output`; ошибки цепочки парсера — `context-memory`.
3. **Обучение.** Граница раздела — получение демонстраций, цели и маски обучения tool use; код подготавливает данные, не обучает модель. Рецепты, происхождение перенесённых иллюстраций и проверка — [в технической записи](notes/agents-trajectory-training.md). Выбор reasoning-модели для приложения разбирается в `planning`.
4. **Контекст и память.** Начать практику с минимального `StateGraph`: схема состояния → функция узла → обновление полей через reducer → `compile()` → `invoke()`. На одном входе проследить состояние до/после; узел может содержать обычный код, цепочку или вызов инструмента, не обязательно LLM. Развести частичное обновление из узла, выход графа по его выходной схеме и сообщения. Для цепочки `prompt | llm | parser` показать тип на каждом переходе и зависимость результата `invoke` от последнего компонента: строка, разобранный JSON или объект Pydantic. Сопоставить строковый парсер, разбор JSON и проверку схемы; на явно заданном парсере показать неверный синтаксис, допустимый JSON с неправильными полями, исключение и ограниченный повтор. Не обещать автоматического исправления любого JSON и не считать любой незакрытый JSON обязательно неисправимым: поведение зависит от парсера/режима и версии.

   Затем через потерю нужного факта объяснить, почему состояние программы не равно входу LLM: последние сообщения, сводка, структурированные условия и поиск по старым сообщениям. Извлечение из длинной истории: текущий запрос → фильтр пользователя/задачи/времени → отбор → разрешение противоречий → сборка входа. Долговременная память — полезные записи между сессиями с происхождением, обновлением и удалением; отдельно от истории, кеша и checkpoint. Ввести состав рабочего промпта через эту сборку: задача, доступные данные и инструменты, ограничения, формат результата, критерии остановки и нехватки данных; обязательность компонентов зависит от задачи, единого магического шаблона нет. Эксперименты с промптом — `evaluation`; упаковка найденных документов — RAG.
5. **Рассуждение, планирование и agentic RAG.** На одной задаче сравнить фиксированный workflow, ReAct (чередование выбора действия и наблюдения) и plan-and-execute (явный план, исполнение шагов и пересмотр после новых данных). Показать, где хранится план и как изменение наблюдения меняет следующий шаг; не выдавать название паттерна за обязательный отдельный фреймворк. Развести reasoning-модель, просьбу «подумай пошагово» и внешний агентный цикл. Через опубликованный рецепт обучения и дополнительный бюджет вычислений объяснить, почему reasoning может помогать сложным многошаговым задачам; преимущество проверяется на задаче, а не гарантируется названием или длиной рассуждения. Сравнить пользу для анализа/кода/планирования с ценой и задержкой на простом извлечении и маршрутизации. Рассуждение не даёт отсутствующих наблюдений, актуальной схемы БД, полномочий или гарантии корректности; для этого нужны источники, инструменты и проверки.

   Считать знакомой мотивацию agentic RAG из главы RAG: использовать готовый ретривер в графе уточнения, накопления оснований и остановки, не пересказывать chunking и ранжирование. Явно разобрать прежний вопрос «зачем RAG при наличии веб-поиска»: источник данных (веб, внутренние документы, БД) и способ управления поиском — разные решения; собственный векторный индекс не обязателен. Поиск отдельных отзывов не заменяет расчёт статистики по таблице. [Граница с RAG](rag.md#особые-договорённости) сохраняется.
6. **Код как действие.** Отличить code agent, генерирующего исполняемую программу, от агента для разработки ПО. На анализе заказов сравнить готовые функции и небольшой сгенерированный Python-код: составление вычисления → изолированное исполнение → результат/ошибка → ограниченное исправление. LangGraph управляет циклом; исполнитель кода предоставляется отдельно. Для text-to-SQL: прочитать реальную разрешённую схему через инструмент, при большом числе таблиц отобрать релевантные определения/связи/описания полей, сгенерировать SQL, проверить ссылки на таблицы и столбцы, выполнить и разобрать ошибку. Не полагаться на схему из памяти модели; не обещать устранения всех галлюцинаций. Успешное выполнение запроса не доказывает верный join, знаменатель или ответ. Привязку к схеме объяснять здесь, ограничения доступа — в `safety`.
7. **Надёжное выполнение.** Пауза/возобновление, checkpoint и потерянный ответ инструмента. Развести подтверждённый неуспех и неизвестный исход, повторы чтения и изменения среды. Ограниченные повторы, ключ операции и проверка статуса — на одном сбое; прежний пример заказа можно сохранить как короткий пример внешнего изменения. Checkpoint не объявлять гарантией однократного внешнего действия. В основном проекте — восстановление поиска/анализа без повторения уже завершённых дорогих шагов. Механика паузы здесь, условия разрешения — `safety`.
8. **Управление действиями.** Посторонняя инструкция в найденном тексте, права исполнителя и подтверждение конкретного изменения. Для доступа к БД явно задать минимальные права (read-only для аналитика), разрешённые таблицы/представления и строки пользователя, ограничение времени, объёма результата и ресурсоёмкости запроса, журналирование и отсутствие секретов в контексте. Проверять структуру SQL и доступ кодом; префикс `SELECT`, `LIMIT`, промпт или один валидатор сами по себе недостаточны. Записи — только отдельными разрешёнными операциями с проверкой условий. Для Python — изоляция процесса/файлов/сети и лимиты; запрет импортов сам по себе не является песочницей. Общие правила доверия к найденному тексту — ссылка на RAG, без копирования его разбора.
9. **Оценка и диагностика.** Проверяемый результат задачи, ошибки по шагам, стоимость и задержка; сравнение workflow, одного и нескольких агентов, способов отбора инструментов/контекста и reasoning-бюджета. Для итогового проекта — правильность вычислений, источников и выполнения ограничений; не подменять это сходством текста. Langfuse: дерево вызовов, входы/выходы, задержки, usage, оценки и сравнение прогонов; интеграция с LangGraph, происхождение оценок и границы подсчёта стоимости. Изменение промпта рассматривать как эксперимент: версия промпта/модели/инструментов/данных, гипотеза, одинаковый набор задач, срезы регрессий и откат; при вариативности нужны повторения. Держать отдельный тестовый набор, не подгонять всё под показательные примеры. Применить рубрику LLM-as-judge и калибровать по человеку; G-Eval и общие метрики генерации подробно принадлежат [справочнику](reference.md). Локальные проверки механики доступны без LLM и аккаунта Langfuse, качество настоящей модели ими не измеряется.
10. **Несколько агентов.** Сначала обычные параллельные инструменты, затем отдельные циклы и контексты для анализа таблиц и исследования текстов; небольшой координатор объединяет результаты. Одна LLM может обслуживать разные роли. Контракт делегирования: задача, разрешённые инструменты, входные данные, формат результата/доказательств и бюджет. Показать передачу ошибки, дублирование работы, объединение источников и остановку. Сравнить с уже собранным одиночным агентом по тем же заданиям. Итог — ограниченная система из двух специалистов и при необходимости координатора, без рекурсивного размножения ролей.
11. **От графа к сервису.** Один запрос пользователя проходит через HTTP-вход, проверку данных, запуск графа и сериализацию результата; термины вводить без предположения о знании бэкенда. Сопоставить FastAPI и Flask по контрактам, валидации, OpenAPI, ASGI/WSGI и работе с ожиданием внешних вызовов, не утверждать, что FastAPI всегда лучше или автоматически ускоряет модель, а Flask не поддерживает async. Pydantic: модели входа/выхода, проверка/приведение типов, ошибки, JSON Schema; это не проверка истинности и не управление правами. Отделить веб-сервис приложения от сервера инференса и долгой фоновой задачи. Хранение разобрать на состоянии этого приложения: SQL для связанных заказов, документы/ключ–значение для подходящих записей. Ответить, что хранится в NoSQL: документные, ключ–значение, семейства столбцов (wide-column), графовые; показать форму записи и запрос, а не каталог продуктов. NoSQL не означает отсутствия схемы, векторный индекс не требует отдельной NoSQL-БД. Для практики достаточно SQLite, вводить несколько хранилищ необязательно.

## Сквозной пример и практика

Первые примеры и готовая тетрадь сохраняют выбор бумажного «Маленького принца» на русском по полной цене и сроку доставки. Магазины условные; эпизод 2026-10-08, срок 2026-10-09. Пользователь поддержал направление итогового проекта — аналитик обращений/заказов с RAG и кодом. Для следующих практик переходить к этому проекту, не переписывая готовый материал ради замены примера.

Кандидат источника — [Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce): при его выборе проект называется аналитиком заказов и отзывов, поскольку это не переписка поддержки. Точный набор и выборка ещё не закреплены и не подготовлены; учесть язык отзывов, исторический период и происхождение переводов. Описание полей, учебные правила метрик и проверочные ответы готовит редактор; учебные документы явно отделять от реальных данных компании. Сначала один агент с RAG и вычислениями, затем обоснованное разделение на специалистов. Поисковые примеры не выдавать за репрезентативную выборку для подсчёта долей.

Практика — **три более крупные тетради `.ipynb`**, а не по заданию на каждый раздел. Данные, инструкции и проверки даёт редактор; ключевые функции и графы пишет пользователь. Готовые решения не публиковать заранее; сначала точечные подсказки и разбор. Предусматривать места для собственных экспериментов и проверки после перезапуска ядра.

| Работа | Основные навыки | Состояние |
| --- | --- | --- |
| [1. От workflow к агенту](../practice/agents/01_workflow_and_agent.ipynb) | Состояние, граф, условные переходы, инструменты, история, ошибки, остановка; ручной запуск через HF | Подготовлена к решению; пользователь ещё не выполнял |
| 2. Аналитик с RAG и вычислениями | Подготовленные таблицы/документы, поиск, контекст и память, фактическая схема БД, один агент; введение code agent в изолированном исполнителе | Запланирована; данные ещё не подготовлены |
| 3. Несколько агентов и надёжное приложение | Делегирование, ограничения, восстановление, проверяемые сценарии, сравнение с одним агентом и Langfuse; небольшой сервис как завершение | Запланирована |

[Запуск и маршрут практики](../practice/agents/README.md). У пользователя пока нет ключа модели; выбран путь через Hugging Face Inference Providers. Локальные упражнения работают без LLM. Удалённый вызов запускает сам пользователь; выбор доступной модели и провайдера ещё предстоит. Не выдавать прохождение проверок с заранее записанными решениями за проверку качества модели.

## Сохраняемые договорённости и открытые задачи

- Писать и согласовывать по одному разделу; следующим переработать `context-memory`. Вопросы из скриншотов не превращать в отдельную длинную анкету или требование раскрыть всё в ближайшем разделе.
- Вне главы: общие метрики генерации, выбор классификатора, аугментации и утечки кросс-валидации закреплены в [плане справочника](reference.md); внутренний механизм structured output — в [плане инференса](inference.md). В агентных разделах дать применение и ссылки, когда тексты появятся.
- Первый раздел сохраняет диагностику `ACCESS_CHECK_FAILED`; не переписывать его ради унификации. Во втором и третьем основной пример — выбор книги; отдельный диагностический пример сохранён в разборе Toolformer и шаблона Qwen в третьем разделе.
- `tool-calling`, `tc-parse`: после появления `inference/structured-output` добавить ссылку рядом с формулой маски. Формулу и таблицу гарантий сохранить в содержательно подходящем блоке, не удалять ради сокращения.
- Сверять изменяемые примеры, таблицы, код и иллюстрации. Общий дизайн и соседние главы не переписывать.
- Полный цикл пользователь пишет в первой тетради самостоятельно. Раздел 2 даёт готовый компонент одного хода с `ToolNode`, а не решение тетради; модель в локальном прогоне явно заменена записанными ответами.
