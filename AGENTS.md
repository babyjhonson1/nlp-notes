# Конспекты по NLP — правила для редакторов

Этот файл читают все агенты, которые правят сайт (Claude Code — через `CLAUDE.md`, Codex и другие — напрямую). Правила одинаковы для всех. Если просьба пользователя противоречит этим правилам, делай как просит пользователь, а при необходимости предложи обновить этот файл.

Сайт — личные конспекты по NLP, устроенные как тетрадь OneNote: главы → разделы. Читатель — человек с техническим образованием, который готовится к работе NLP-разработчиком: формулы и инженерные детали приветствуются, объяснять нужно строго и по существу, без научпопного упрощения. Материал строится вокруг переносимых идей, алгоритмов, метрик и компромиссов; API конкретных фреймворков разбираются только как практические примеры, без привязки всего конспекта к одному стеку. Язык сайта — русский.

## Порядок работы

1. Перед началом подтяни последние изменения (`git pull`): сайт правят из разных мест.
2. Прочитай `outline.json`, чтобы понять структуру. Перед работой над главой RAG также прочитай [её план](plans/rag.md), над главой «Модели» — [её план](plans/models.md): план задаёт порядок, содержание и границы разделов. После работы обнови в нём состояние соответствующего раздела и оставшиеся замечания. Тексты разделов целиком открывай только те, с которыми работаешь.
3. Перед тем как писать новый раздел, прочитай целиком хотя бы один готовый (например, `sections/rag/ann.html`) и выдерживай тот же тон, глубину и разметку.
4. Внеси правки.
5. Запусти `python3 tools/check.py` и исправь всё, что он нашёл.
6. Браузерную проверку пользователь выполняет сам: без отдельной просьбы не открывай браузер, а передай короткий список того, что проверить. Для локального просмотра нужен `python3 -m http.server 8000` в корне репозитория и http://localhost:8000. Открывать `index.html` как файл с диска нельзя: оглавление и разделы грузятся через `fetch`.
7. Закоммить в `main` с понятным сообщением на русском («Новый раздел: чанкинг», «ANN: исправлена формула PQ») и сделай `git push`. GitHub сам запустит проверку и опубликует сайт; если проверка не прошла, сайт не обновится.

Модели и бенчмарки на компьютере пользователя не запускать, веса не скачивать без его явного согласия: такие прогоны уже перегревали ноутбук. Если запуск необходим, сначала назвать цель, объём скачивания и ожидаемую нагрузку. Использовать первоисточники и ранее полученные результаты, отмечая их происхождение. Лёгкие проверки структуры, арифметики, JavaScript и токенизатора без весов допустимы. Не писать «код проверен запуском», если проверены только документация, токенизатор или эквивалентный фрагмент кода.

## Как вести планы глав

- План — краткая карта текущей работы: порядок и статус разделов, их содержание и границы, открытые задачи и особые договорённости главы. Общие правила не копировать из `AGENTS.md`, аннотации готовых разделов — из `outline.json`.
- После выполнения задачи обновить статус и убрать её из открытых. Не дописывать подробный отчёт «что было сделано»; для истории есть Git и рецензии.
- Происхождение измерений, версии, расчёты, источники и ограничения проверки сохранять отдельно: новые записи — `plans/notes/<глава>-<раздел>.md`, старые снимки — `plans/archive/`. В плане оставить короткую ссылку. Читать только запись, относящуюся к текущей задаче; архивы не являются действующими инструкциями.
- Открытое замечание хранить в одном месте — плане ответственной главы. Отличать невыполненную задачу от уже оговорённой неопределённости; не превращать отсутствие измерений в поручение запустить модель.

## Совместная работа нескольких агентов

- По умолчанию только один агент одновременно вносит изменения в текущий checkout. Закончив задачу, он запускает проверку, коммитит и отправляет изменения; следующий агент начинает с `git pull`.
- Не запускай Codex и Claude Code на запись в одном checkout одновременно: даже правки разных файлов могут пересечься в `outline.json`, `index.html` и Git-индексе.
- Если действительно нужна параллельная работа, используй отдельные ветки и отдельные worktree, заранее раздели файлы и своди изменения только после проверки каждой ветки.

## Оглавление: outline.json

```json
{ "id": "rag", "title": "RAG", "color": "#2E6E73", "sections": [
  { "id": "ann", "title": "ANN: приближённый поиск ближайших соседей",
    "status": "done",
    "summary": "1–3 предложения: о чём раздел и что в нём разобрано.",
    "concepts": ["ANN", "recall@k", "HNSW"] }
]}
```

- `id` главы и раздела — латиница в kebab-case. После создания не меняется: на нём держатся ссылки (`#/rag/ann`) и путь к файлу `sections/rag/ann.html`.
- Порядок в массивах = порядок на сайте. Перестройка структуры — это правка `outline.json` (и перенос файла в `sections/`, если раздел переехал в другую главу). Тексты при этом не переписываются.
- `status`: `"empty"` — текста нет (файла нет или он пустой), `"draft"` — черновик, `"done"` — готово.
- `summary` (1–3 предложения) и `concepts` (3–10 ключевых понятий) на сайте не показываются: по ним работают со структурой, не читая тексты. **При каждом создании или изменении раздела обнови его `summary`, `concepts` и `status`.**
- Цвета глав. Заняты: `#2E6E73` (RAG), `#55609E` (Инференс LLM), `#9A5B2E` (Мультимодальные LLM), `#6B7F2A` (Справочник), `#A63D5A` (Модели). Для новых глав бери по очереди: `#2F7FA8`, `#A47A1E`, `#4F5D73`.

## Новый раздел: по шагам

1. Добавь раздел в `outline.json` в нужную главу и на нужное место.
2. Создай `sections/<глава>/<раздел>.html` по шаблону ниже.
3. Если нужны интерактивные иллюстрации, создай `figures/<префикс>.js` (и при необходимости `.css`) и подключи их в `index.html` в блоках «Иллюстрации: стили» и «Иллюстрации: код» перед `assets/site.js`.
4. Заполни `summary`, `concepts`, `status`.
5. `python3 tools/check.py`, короткий список для браузерной проверки пользователем, коммит, push.

## Шаблон текста раздела

Текст должен последовательно объяснять центральную идею раздела. Новый термин вводится, только если он нужен для следующего шага объяснения, и раскрывается достаточно для понимания. Уточнения добавляются, когда без них возникает существенное заблуждение или непонятен выбор метода. Не перечисляй смежные технологии и детали реализации по одному предложению «для полноты». Техническая глубина — это объяснение формул, допущений и причин выбора алгоритма, а не количество упомянутых методов. По возможности проводи один пример через всё объяснение.

### Связность и строгость

- Новый метод по возможности вводится через конкретную проблему предыдущего: ошибка → изменение метода → результат на том же примере. Ориентиры — постепенная сборка BM25 в `rag/lexical-search` и разбор негативов в `rag/dense-retrieval`. Не переписывать удачные объяснения только ради единообразия.
- Формула должна работать в объяснении: показывать причину изменения ранжирования, направление градиента, стоимость или ограничение. Указывать необходимые условия, согласовывать размерности и различать потери одного примера, среднее по батчу и математическое ожидание. Не заменять математическую глубину списком формул.
- Различать доказанное свойство, эмпирический результат и рекомендацию. Не превращать наблюдение на одном примере или бенчмарке в гарантию; не приписывать улучшение одному компоненту без сравнения, которое выделяет его вклад. Оговорки нужны в местах, где меняется вывод, а не после каждого предложения.
- Разделять общий алгоритм, рецепт семейства и конкретный чекпойнт/версию библиотеки. Не переносить автоматически на всё семейство пулинг, токенизатор, нормировку, формат входа или функцию потерь одного варианта. Функция обучения и мера сравнения при использовании могут различаться — это нужно объяснить.
- Общие определения и выводы имеют основное место в справочнике; глава RAG раскрывает их роль в конвейере, карточка модели — конкретный рецепт. Коротко напомнить формулу или предпосылку можно; полный вывод и численный разбор не копировать между разделами. При появлении справочника не обрывать существующее объяснение механическим удалением нужных шагов.
- Числа оставлять в основной линии, если они объясняют механизм или подтверждают вывод. Второстепенные гиперпараметры и абляции — в справочной таблице или дополнительном блоке. Отмечать, где пример условный, где результат из статьи, а где локальное измерение; при изменении примера согласовывать текст, код и иллюстрацию.
- После правки сверять связанные утверждения в соседних разделах (метрика, нормировка, обозначения, границы применимости). Вне порученного объёма файлы не исправлять: записать точное замечание в план соответствующей главы или согласованную рецензию.

### Разметка

Заголовок раздела (`<h1>`) не пишется: сайт берёт его из оглавления.

1. `<p class="lead">` — вводный абзац, 3–6 предложений: какая задача, почему она важна, в чём суть подхода.
2. Содержание раздела по заголовкам `h2`:
   ```html
   <nav class="toc" aria-label="Содержание раздела">
     <p>Содержание</p>
     <ol><li><a href="#" data-jump="ann-task">Задача и метрики качества</a></li></ol>
   </nav>
   ```
   У каждого `h2` есть `id` вида `<префикс раздела>-<слово>` (`ann-task`, `cb-why`). Префикс один на весь раздел и уникален на весь сайт; тот же префикс используют иллюстрации раздела.
3. Основная часть: блоки `h2`, внутри при необходимости `h3`. Глубже `h3` не уходить.
4. Предпоследний `h2` — применение на практике: библиотеки, параметры, код.
5. Последний `h2` — «Ключевые статьи», список вида `Авторы. <i>Название</i>, год — чем важна.`

Термин при первом упоминании: русское название и английское в скобках, например «векторная база (vector database)». Важное обобщение или вывод — в `<div class="note"><p>…</p></div>`. Таблицы оборачиваются в `<div class="table-wrap">`. Код — `<pre><code>`, внутри `<` пишется как `&lt;`, `&` как `&amp;`. Картинки — только inline SVG или `data:` URI.

## Разделы главы «Модели»

Глава `models` — карточки моделей. Один раздел описывает семейство, то есть общий рецепт обучения, а не отдельный чекпойнт: варианты (например, E5, multilingual-e5 и e5-mistral) разбираются в одном разделе, а различия между ними называются явно. Порядок разделов, их границы и состояние ведутся в [плане главы](plans/models.md).

Порядок блоков раздела (дополняет общий шаблон выше):

1. `<p class="lead">`: какую проблему решали авторы и что нового по сравнению с предшественниками.
2. Архитектура — только отличия от стандартного BERT или decoder-трансформера. Сами эти архитектуры читатель знает, их не пересказывать.
3. Данные: откуда взяты, как фильтровались и чистились, как строились пары или примеры. Объяснять через конкретные примеры и компактные таблицы по правилам ниже.
4. Обучение: функция потерь с формулой в LaTeX, как подавались данные (формат входа, сборка батчей, негативы), этапы (предобучение, дообучение, дистилляция).
5. Что из этого следует при использовании: префиксы и инструкции, пулинг, функция сходства, предельная длина входа и т. п. Это ошибки, которые не выдают сообщений, а тихо снижают качество.
6. Предпоследний `h2` — практика: короткий пример загрузки и использования. Последний подраздел `h3` практики — таблица с числами (слои, размерности, параметры, длина контекста, словарь, объём данных), так что она стоит непосредственно перед статьями. В основном тексте числа приводить, только когда суть модели в масштабе или число подтверждает ключевой вывод.
7. Последний `h2` — «Ключевые статьи».

Если чекпойнты семейства сегодня почти не используют (как DPR), а ценен рецепт, карточка короче: во введении это сказано прямо, основной текст — рецепт и выводы из него для использования, без подробных таблиц данных и второстепенных абляций.

Факты (числа, датасеты, детали обучения) берутся из статей и официальных описаний моделей (model card, конфигурации чекпойнтов), а не по памяти. Если подтверждение не найдено, так и написать в тексте или пропустить. Для быстро меняющихся семейств указывать, на какую версию и дату актуален раздел.

Общие функции потерь (InfoNCE, triplet loss, дистилляция, MLM, span corruption, denoising) описываются один раз в справочнике, в разделе `reference/training-objectives`. В карточке модели формула приводится в обозначениях этой модели со ссылкой на справочник, вывод и общие свойства не повторяются. Справочник пополняется по мере того, как функции потерь понадобятся моделям.

Иллюстрации в карточках — только если рецепт обучения действительно трудно понять без картинки. Для схем архитектуры и обучения (башни кодировщиков, токены, векторы, стрелки прямого прохода и градиента, функция потерь) есть общие помощники `figures/mdl.js` и стили `figures/mdl.css`: переиспользуй их, как в `sbert-flow` и `dpr-flow`.

### Как описывать обучающие данные

Цель — дать читателю представить один обучающий пример, понять, откуда взялась связь между его частями и зачем такие данные нужны модели. Перечень названий корпусов сам по себе этого не объясняет.

- Если источников или типов примеров несколько, основной формат — компактная таблица: **«Датасет / источник» → «Пример обучающего примера» → «Как получена связь / разметка» → «Роль в обучении»**. Для одного простого источника достаточно короткого примера в тексте; не делать таблицу ради таблицы. Использовать существующий `table-wrap`.
- В примере показывать короткие конкретные тексты, а не только обозначения вроде «вопрос — ответ». Явно называть роли частей: запрос, позитив, негатив; посылка, гипотеза и метка; оригинал и перевод. Показывать негативы и целевые метки там, где они нужны для понимания рецепта. Не изображать любую пару как «вход → генерируемый ответ»: контрастивное обучение, классификация и дистилляция ставят разные задачи.
- Придуманные примеры явно помечать как **условные** (можно одной подписью ко всей таблице); их структура должна соответствовать реальным данным и рецепту. Не выдавать их за записи датасета. Для подлинных примеров указывать первоисточник.
- Перед таблицей кратко объяснять задачу этапа. Разные этапы обучения и существенно разные варианты семейства разделять, а не смешивать в одной большой таблице. Выбирать характерные источники и типы примеров; однотипные можно группировать. Не превращать таблицу в полный каталог корпусов.
- После таблицы оставлять только существенные пояснения о фильтрации, построении позитивов и негативов. Если фильтрация — центральная идея метода (например, фильтр согласованности E5), объяснять её отдельно и содержательно. Не пересказывать строки таблицы соседними абзацами и не дублировать блок обучения.
- Объёмы данных и доли смеси добавлять лишь когда они объясняют масштаб, выбор метода или результат; это не обязательные столбцы. Сводные числа по-прежнему размещать в таблице практики. В исторических карточках вроде DPR достаточно небольшой таблицы характерных примеров без подробной статистики выборок.

## Формулы — только LaTeX

- Любая математика, включая одиночные переменные и индексы, набирается в LaTeX: строчные формулы `\( ... \)`, выносные — отдельным абзацем `<p class="formula">\[ ... \]</p>`. Рисует MathJax 3 (SVG).
- Нельзя набирать математику через `<i>`, `<sub>`, `<sup>` и символы Unicode (`·`, `‖`, `ℝ`, `²`, `α`, `≈`). Знак `$` разделителем формул не служит.
- Внутри формул `<` пишется как `&lt;`, `&` как `&amp;` (например, в `cases`).
- Слова внутри формул — `\text{...}`, имена функций — `\operatorname{...}` или `\log`, `\exp`, `\max`.
- В текстах иллюстраций (пояснения `fig-say`, подписи, кнопки) формулы тоже LaTeX. В JS-строках обратный слэш удваивается: `"\\(x_{1}\\)"`. Внутри SVG (элементы `<text>`) LaTeX не работает — там только простые подписи.

## Справочник и всплывающие определения

- Полные определения и выводы формул находятся в главе `reference` («Справочник»). Базовую векторную математику отдельным разделом не добавляй: читатель её знает; возвращайся к ней только по прямой просьбе.
- Всплывающие карточки добавляются только к терминам, которые явно назвал пользователь, обычно при первом важном употреблении в разделе. Не размечай автоматически каждое совпадение.
- Краткое определение, формула и ссылка на полный раздел хранятся в едином реестре `assets/glossary.js`. Не копируй определения в код отдельных разделов.
- Термин в тексте размечается кнопкой `<button type="button" class="term-ref" data-term="mrr">MRR</button>`. Ключ `data-term` должен существовать в `GLOSSARY`.
- Карточка должна оставаться доступной по наведению, фокусу с клавиатуры и нажатию на мобильном устройстве. Это обеспечивает общий движок; в разделе не добавляй собственные обработчики.
- Формула в реестре тоже пишется в LaTeX. В обычной JS-строке обратный слэш удваивается.

## Иллюстрации

Иллюстрации нужны там, где они заметно упрощают понимание ёмкого алгоритма, процесса или компромисса: показывают работу по шагам, влияние параметра или сравнение режимов. Не добавляй декоративные схемы и не иллюстрируй каждый термин; один содержательный интерактивный рисунок может закрывать несколько близких методов. Для алгоритмов уровня HNSW предпочтительны пошаговый проигрыватель, ползунок параметра или переключение режимов.

Обязательной квоты иллюстраций на раздел или карточку нет. Сначала сформулируй, на какой вопрос отвечает рисунок; если тот же механизм уже наглядно разобран, дай ссылку. Это не повод удалять полезные готовые иллюстрации.

В тексте раздела:

```html
<figure class="fig" data-figure="cb-flat">
  <div class="fig-box" data-mount></div>
  <figcaption>Что показано и что можно делать.</figcaption>
</figure>
```

Код — функция `mountИмя(box)` в `figures/<префикс>.js`, зарегистрированная в конце файла:

```js
Object.assign(FIGURES, {
  "cb-flat": mountCbFlat
});
```

Функция может вернуть функцию очистки (снять таймеры и обработчики). Имена иллюстраций, функций и CSS-классов — с префиксом раздела. Общие помощники (`rng`, `legend`, `ICON`, `vlControls`, `vlPlayer`, `cbFit` и другие) лежат в `figures/common.js` и в файлах уже готовых иллюстраций — переиспользуй их, а не пиши заново. Цвета берутся из CSS-переменных (`--chapter`, `--fig-accent`, `--g1`…`--g4` и т. д.), чтобы работала тёмная тема.

**Порядок блоков внутри иллюстрации: картинка (`fig-stage`) → управление (`fig-row`: кнопки шагов, ползунки, переключатели) → текст пояснения (`fig-say`) → легенда (`fig-legend`).** Управление никогда не ставится под `fig-say`: длина текста меняется от шага к шагу и не должна сдвигать кнопки.

## Чего не делать

- Не менять `id` существующих глав и разделов.
- Не трогать дизайн, `assets/*` и общие стили без прямой просьбы.
- Не подключать внешние картинки и сторонние библиотеки без необходимости; если библиотека нужна, только с cdnjs.cloudflare.com с фиксированной версией.
- Не коммитить, если `python3 tools/check.py` выдаёт ошибки.
